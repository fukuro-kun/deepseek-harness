# Agent Note: Interception-Extension-Points — die typisierte Decision-Oberfläche, gegen die ein Hook programmiert
[English](2026-06-30-interception-extension-points.md) | [中文](2026-06-30-interception-extension-points.zh.md) | Deutsch

Status: implemented


## Problem

Das harness braucht ein Hook-Subsystem: Users erweitern oder gaten den Agent an Lifecycle-Punkten so, wie es Claude Code (CC) und Codex tun. Der Schlüssel-Reframe hinter diesem Design ist, dass **„native Hooks" kein Paket sind** — ein nativer Hook ist nur ein gewöhnliches Cordis-Plugin, das die kanonischen Lifecycle-Events abonniert. Das eigentliche Produkt ist also eine *mächtige, gut typisierte kanonische Event-API*; die CC/Codex-Bridges (die Pakete `dsh-hooks-claude-code` / `dsh-hooks-codex`) sind bloße Übersetzer, die ein externes Shell-Hook-Protokoll auf dieselbe API mappen. Alles, was eine Bridge kann, kann ein einfaches Plugin direkt — mächtiger (keine Serialisierungsgrenze, voller `ctx`, typisierte Returns).

Die Oberfläche braucht getrennte Verträge für Per-Prompt-Policy (CCs `UserPromptSubmit`), Session-Start-Beobachtung (CCs `SessionStart`), Pre-Tool-Policy, Around-Dispatch-Kontrolle, Post-Tool-Transformation, Final-Result-Beobachtung und Continuation mit einem modellzugewandten Grund. Diese Phasen zu vermengen gibt Plugins Mutationskanäle, die sie nicht brauchen, und macht Finalität von der Listener-Reihenfolge abhängig. Die [Event-Domain-Semantics-Agent-Note](../architecture/2026-06-30-event-domain-semantics.de.md) liefert die Drei-Domänen-Regel und das typisierte-Decision-Idiom; diese Agent Note wendet sie auf die Lifecycle-Extension-Points an.

## Entscheidung

Die kanonische Oberfläche trennt transformierbare Policy, Around-Dispatch-Kontrolle und Observe-only-Notification. Policy-Waterfalls geben kleine extension-point-spezifische **typisierte Decision-Unions** zurück; Wrapper geben normalisierte Ergebnisse zurück; Notifications erhalten unveränderliche Snapshots und können das Ergebnis nicht beeinflussen. Das Set deckt die in-scope Hook-Punkte (`session-start`, `prompt-submit`, `pre-tool`, `post-tool`, `stop`-via-Continuation) ab, während es nicht-hook Execution-Policy unabhängig komponierbar lässt.

**Agent-Events** (`dsh-agent`):
- `agent/session-start({ agent, source })` — Emit, einmal vor Turn 1, trägt eine `SessionStartSource` (`startup` für einen frischen/geforkten Create, `resume` für eine neugeladene persistierte Session; `clear`/`compact` reserviert). Eine reine Notification — sie KANN den Start nicht blockieren (eine bewusste Lücke: eine Bridge loggt/injiziert, sie gatet den Start nicht). Ein Listener seedet Context via `agent.inject()`.
- `agent/pre-step({ agent, messages, turn, step, signal }, next) → PreStepDecision` — Waterfall, gefeuert vor jedem vorgeschlagenen Schritt, nachdem der Loop seinen exklusiven Inbox-Batch atomar entfernt hat. Das Payload trägt `turn`, `step` und das Cancellation-`signal` des Requests (die pensionierten `PreStepContext`-Felder leben im Payload; siehe die [Payload-Object-Events-Entscheidung](../../archived/architecture/2026-08-06-agent-event-payload-objects.md)); `messages` ist leer für eine Tool-Continuation ohne dazwischenliegenden Input. `enter` gibt den vollständigen Nachrichten-Batch zurück, einschließlich etwaigen Current-Request-Contexts, den ein Listener beiträgt; `reject` öffnet keinen Schritt und lässt die geclaimten Nachrichten entfernt.

**`agent/turn-stopping`** ist eine awaited Notification an der natürlichen Stopp-Grenze. Ein Listener, der einen weiteren Schritt braucht, ruft `agent.steer()` mit explizit gesourctem modellzugewandtem Inhalt auf; der Loop liest dann die Outbox erneut und setzt den Turn entweder fort oder schließt ihn.

### Die Tool-Pipeline gibt jeder Phase eine Art von Autorität

Jeder Call folgt `tools/pre-execute` → Guards → `tools/execute` → Dispatch → `tools/post-execute` → definitions-eigenem `finalizeContent` → `tools/result`. Die Registry snapshotet den Caller-Input, materialisiert und friert Argumente ein, vergibt ein opakes Token und snapshotet den Final-Content-Callback der sichtbaren Definition, bevor die Policy beginnt. Verschachtelte Calls tragen nur das Eltern-Token. Identität bleibt unveränderlich; nur `signal` darf sich um den Dispatch herum ändern. Log, UI und Tool-Body stimmen daher darin überein, was gelaufen ist.

- **`tools/pre-execute`** ist das erweiterbare Waterfall-Gate. Seine `PreToolDecision` erlaubt, verweigert oder fragt. Deny überspringt `tools/execute` und den Core-Dispatch. Ask löst über den optionalen Approval-Seam auf: Nur `allowed-once` läuft durch Guards und Dispatch; Ablehnung, Cancellation, ein nicht verfügbarer Kanal, ein fehlender Approval-Service oder ein agent-loser Call wird zu einer normalisierten Denial. Jede aufgelöste Entscheidung erreicht weiterhin die Post-Policy; ein werfender Listener wird zu einem finalen normalisierten Fehler.
- **`ctx.tools.guard()`** installiert synchrone scope-aware Policy nach dem gesamten Pre-Execute-Waterfall. Ein Guard darf denyen oder enthalten, nie force-allown, sodass die Listener-Reihenfolge eine Operation nicht wiederbeleben kann, die ein finales Invariant verbietet.
- **`tools/execute`** ist der Around-Dispatch-Waterfall für Timeout-, Retry- und Metrik-Plugins. Ein Wrapper delegiert mit `next()` an den Core-Dispatch, darf das erforderliche `exec.signal` vorher ersetzen und wiederherstellen, es aber nicht entfernen, und erhält das bereits normalisierte kanonische Erfolg-/Fehler-Ergebnis eines geworfenen oder unbekannten Tools; ein Wrapper-verfasster Erfolg kurzschließt den Dispatch und wird über die aufgelöste Output-Deklaration erneut normalisiert.
- **`tools/post-execute`** ist der Inspect/Transform-Waterfall. Seine `PostToolDecision` akzeptiert, blockiert mit Feedback, ersetzt entweder Präsentationscontent oder kanonischen Wert oder hängt `additionalContexts` an. Wertersatz revalidiert und berechnet die Präsentation neu; Content-Ersatz erhält den programmatischen Wert und ist keine Vertraulichkeitsgrenze. Die zurückgegebene Decision ist der unterstützte Transform-Kanal.
- **`ToolDefinition.finalizeContent`** ist eine optionale synchrone, totale, nur-Content-Grenze, die mit der sichtbaren Definition bei Call-Erzeugung gesnapshotet wird. Sie läuft genau einmal, nachdem die Registry das Kandidaten-Outcome normalisiert und verlustfrei gesnapshotet hat, einschließlich Pre-, Around- oder Post-Listener-Fehlern, die spätere Waterfalls umgehen, und Fehlern, die beim Snapshoten eines anderen Result-Felds entdeckt werden. Sie darf `content` ersetzen oder mit `undefined` erhalten, kann aber `isError`, strukturierte Fehler-Identität, Contexts oder Präsentationsmetadaten nicht umschreiben. Hier setzt ein Tool sein eigenes Last-Mile-Content-Invariant durch, ohne Policy-Fehler in schwächere Block-Decisions umzuwandeln.
- **`tools/result`** ist die synchrone contained Notification nach jeder Transformation, verlustfreier JSON-Materialisierung und der äußeren Fehlergrenze. Sie erhält dieselbe eingefrorene Execution-Identität und einen unveränderlichen Snapshot des autoritativen Ergebnisses; Observer-Fehler sind pro Listener contained und können das von `ToolRuntime.execute()` zurückgegebene Outcome weder ändern noch ablehnen.

Core-Dispatch und Tool-Body sitzen innerhalb von Normalisierungsgrenzen, sodass Tool-, Listener-, Invalid-Canonical-Value-, Renderer-/Projektor-, Nicht-JSON-Präsentations- und Identity-Shape-Fehler als JSON-sichere `isError`-Ergebnisse aufgelöst werden, statt dem Turn zu entkommen. Ein Post-Execute-Listener kann daher ein geworfenes Tool inspizieren; definitions-eigene Final-Content-Invariants decken auch äußere Pipeline- und Kandidaten-Materialisierungsfehler ab; und ein finaler Observer sieht den execution-lokalen kanonischen Wert neben genau den Präsentationsfeldern, die das Session-Log persistieren kann. Der [Canonical-Tool-Output-Vertrag](../architecture/2026-07-20-canonical-tool-output-contract.de.md) besitzt die Wert-/Projektions- und Dauerhaftigkeitsregeln.

### Drei tragende Loop-Entscheidungen

1. **Pre-Step-Policy an jedem vorgeschlagenen Schritt ausführen.** Der Loop öffnet den Turn vor dem initialen Claim und der Entscheidung, sodass ein Rejection einen durable blockierten Turn ohne Schritt oder modellsichtbare Nachricht schließt. Eine Tool-Continuation ohne neu geclaimten Input reicht dennoch einen leeren Batch ein, sodass Per-Request-Context-Produzenten geloggte Nachrichten zu genau diesem Request hinzufügen können. Bei Enter öffnet der Loop den Schritt und hängt den zurückgegebenen Batch als `user/message`-Events vor der Request-Ableitung an. Jedes geclaimte Follow-up bleibt der einzige direkte Prompt seines Turns unter der [One-Send-One-Turn-Simplification](../simplification/2026-07-17-one-send-one-turn.de.md).

2. **Post-Tool-`additionalContexts` und asynchrone Injections treten in die Active-Batch-FIFO ein und hängen an, wenn dieser Batch abrechnet.** `content`/`feedback` formen das Ergebnis, das `execute()` zurückgibt, aber jeder Context ist eine eigene gesourcte `user/message`, und ein einzelner Schritt oder ein Composite-Tool kann viele erzeugen. Context sofort anzuhängen würde `result(c1) → context → result(c2)` verflechten oder verschachtelten Context vor sein äußeres Result stellen und die Tool-Call/Result-Adjazenz brechen. `ToolRunContext.deferContext()` sammelt daher Nested-Dispatch-Context über Fehler hinweg, `execute()` hebt das geordnete Array auf `ToolExecutionResult` hervor, und der Loop nimmt es in dieselbe FIFO auf wie `agent.inject()`-Calls während der Ausführung. Die FIFO hängt nach jedem aufgezeichneten Ergebnis an, wenn der Batch abrechnet, einschließlich vor dem Schließen eines unterbrochenen Turns. Ein akzeptierter Outer-Call erhält Deferred-Contexts vor Decision-Contexts; ein Outer-Block verwirft Deferred-Contexts und legt nur Contexts offen, die die blockierende Decision explizit liefert.

3. **Ein Stopping-Listener fordert Continuation über den Steering-Kanal an**, sodass der Top-of-Loop-Drain des nächsten Schritts es als Steering für den fortgesetzten Turn aufzeichnet — Next-*Step*-Steering innerhalb des GLEICHEN Turns, kein Next-*Turn*-Prompt.

### Pre-Tool-Input-Rewrite ist eine separate Konsistenzentscheidung

`PreToolDecision` kann keine Argumente umschreiben. History und der Audit-Call werden vor der Ausführung geloggt, und die UI-Präsentation liest denselben Input, sodass die Registry Argumente vor der Policy versiegelt. Ein gültiges Rewrite muss History, Audit, Präsentation und Ausführung aktualisieren, bevor die Identität erzeugt wird; dieser Vertrag gehört dem [Input-Rewrite-Proposal](../../proposed/feature/2026-06-30-pre-tool-input-rewrite.de.md).

### Grenzen

Das Service-Definition-Paket deklariert **keine** `hook/*`-Session-Events (das durable Hook-Invocation-Log); die gehören zu `dsh-hook-protocol`, weil ein natives Plugin typisierte Decisions ohne ein externes Hook-Log verwendet. Der Native-Plugin-Integrationstest (`packages/core/agent-loop/tests/interception.spec.ts`) komponiert die Extension-Points durch den echten Loop ohne `hook/*`-Protokoll. Compaction (`PreCompact`/`PostCompact`), Notification und Codex `PermissionRequest` bleiben außerhalb dieser Entscheidung. Der [Approval-Seam](2026-07-06-approval-seam.de.md) löst `ask`-Decisions über `ctx.approval` auf; terminales monotones Stoppen wird durch Tool-Result-Daten ausgedrückt, während `agent/turn-stopping` die letzte Chance ist, einen weiteren Schritt zu steuern.

## Erwogene Alternativen

- **Pre-Tool-INPUT-Rewrite als Teil dieses Extension-Point-Sets auszuliefern** — als Over-Reach-Signal verschoben; der Abschnitt oben trägt das Konsistenzproblem (Audit, History und Präsentation lesen alle das vor der Ausführung geloggte `tool/call.arguments`), und das [Pre-Tool-Input-Rewrite-Proposal](../../proposed/feature/2026-06-30-pre-tool-input-rewrite.de.md) besitzt das Design.
- **Die durablen `hook/*`-SessionEvents neben den Extension-Points zu deklarieren** — abgelehnt: Ein natives Plugin verwendet die typisierten Decisions ganz ohne Hook-Log (das Worked-Example beweist es), sodass das durable Log zur [Hook-Protocol-Library](../../../../packages/hooks/hook-protocol/README.de.md) gehört, nicht zur Extension-Oberfläche.

## Konsequenzen

Die kanonische Interception-Oberfläche ist einheitlich typisiert, ohne jeder Extension dieselbe Macht zu geben: Hooks geben Decisions zurück, Execution-Wrapper wrappen, terminale Guards dürfen nur denyen, und finale Observer beobachten nur. Der Loop besitzt Session-Start, Pre-Step-Claim-Abrechnung, Post-Tool-Context-Pufferung und Stopping; `dsh-tools` besitzt Identity-Sealing und die Fünf-Phasen-Execution-Pipeline. Ihre Verträge sind in [architecture.md](../../../../docs/architecture.de.md), Paket-READMEs, [Core-Interception-Decisions](../../../../docs/subsystems/core.de.md#interception-decisions) und [Tool-Structures](../../../../docs/subsystems/tools.de.md) dokumentiert. Die ACP-Bridge rechnet einen initialen Pre-Step-Rejection aus seinem blockierten Step-losen Turn als `end_turn` ab, während Hook-getriebene Snapshots das beobachtbare Bridge-Verhalten Ende-zu-Ende verifizieren.
