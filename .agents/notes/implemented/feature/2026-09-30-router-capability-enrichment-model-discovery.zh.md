# Agent Note: 从路由器能力元数据补充模型发现

Status: implemented

[English](2026-09-30-router-capability-enrichment-model-discovery.md) | 中文 | [Deutsch](2026-09-30-router-capability-enrichment-model-discovery.de.md)

## Problem

标准 OpenAI 兼容 `/models` 响应会标识模型，但不会报告上下文窗口或输出上限。一些路由器会在独立端点提供能力元数据，因此现有 Models 页面抓取操作虽然能列出模型 id，却缺少可靠采纳模型所需的信息。

## Decision

现有模型抓取操作会通过一次尽力而为的 `GET {root}/endpoints` 请求补充不完整的列表。`root` 是配置的列表基础 URL 去掉一个末尾 `/v1` 后的地址。解析器会考虑所有与已列出模型 id 匹配且状态健康的端点。最大的正数 `n_ctx` 提供 `contextWindow`；瞬时 slot 数不会决定元数据来源。只有当每个匹配的健康端点都报告了正数 `max_tokens_cap` 时，解析器才会提供 `maxTokens`，并取最小上限作为共享限制。解析器只填写模型列表省略的字段。`max_tokens_default` 是生成默认值，并非输出上限。

主模型列表请求的截止时间为十秒，可选能力请求的截止时间为三秒。两者都拒绝重定向。能力请求的传输、超时、响应大小或解析失败都不会影响原始模型列表。调用方取消仍会返回 `ABORTED`。如果主模型列表请求失败或超时，发现操作会返回可见的 `DISCOVERY_FAILED`，而不是空目录。共享发现类型不携带输入模态，因此能力探测不会采纳 `supports_vision`。

Models 页面会默认选中新模型，以及已报告容量与当前值不同的已配置模型；用户可以取消任意选择。应用选择会添加新行，并且只刷新所选现有行中已报告的 `contextWindow`/`maxTokens` 字段，同时保留其名称与其他字段。发现操作本身不会写入设置。行为文档见 [`llm-pi-ai`](../../../../packages/llm/llm-pi-ai/README.zh.md#discover-models-from-endpoints)。

## Alternatives considered

**继续手动维护能力值或运行同步脚本。** 手工维护的值可能与路由器元数据漂移，而脚本仍要求有人记得运行。现有抓取按钮已经是偶尔刷新模型列表的用户操作，可在此时完成能力补充。

**在模型选择或请求执行期间刷新路由器能力。** 运行时发现会让临时路由器可用性影响常规适配器或目录行为，并需要缓存刷新语义。由于模型集群很少变化，用户只需在编辑模型配置时刷新，因此 Models 页面操作已足够。

**将 `max_tokens_default` 用作 `maxTokens`。** 默认生成大小并非端点强制的输出上限；这样使用会错误描述路由器限制。解析器只采纳 `max_tokens_cap`。

## Consequences

- OpenAI 兼容列表仍是模型 id 及其已报告容量的权威来源；路由器元数据只补充缺失字段。
- 没有 `/endpoints` 的路由器仍会返回普通模型候选项。能力端点停滞时，此操作最多额外等待三秒。
- 主列表停滞时，最多等待十秒，随后 UI 会收到可恢复的发现错误。
- 能力策略报告健康端点中的最大上下文，并且只在每个健康端点都提供共享输出上限时报告该上限；它不报告输入模态或依赖提示词长度的剩余上下文计算。
- 回归测试覆盖匹配、多端点选择、容量优先级、元数据缺失或无效、重定向、截止时间和调用方取消。
