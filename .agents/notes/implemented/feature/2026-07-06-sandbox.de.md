# Agent Note: Die Subprocess-Sandbox — Einschränkungs-Seam, native Runner, Eskalation und modi pro Session

Status: implemented

[English](2026-07-06-sandbox.md) | [中文](2026-07-06-sandbox.zh.md) | Deutsch

## Problem

Ein Coding Agent braucht diesen Produktpfad: Bash-Subprozesse — und die Hook-Kommandos, die auf ihnen mitfahren — laufen standardmäßig in einer eingeschränkten Datei-Sandbox; genau dann, wenn die Sandbox eine Operation tatsächlich verweigert, darf das Modell eine einmalige Nutzerfreigabe für dieselbe Operation anfordern und sie nach Erteilung einmal mit weitergehenden Rechten wiederholen. Eine Grenze für alle Tools ist bewusst NICHT der Anspruch: fs/web/todo laufen prozessintern, wo ein `execve`-Wrapper nichts bewirkt (§ Prozessinterne Tools), und die familienübergreifende Grenze ist gestaffelte Folgearbeit (§ Zurückgestellte Phasen). Ohne gemeinsames Vokabular erfindet jedes Tool Freigabefelder, Verweigerungserkennung, Retry-Abgleich und Hinweise zum Berechtigungszustand neu.

Der Harness ist ein SDK, also muss Einschränkung eine Fähigkeit sein, die Entwickler KOMPONIEREN: ob eingeschränkt wird und welches Backend pro Plattform, gehört als erstklassiger Eintrag in die Leaf-`cordis.yml` — nicht in die private Maschinerie eines einzelnen Executors. Und der Runner der ersten Wahl, `bwrap`, ist genau auf den Hosts unbrauchbar, auf denen eine Sandbox am wichtigsten ist (minimale Container, deaktivierte unprivilegierte userns, LSMs, die `mount` verweigern) — ein Fallback-Runner muss also mit dem SDK ausgeliefert werden statt auf dem Host vorausgesetzt zu werden.

Einschränkung allein lässt zwei Lücken. Eine Verweigerung ohne Eskalationspfad ist endgültig — das Modell kann nur aufgeben, was Betreiber unter Druck setzt, global `workspace-write` oder `danger-full-access` zu konfigurieren, und die Sandbox damit aushebelt. Sandbox-Modus und Freigaberichtlinie können sich zudem über die Lebensdauer eines Agent ändern, durch Deployment-Konfiguration oder ein optionales UI-Richtlinienelement; Ausführung und modellsichtbare Richtlinie müssen aus demselben protokollierten Zustand abgeleitet werden.

## Entscheidung

Ein Seam, eine plattformspezifische Kette lokaler Backends, ein Consumer — und zwei Stellhebel darüber: ein Eskalationspfad pro Aufruf und Runtime-Modi pro Session. Alles Folgende wird aus der Leaf-`cordis.yml` komponiert; nichts berührt `agent-loop`. Familienübergreifende fs-Durchsetzung, Workspace-Roots pro Session und die Windows-Kette sind als Folgearbeit auf demselben Richtlinienträger ausgeliefert; der `subagent-acp`-Consumer und weitere Umgebungen bleiben unter § Zurückgestellte Phasen.

### Wie ein Deployment sie nutzt

Vier `cordis.yml`-Einträge verwandeln einen uneingeschränkten Coding Agent in den Sandbox-Produktpfad; das [Base-Profile-Bundle](../../../../packages/bundle/base/cordis.patch.yml) nutzt diese Komposition standardmäßig:

```yaml
- id: sandbox
  name: '@deepseek-ai/dsh-sandbox-local'   # the per-platform runner provider (ctx.sandbox)
- id: bash
  name: '@deepseek-ai/dsh-bash-sandbox'    # the confined executor, replacing dsh-bash-local behind ctx.shell
  config:
    mode: workspace-write                  # the deployment default every session starts from
    workspaceRoot: !!js process.cwd()      # the boundary workspace-write may write under
- id: approval
  name: '@deepseek-ai/dsh-user-approval'        # the escalation gate's channel (the approval Agent Note)
  config:
    policy: ask
- id: permission
  name: '@deepseek-ai/dsh-permission-presets'      # one product-facing select over both mechanism knobs
```

Der Austausch ist für jeden Consumer von `ctx.shell` unsichtbar: Die Bash-Tools, Hook-Kommandos und Background Jobs laufen exakt wie zuvor, indem sie das vom Provider zurückgegebene umhüllte argv direkt spawnen. Das Entfernen der Einträge `sandbox` und `permission` sowie das Ersetzen von `bash` durch `@deepseek-ai/dsh-bash-local` ist das Opt-out — die Ausführung ist wieder uneingeschränkt und die Eskalationsfelder verschwinden aus dem Tool-Schema, weil sie auf dem gemounteten Executor capability-gated sind, nicht auf der Konfiguration. Nur `approval` wegzulassen behält die Einschränkung, lässt aber jede Eskalation mit eigenem Fehlertext geschlossen fehlschlagen; `permission` erfordert ebenfalls den Approval-Seam und einen einschränkenden Executor, sodass eine teilweise komponierte Preset-Schicht beim Laden laut fehlschlägt.

Fehlkonfiguration schlägt laut fehl: Ein `mode` außerhalb des geschlossenen Vokabulars wird beim Laden des Plugins zurückgewiesen, und ein Host ohne nutzbares Backend wirft bei `confine()` den strukturierten `SANDBOX_UNAVAILABLE`, statt auf uneingeschränkte Ausführung zurückzufallen. Ein zurechenbarer `ENOENT` oder `EACCES`, der den gewählten Runner nennt, beweist, dass die Executable nicht gestartet wurde — der Consumer meldet also denselben Infrastrukturfehler; andere synchrone Erzeugungsfehler werden unverändert weitergereicht. Eine asynchrone Subprocess-Provider-Abweisung legt keine öffentliche Zielphase offen und behält phasenneutrale lokale Semantik. `runnerCommand` auf `dsh-sandbox-local` ist die explizite Zusicherung des Betreibers, dass ein bwrap-kompatibler Runner vorliegt (Kette und Probes werden übersprungen); es dient zugleich als deterministischer Fake-Runner-Hook für schlüssellose Tests.

Verweigerte Dateieffekte liefern eine `[sandbox: file access denied under <mode> mode]`-Markierung und die Anweisung, die Verweigerung nicht zu umgehen. Ein einschränkender Executor fügt die gepaarten Felder `sandbox_permissions` und `justification` für einen genehmigten Retry hinzu, der strikt weiter sein muss als der effektive Modus der Session. Eine Erteilung erweitert nur diesen Retry; eine Ablehnung führt nichts aus, liefert `the user rejected escalating this command to "<mode>"` und erlaubt kein erneutes Nachfragen. Der vom Owner abgeleitete anstehende Richtlinienkontext benennt die aktuelle Dateirichtlinie, ohne diese Durchsetzungsgrenzen zu ersetzen. Wird `dsh-permission-presets` mit einem UI-Adapter komponiert, wählt ein Preset beide Stellwerte zugleich; nicht passende Werte fallen auf `custom` zurück. Das [ACP-App-Bundle](../../../../packages/bundle/acp-app/README.de.md) mountet diesen UI-Service nicht und wählt seinen Deployment-Modus explizit.

### Design-Details

#### Abgrenzung des Geltungsbereichs

OS-Subprocess-Einschränkung gilt für den Bash-Executor einschließlich Hook-Kommandos und später für ACP-Subagent-Children. Dateisystem-, Web- und andere Tools laufen prozessintern und brauchen Richtlinie an ihren eigenen Seams; ein argv-Wrapper kann keine Funktion einschränken, die über `ctx` schließt. Die bestehende Bash-Request/Spec-Trennung trägt Overrides pro Aufruf, während `tools/pre-execute` und der Approval-Seam die einmalige Richtlinienentscheidung besitzen.

#### Der Seam: `ctx.sandbox`

`dsh-sandbox` besitzt das Vokabular und den `SandboxProvider`-Vertrag: `confine(argv, policy)` liefert das argv, das der Aufrufer STATT seines eigenen spawnen soll — so umhüllt, dass der Prozess und alles, was er startet, eingeschränkt laufen — plus die `enforcement`-Vollständigkeit, die das gewählte Backend erreicht, seinen Verweigerungsdialekt (`denialSignatures`, die stderr-Substrings, die der Kernel des Backends bei einem verweigerten Dateieffekt ausgibt) und seine strukturierte Runner-Fehler-Evidenz (`runnerFailureRules`, optional erlaubte Exit-Codes plus fatale Zeilen-Signaturen nach exakten Ausschlüssen informativer Zeilen); ohne nutzbares Backend wirft es den fail-closed `SANDBOX_UNAVAILABLE`-Fehler, niemals ein stilles uneingeschränktes Durchreichen. Das Vokabular: `SandboxMode` (`read-only` / `workspace-write` / `danger-full-access`, nur DATEI-Effekte — Netzwerk und Prozess-Sichtbarkeit werden nicht beansprucht), `SandboxEnforcement` (`full` / `partial`), `SandboxExecutionPolicy` (der vollständige Modus pro Fähigkeitsaufruf + Workspace-Root) und `SandboxPolicy` (die eingeschränkte Provider-Teilmenge).

Die Richtlinie reitet auf jedem AUFRUF, nicht auf dem Provider: Zwei Consumer können im selben Moment unter verschiedenen Richtlinien einschränken (bash unter `read-only`, während ein eingeschränkter Child Agent sein State-Verzeichnis beschreibbar hält), und ein genehmigter eskalierter Retry ist ein neuer Aufruf mit weiterer Richtlinie — unter einem konfigfixierten Provider-Modus nicht ausdrückbar.

Der Seam beschränkt nur SAME-WORLD-Subprozesse: Ein Backend teilt Dateisystem und Kernel des Hosts. Container, MicroVMs und Remote-Executors sind KEINE Backends dieses Seams — sie ersetzen die Service Providers ganzer Capability Seams (`ctx.shell`, `ctx.fs`) als umgebungskohärente Gruppen, denn ein Agent, dessen bash in einem Container läuft, während seine fs-Tools auf den Host schreiben, lebt in zwei gespaltenen Welten.

Offen gelassen für die Phase, die sie braucht: ob Netzwerkrestriktion als eigenes `network_mode` kommt oder in `sandbox_mode` aufgeht, sobald ein Runner beides durchsetzt, und ob `SandboxPolicy` jetzt schon zusätzliche beschreibbare Root-Grants bekommt (der Launcher spricht bereits `--rw <path>`) oder erst, wenn die Eskalation sie braucht.

#### Lokale Backends und der mitgelieferte Launcher

`dsh-sandbox-local` wählt einen Plattform-Runner pro Provider-Lebensdauer und cached das Urteil. Linux prüft funktional `bwrap`, dann Landlock; macOS nutzt Seatbelt. Nicht unterstützte Plattformen und unbrauchbare Runner schlagen geschlossen fehl. Jede Umhüllung trägt backend-spezifische Verweigerungssignaturen und Runner-Fehler-Regeln, damit `dsh-bash-sandbox` einen verweigerten Dateieffekt von einer kaputten Sandbox unterscheiden kann. Ein Landlock-Runner-Fehler erfordert Exit 125 plus eine `landlock-run:`-Zeile, die kein Hinweis ist; die exakte Partial-Enforcement-Zeile ist selbst dann nur informativ, wenn ein Child mit 1, 2 oder 125 endet. Bubblewrap und Seatbelt bleiben rein signaturbasiert, weil keiner der öffentlichen Verträge einen Launcher-Fehler-Status reserviert. `runnerCommand` behält seine operatorseitige `runnerFailureSignatures`-Konfiguration, verlangt nicht-leere einzeilige Einträge und bildet sie auf eine interne fatale Regel ab. Der Consumer spawnt jedes zurückgegebene argv direkt, sodass ein fehlender Runner, ein nicht ausführbarer Runner oder ein ausführbares Skript mit nicht verfügbarem Shebang-Interpreter über den zurechenbaren `ENOENT`/`EACCES`-Spawn-Kanal fehlschlägt, während ein erfolgreich gestartetes Child mit Exit 126 oder 127 ein gewöhnliches Ergebnis bleibt. Ein vom Betreiber konfiguriertes Skript besitzt notwendigerweise den Start seines Interpreters, bevor es sein Profil anwendet.

Der Launcher ist ein ~300-zeiliges C-Programm (schlichtes C11 über der rohen Landlock-UAPI — keine Bibliotheken außer einem statisch gelinkten musl, die Audit-Fläche ist also diese eine Datei plus der stabile Syscall-Vertrag des Kernels): `--ro <path>`- / `--rw <path>`-Grants, `--`, das umhüllte argv; er installiert das Regelwerk auf sich selbst und führt `exec` aus (Regelwerke werden über `execve` vererbt, und er setzt `no_new_privs` vor dem Einschränken); `--probe` erzwingt ein maximales Regelwerk in einem kurzlebigen Child und endet nur dann mit 0, wenn der Kernel tatsächlich durchsetzt; jeder Launcher-Fehler endet mit 125, ohne das Child zu starten, und gibt eine fatale `landlock-run:`-Zeile aus. Ein erfolgreich geexec'tes Child kann ebenfalls 125 liefern, der Status allein ist also kein Launcher-Beweis. Eine ältere ABI gibt die exakte Meldung `landlock-run: partial enforcement (older Landlock ABI)` aus, bevor sie das Child ausführt — diese Zeile ist daher kein fatales Indiz.

Der Landlock-Launcher-Quelltext und die Paketfamilie liegen unter `native/system`, neben den Harness-Consumern und innerhalb des Root-pnpm-Workspace. Das [`native/` README](../../../../native/README.de.md) besitzt Lockfile, nativen Build, Pack-Probe und die npm-Veröffentlichungsgrenze. Plattformbinärdateien wählt npm aus, und das Entry-Paket besitzt Pfadauflösung, Probing, CLI-Flags, das fatale Präfix und die Partial-Enforcement-Meldung, während der Harness Sandbox-Modi auf Grants abbildet. Das gemeinsame Versionieren von Entry-Point und Binärdateien hält Probe-Parsing und Launch-Syntax aufeinander abgestimmt.

Backend-Profile teilen den Modus-Vertrag, unterscheiden sich aber in den nötigen Host-Grants. Landlock und Seatbelt erlauben im read-only-Modus nur `/dev/null`; workspace-write erlaubt zusätzlich die benötigten Host-Temp-Roots. Jede Umhüllung trägt backend-spezifische Verweigerungssignaturen. Landlock meldet auf älteren ABIs, die nicht jede Operation beherrschen, Partial Enforcement, während erfolgreiche bwrap- und Seatbelt-Profile Full Enforcement melden.

#### Der Bash-Consumer

`dsh-bash-sandbox` erweitert `LocalBashExecutor`, reicht das exakte `['bash', '-c', command]`-argv an `ctx.sandbox` und spawnt das Provider-Ergebnis direkt. Damit bleiben Shell-Semantik und `BASH_ENV` beim inneren Bash, nachdem der mitgelieferte native Runner die Einschränkung hergestellt hat. Ein Provider-Fehler wird unverändert weitergereicht. Eine asynchrone Abweisung zählt nur dann als Runner-Fehler, wenn das aufrufereigene workdir unabhängig nutzbar ist und Node `ENOENT` oder `EACCES` meldet — entweder mit einem `error.path` gleich Provider-argv[0], oder, wenn `error.path` fehlt, mit einem exakten `syscall: 'spawn <runner>'`; ein vorhandener Pfad erfordert zusätzlich `syscall: 'spawn'` oder das exakte `spawn <runner>`. Andere Codes, ungültige workdirs, Ressourcenfehler, fremde syscalls und unstrukturierte Abweisungen behalten die phasenneutrale Provider-Failure-Semantik. Die Foreground-Ausführung wandelt zurechenbare Runner-Fehler in `SANDBOX_UNAVAILABLE` mit dem ursprünglichen Detail um; eine zurechenbare asynchrone Background-Abweisung stempelt `runnerFailed: true`, `denied: false`. Eine `SubprocessRuntime`, die synchron dieselbe runner-identifizierende Form wirft, lässt den Background-Start `SANDBOX_UNAVAILABLE` werfen, während andere synchrone Fehler unverändert propagieren. Sobald ein direktes Ergebnis vorliegt, nutzen Foreground und Background einen gemeinsamen Runner-Failure-Classifier, der die Exit-Code-Prüfung der Regel und eine verbleibende fatale Zeile nach Ausschluss informativer Zeilen verlangt. Ein Match hat Vorrang vor Verweigerung: Die Foreground-Ausführung wirft `SANDBOX_UNAVAILABLE` mit dieser fatalen Zeile als Detail; ein abgerechneter `ShellProcess` stempelt `sandbox.runnerFailed`, und der Bash-Producer rendert es über das generische `job_output`.

Das Modell sieht die aktuell wirksame Dateirichtlinie im vom Owner abgeleiteten `sandbox:policy`-Kontext, während die statische Tool-Beschreibung die Verweigerungsmarkierung (`[sandbox: file access denied under <mode> mode]`) erklärt, zum Ausprobieren möglicherweise verweigerter Kommandos ermutigt und das Umgehen einer Verweigerung verbietet; werden die Eskalationsfelder annonciert, trägt ein verweigertes Ergebnis zusätzlich den Eskalationshinweis selbst, sodass der sanktionierte Retry im selben Turn am Entscheidungspunkt angeregt wird statt vom Erinnerungsvermögen des Modells an die Beschreibung abzuhängen (§ Eskalation). [Die Current-Policy-Entscheidung](../../archived/feature/2026-07-30-current-sandbox-policy-context.md) besitzt Begründung und Grenzen dieses Kontexts.

#### Eskalation: ein genehmigter weiterer Retry nach einer Verweigerung

`ShellExecRequest.sandboxPolicy` ist eine optionale, vollständige Eingabe pro Aufruf; aufgelöste Specs machen das Feld explizit. `ShellExecutor.sandboxMode` bleibt die Capability-Tatsache, die anzeigt, ob der gemountete Executor diese Richtlinie einlösen kann — nur eine einschränkende Komposition exponiert also Eskalation. Der Seam akzeptiert jede explizite Richtlinie; das Tool besitzt Session-Auflösung und die Nur-weiter-Eskalationsregel. Nicht-sandboxende Executoren bleiben ehrlich uneingeschränkt.

`ctx.sandboxPolicy.resolve()` stempelt die vollständige Ausführungsrichtlinie — expliziter Eskalationsmodus > Session-Override > konfigurierter Default, mit `SessionHeader.cwd` > konfiguriertem Fallback-Root — bevor der Executor läuft. `SandboxBashExecutor.resolve()` behält diese Richtlinie auf dem Spec oder liefert den Deployment-Fallback für einen direkten agentlosen Aufrufer, sodass `run()`/`start()` niemals veränderlichen Session-Zustand lesen. Wrap-Fakten pro Prozess werden am zurückgegebenen `ShellProcess` gekeyt; `onProcessDone()` erhält Spawn-Fehler out-of-band von der stderr-Klassifikation und stempelt dieses Handle, bevor `done` sich abrechnet — überlappende Prozesse behalten so ihre eigenen Modi und Runner-Dialekte.

Ist ein einschränkender Executor gemountet, annonciert `bash` die gepaarten Felder `sandbox_permissions` und `justification`. Das Schema exponiert das vollständige geschlossene Eskalationsvokabular, weil der effektive Modus pro Session gilt; die Ausführung weist jedes Ziel zurück, das nicht strikt weiter ist als der effektive Modus dieses Aufrufs. Die Freigabe wird vor der Ausführung aufgelöst. `allowed-once` stempelt den genehmigten Modus nur auf diesen Request, während `rejected`, `cancelled`, `unavailable`, ein fehlender Approval-Service oder ein fehlender Agent jeweils mit eigenen Ergebnissen geschlossen fehlschlagen. Kein Grant wird persistiert.

Eskalation ist ein Retry im selben Turn des verweigerten Kommandos mit dem engsten hinreichenden `sandbox_permissions` und einer `justification`; der Freigabe-Prompt ist der Zustimmungsschritt. Sie muss auf einer tatsächlichen Verweigerung gründen, es sei denn, die Session hat denselben verweigerten Zugriff bereits beobachtet, und eine deaktivierte oder abgelehnte Freigabe beendet das Kommando. Retry, Freigabeentscheidung und Ergebnis nutzen die bestehenden Tool- und Approval-Events. `dsh-tool-bash` besitzt die Anfrage, weil die Service Definition des Executors weder den Agent noch die Call-ID hat, die für Nutzerinteraktion nötig wären.

Offen: was die Scope-Identität eines dauerhaften Grants jenseits des Sandbox-Modus ist — exakter Aufruf, Pfad, Kommando-Präfix, Session oder Zeitfenster — bevor eine `allow_always`-Option annonciert werden kann.

#### Modi pro Session: das Session-Log als Store

```
effective(session) = sessionProjections.stateOf(session, '<knob>') ?? the composition-config default
```

Der Default ist Kompositionskonfiguration (`cordis.yml`) — im Besitz des Betreibers, prozessweit. Ein Runtime-Wechsel ist ein session-scoped Override, der als ein einzelnes log-only Event im Log dieser Session aufgezeichnet wird; die Projection Unit des Stellwerts faltet es, und der Zustand jeder Unit wird checkpointed — Restart-Festigkeit und Multi-Session-Isolation folgen also aus dem dauerhaften Projection-Cache plus Log-Replay, ganz ohne externen Config-Store. Der prozessinterne Subagent-Treiber snapshotet den expliziten Override eines Parents bei der Delegation und setzt nach dem optionalen Fork-Präfix des Child ein quellenmarkiertes Event, sodass Delegation nicht auf einen weiteren Default zurückfallen kann ([Entscheidung](2026-07-25-subagent-policy-inheritance.de.md)).

**Ein Event pro Stellwert, im Besitz seiner Domäne** — die merge-erweiterbare `SessionEventMap`-Idiom, der jede bestehende Event-Familie bereits folgt (`approval/*` in `dsh-user-approval`, `hook/*` in den Hooks-Paketen):

```ts
interface SessionEventMap {
  'sandbox/mode': { mode: 'read-only' | 'workspace-write' | 'danger-full-access' }
  'approval/policy': { policy: 'ask' | 'never' }
}
```

Jeder Owner steuert dieselben Teile bei: die Event-Deklaration, eine auf der erforderlichen `ctx.sessionProjections`-Registry registrierte Projection Unit (`key` `sandboxMode` / `approvalPolicy`, `stateVersion` 1, ein zod-`stateSchema`, das persistierten Zustand validiert, `init` auf `null` und `apply` — der Fold, ein find-last-förmiger Übergang über sein Stellwert-Event, typisiert auf die geschlossene Union der Domäne) und DEN Schreibpfad (`setSandboxMode(session, mode)` / `setApprovalPolicy(session, policy)` — ein Wechsel IST sein Event; nichts mutiert Zustand out-of-band). Die Registry treibt jede Unit eifrig über committed Session-Events und checkpointed alle Zustände einheitlich — Host-only-Units eingeschlossen, kein `persist`-Opt-in — sodass Restart-Festigkeit und Multi-Session-Isolation auf dem dauerhaften Cache plus Log-Replay ruhen statt auf einem paketweisen Lesehelfer. Es ist geteilte Framework-Infrastruktur, keine Facts-Map mit Owner-Service: Jede Domäne behält ihr eigenes Event und ihre Unit, und ein dritter Stellwert schreibt Event, Unit und Setter im eigenen Paket und registriert die Unit — Drive, Checkpointing und Leseflache kommen von der Registry, es gibt keinen Fold-Export zum Kopieren. Host-Leser lesen den gefalteten Override über `stateOf(session, key)` (`SandboxPolicyService.overrideOf` und `ApprovalService.overrideOf` sind genau diese Reads), und Beitragende wie Leser benötigen beide `sessionProjections` ([der obligatorische Projection-Seam](../architecture/2026-08-19-session-projection-mandatory-seam.de.md)). Die Ausführung folgt auf beiden Seiten dem projizierten Zustand — der Stempel pro Aufruf des Bash-Tools liest ihn als mittlere Sprosse der §-Eskalations-Vorrangkette, und das `'never'`-Gate des Approval-Seams ist die Seite desselben Musters im [Approval Agent Note](2026-07-06-approval-seam.de.md).

Vor jedem vorgeschlagenen Schritt werden Sandbox- und Approval-Richtlinie als geordnete Beiträge zu einer gewünschten Policy-Kontext-Nachricht gerendert. Der Listener gleicht diese Nachricht gegen Session-Verlauf, den geclaimten Batch und seinen anstehenden `next-step`-Inbox-Eintrag ab. Einmal geclaimt und eingetreten, zeichnet der Loop die vollständige quellenbehaftete `user/message` auf; sowohl `'ask'` als auch `'never'` sind explizit, sodass kein Owner Wechselnarration oder Last-told-Zustand braucht.

**Die optionale UI-Oberfläche** ist `PermissionPresetService`: eine deployment-definierte Preset-Tabelle, deren Einträge je einen Sandbox-Modus mit einer Approval-Richtlinie bündeln. Die ausgelieferten Presets `workspace-write` und `danger-full-access` schreiben in beide Domänen-Setter durch; eine Stellwert-Kombination außerhalb der Tabelle wird als `custom` gemeldet. UI-Adapter können diese Tabelle als Selektor exponieren. Der rein automatisierungsorientierte ACP-Transport annonciert keinen Konfigurationsselektor und mountet keinen Permission-Preset-Service.

**Das committed Event ist die Commit-Grenze.** Ein Runtime-Wechsel zeichnet auf der Ziel-Session sein Preset und die geänderten Stellwert-Events auf, und jede spätere Capability-Auflösung faltet die letzten Werte. Die Wahl einer gültigen Session-Append-Grenze liegt bei den Adaptern; der ACP-Transport hat keinen Runtime-Switch-Pfad. (Die frühere ACP-Idle-Switch-Verankerung — eine anstehende Idle-Auswahl bis zur nächsten Prompt-Einreichung halten — ist mit jener Bridge verschwunden.)

#### Prozessinterne Tools

fs/web/todo laufen prozessintern, ihre Sandbox-Semantik ist also Richtlinie an ihren Capability-Grenzen. Der fs-Seam setzt das geteilte Modus-Vokabular jetzt über einen gesandboxten Provider durch (`dsh-fs-sandbox` begrenzt write/edit nach Modus; siehe [das Cross-Family-fs-Sandbox-RFC](2026-07-14-cross-family-fs-sandbox.de.md)) — `read-only`/`workspace-write` sind damit echte Grenzen für die Dateisystem-Tools, keine Bash-only-Approximation. web/todo bleiben unbegrenzt (webs einziger Effekt ist Netzwerk, außerhalb des Datei-Effekt-Modus-Vokabulars). Es gibt keine generische Per-Tool-Sandbox-Runtime: Ein host-vermitteltes Tool verlässt den Prozess nur, indem es deklarative Effekte zurückgibt, die der Host validiert — ein Rewrite, kein Wrapper; die Folgeentscheidung wählte ein geteiltes Richtlinien-Zuhause (`ctx.sandboxPolicy`) mit Durchsetzung pro Capability statt eines einheitlichen Wrappers.

### Testing

- **Unit:** fixiert Plattformauswahl und Profile, direkte Provider-argv-Übergabe, Spawn-Ebenen-Fehler mit Invalid-Workdir-Kontrollen, Missing-/Non-executable-/Missing-Interpreter-Evidenz, Malformed-Runner-Negativkontrollen, eingeschränkte `BASH_ENV`-Reihenfolge, strukturierte Runner-Klassifikation (einschließlich Partial-Landlock-Notice-only-Child-Ergebnissen, gegater fataler Evidenz, Child-Exits 126/127 und Foreground/Background-Parität), Mode-/Root-Auflösung pro Aufruf, Fakten pro Prozess, Eskalationsvalidierung und -Ergebnisse, Permission-Preset-Folding und Write-through sowie Runtime-Context-Ordnung und -Materialisierung.
- **Schlüssellose Real-Runner:** übt bwrap, Landlock und Seatbelt gegen reale Dateisystemeffekte auf Provider- und Bash-Consumer-Ebene; ein realer Cordis-Kontext treibt zwei Projekt-Sessions gleichzeitig über die ausgelieferten Bash- und fs-Tools und beweist Erfolg im eigenen Root sowie Verweigerung im Geschwister-Root. Packed-Install-Coverage installiert die nativen Tarballs des aktuellen Checkouts und beweist, dass der Launcher ausführbar und byte-identisch bleibt. CI lehnt ein stilles Komplett-Skip ab.
- **With-Key:** startet die reale ACP-Komposition im read-only-Modus, lässt einen modellgetriebenen Bash-Write auf die Verweigerungsmarkierung des Runners treffen und treibt dann Bridge-Answerer und Festplatten-Effekt über gewährte und abgelehnte workspace-write-Retries; nicht verfügbare Credentials oder Runner skippen selbst.
- **Snapshot:** fixiert den atomaren Current-Policy-Kontext und beide skriptgesteuerten Approval-Zweige. Ein reales ACP-Beispielszenario platziert seine Session unter dem User-Home, während der Deployment-Fallback auf `/tmp` zeigt, und fixiert dann sowohl die workspace-write-Runtime-Context-Nachricht als auch eine erfolgreiche deployment-gewählte Mutation; das unterscheidet Session-Root-Auflösung vom Prozess-Fallback, ohne runner-spezifischen Verweigerungstext zu benötigen. Ein POSIX-Fake-Partial-Landlock-Provider fixiert, dass direktes bash `false` in der assemblierten App ein gewöhnliches Child-Ergebnis bleibt und eine fehlende Provider-Executable in Foreground wie Background ein Infrastrukturfehler ist. Andere Snapshots starten uneingeschränkt, damit unverbundene Fixtures plattformunabhängig bleiben.

## Zurückgestellte Phasen

Jede Phase bekommt ihr vollständiges Design, wenn sie angegangen wird, validiert gegen den dann aktuellen Code, und landet mit Unit-, Real-API-e2e- und Snapshot-Coverage auf den Ebenen, die sie berührt.

- **Zweiter Consumer** — `subagent-acp` schränkt Child Agents optional ein (Policy pro Aufruf; Default uneingeschränkt — ein Child Agent muss seine eigene Persistenz schreiben).
- **Weitere Umgebungen** — ein Beispiel einer umgebungskohärenten Capability-Gruppe (z. B. bash+fs gegen einen Container).

## Betrachtete Alternativen

- **Heuristisches Kommando-String-Preflight** — abgelehnt: kann Expansion/Subprozesse/Symlinks nicht verstehen; der strikte Versuch (ausführen, den Kernel entscheiden lassen) ist das einzig verlässliche Verweigerungssignal.
- **Funktionales Probing auch beim einzigen Backend einer Plattform** — abgelehnt: Probing arbitriert zwischen Kandidaten; bei einem gibt es nichts zu entscheiden, und die Probe-Kosten belasten das erste eingeschränkte Kommando jeder Session (prohibitiv für schwere künftige Backends). Die exec-zeitige fail-closed-Weigerung des Runners selbst plus strukturierte `runnerFailureRules`-Klassifikation trägt stattdessen die Sicherheitseigenschaft.
- **Gebaute Launcher-Binaries committen** — abgelehnt: ein Binary im Diff ist nicht reviewbar und bläht die Historie; reviewter Source + native CI-Builds + die byte-gepinnte Publish-Probe des Haupt-Repo halten Bytes aus jedem Tree.
- **Launcher bei der Installation kompilieren** — abgelehnt: drückt jedem Consumer eine C-Toolchain auf; ein Fallback, das nur existiert, wo zufällig ein Compiler liegt, ist kein Fallback.
- **Beide Architekturen von einem Builder cross-kompilieren** — abgelehnt: erfordert eine gepinnte Cross-Toolchain (rustup-Targets, zig oder ein Container-Image), nur um zwei ~70-KB-Binaries neu zu bauen; Architektur-eigene native Runner existieren bereits und bauen jeweils ihr eigenes Plattformpaket (das `node-addon-require-builtin`-Modell, von der nativen Pipeline des Haupt-Repo beibehalten).
- **Kein Fallback (bwrap oder fail closed)** — abgelehnt: konzentriert den Fehler genau auf den Hosts, auf denen eine Sandbox am wichtigsten ist, und degradiert per Resignation auf `danger-full-access`.
- **Mechanismus in `dsh-bash-sandbox` belassen** — abgelehnt: blockiert den bestehenden zweiten Consumer, ließe künftige Phasen den Modus aus der Config eines Bash-Plugins lesen und kann Eskalation nicht ausdrücken.
- **Konfigfixierter Modus am Provider** — abgelehnt: ein Modus pro Prozess; kann weder gleichzeitige Consumer mit unterschiedlichen Richtlinien bedienen noch den einmalig erweiterten Retry.
- **Ein Interface, das auch Container/VMs umspannt** — abgelehnt: `confine(argv)` setzt ein geteiltes Dateisystem voraus; Umgebungsisolation sind Capability-sibling-Backends, die als kohärente Gruppen deployt werden.
- **Generisches ToolRuntime-Wrapping beliebiger Tools** — abgelehnt: für prozessinterne Tools mechanisch falsch (Closures über `ctx`); das Declarative-Effects-Rewrite ist für fs/web/todo nicht gerechtfertigt.
- **Im Executor fragen (`dsh-bash-sandbox`)** — abgelehnt: kein `agent` zum Durchrouten, kein `callId` zum Anhängen des Prompts; sie hinzuzufügen würde einer Transport-Grenze Sessions und UIs beibringen — die Tool-Schicht hält beides und besitzt das modellseitige Vokabular.
- **Auto-Retry innerhalb desselben Tool Calls** — abgelehnt: ein versteckter Wiedereintritt, den das Log nicht rekonstruieren kann: ein `tool/call` hätte zwei Ausführungen mit unterschiedlichen Richtlinien erzeugt — der Retry ist ein NEUER geloggter Aufruf mit eigenen Argument- und Ergebnisfakten.
- **Eskalationsfelder unbedingt annoncieren** — abgelehnt: unter `dsh-bash-local` sind sie ein toter Hebel — eine Option anzubieten, die der Harness nicht einlösen kann, erzeugt zum Scheitern verurteilte Grants; Capability-Gating kostet einen einzigen Read bei der Registrierung.
- **Eine default-relative Eskalationsleiter (nur Modi annoncieren, die weiter sind als der Default zur Registrierungszeit des Executors)** — abgelehnt: Session-Overrides machen den Default zur falschen Basislinie — eine Session, die enger als der Default geschaltet ist, verliert genau den Hebel, den sie braucht, und unter einem `danger-full-access`-Default verschwinden die Felder ganz, während eine auf `read-only` übersteuerte Session eingeschränkt bleibt ohne Eskalationspfad. Das Enum fixiert das geschlossene Zielvokabular; strikte Erweiterung ist eine Execution-Check pro Aufruf gegen den effektiven Modus der Session.
- **Session-eigene dynamische Tool-Schemas** — abgelehnt: Schemas sind per Design registry-global (ein Assembly-Vokabular, der Pinned-Header-Snapshot-Vertrag), und eine Neu-Registrierung pro Session würde nur kaufen, was der Strict-wider-Check zur Ausführungszeit bereits garantiert — zum Preis eines Session-Schemas und Header-Churn bei jedem Wechsel.
- **Den Retry hart an eine frühere Verweigerung koppeln** — abgelehnt: Kommando-String-Identität ist fragil (Quoting, `workdir`, env-Präfixe, eine Pipeline, die als ihre scheiternde Stufe retried wird) — weist entweder ehrliche Retries fälschlich ab oder ist trivial erfüllt; die echte Grenze ist der Mensch, der Kommando + Begründung sieht. Nur erneut prüfen, falls `allow_always`-Grant-Speicher je maschinell prüfbare Scopes braucht.
- **Generische `env/state`-Facts-Map mit Owner-Service** — abgelehnt: Approval und Sandbox komponieren unabhängig, der Zustand keiner Seite darf also ein drittes Paket hineinziehen; Single-Key-Folds sind je ein `findLast`, der Owner-Service löst sich auf; keine Invariante überspannt die Stellwerte, also brachten atomare Multi-Key-Patches nichts.
- **Jeden Wechsel über `agent.inject()` plus Bus-Event narrativieren** — abgelehnt: unabhängige Notices legen Owner-Reihenfolge und Zwischenkombinationen offen, während eine Pre-Step-Komposition den vollständigen aktuellen Zustand atomar einreihen kann.
- **Sandbox-Modus im stabilen System Prompt nennen** — zuerst ausgeliefert, dann auf Live-Evidenz entfernt: mit `Bash commands run under the "read-only" file sandbox.` in jedem Request weigerte sich das Modell, verweigerbare-then-eskalierbare Arbeit überhaupt zu VERSUCHEN (fünf von zwölf Turns der ersten manuellen Session endeten mit null Tool Calls) und machte die Sandbox zum Soft-Lockout. Die Verweigerungsmarkierung nennt den Modus im relevanten Moment, die Eskalationsfelder tragen den Recovery-Pfad. Die Weglass-Entscheidung ist durch [die Current-Policy-Entscheidung](../../archived/feature/2026-07-30-current-sandbox-policy-context.md) ersetzt; diese Messung und Kausalbeobachtung bleiben die Evidenz, die jede Alternative gegentesten muss.
- **„Last told" mit eigenen Buchungs-Events tracken** — abgelehnt: der Session-Verlauf zeichnet den exakten Policy-Kontext auf, den das Modell gesehen hat, während geclaimter Batch und anstehender Inbox-Eintrag zeigen, was eintritt oder gequeued ist. Das Neuberechnen der Zielnachricht ersetzt einen zweiten Buchungsstrom — Events werden nur dort gebraucht, wo sie der Store SIND.
- **Unabhängige Sandbox- und Approval-Selektoren** — abgelehnt: ein deployment-definiertes Permission-Preset hält die beiden Richtlinien-Stellwerte für UI-Clients kohärent, die Runtime-Wechsel exponieren.

## Konsequenzen

Was ausgeliefert wurde, fixiert — die Ebenen unter Testing halten jedes einzelne:

- Ein verweigertes Kommando, das mit `sandbox_permissions` + `justification` retried wird, fragt den Nutzer über die komponierte Answerer-Kette; ein Grant lässt JENEN Aufruf im weiteren Modus laufen (Ergebnisfakten sagen das so), während jeder andere Aufruf seinen eigenen effektiven Modus behält; jedes Nicht-Grant-Ergebnis erzeugt seinen eigenen Fehlertext und führt nichts aus.
- Die Eskalationsfelder existieren genau dann, wenn der gemountete Executor einschränkt; ein Request, der nicht strikt weiter ist als der effektive Modus des Aufrufs, schlägt mit eigenem Text geschlossen fehl und fragt niemanden; ein Deployment ohne ApprovalService lässt eskalierende Aufrufe geschlossen fehlschlagen und lässt einfache Aufrufe unberührt.
- Eine quellenbehaftete Policy-Kontext-Nachricht nennt atomar die vollständigen aktuellen Sandbox- und Approval-Richtlinien; der gesamte Austausch — Kontextnachrichten, Header, Stellwert-Events, Approval-Notices, Freigaben und Ergebnisse — lässt sich allein aus dem Session-Log rekonstruieren, ohne weitere Policy-Buchungs-Events über die zwei Stellwert-Events hinaus.
- Eine Preset-Auswahl zeichnet nur geänderte Stellwerte auf, eine No-op-Auswahl nichts; der nächste Pre-Step upsertet beide aktuellen Werte atomar, und ein committed Sandbox-Wechsel wird vom Stempel des nächsten Aufrufs eingelöst.
- Die Overrides einer wiederaufgenommenen Session treten ohne Catch-up-Zustand in ihre erste neue Policy-Kontext-Nachricht ein; ein bei gestopptem Prozess geänderter Kompositions-Default erscheint ebenfalls in dieser Nachricht.
- Zwei gleichzeitige Sessions sehen nie den Zustand oder die Notices der anderen.
- Zwei gleichzeitige Projekt-Sessions in einem Cordis-Kontext lösen unabhängige Workspace-Roots auf; Bash- und fs-Writes gelingen innerhalb des cwd der aufrufenden Session und scheitern gegen das cwd der Nachbar-Session.
- Richtlinien-Ownership bleibt in Plugins — durch `SessionEventMap`-Merging, die auf der erforderlichen `ctx.sessionProjections`-Registry registrierten Projection Units, Inbox-Mutation aus `agent/pre-step` und capability-eigene Auflösung; der generische Loop claimt und protokolliert nur den final eingetretenen Batch.

Kosten und akzeptierte Grenzen:

- **Die Ein-Wrapper-Illusion wird wissentlich aufgegeben.** Ein `tools/pre-execute`-Wrapper plus Prompt-Konventionen löst Sandbox-Freigabe nicht — das korrekte Design kostet strukturierte Verweigerungen, native Runner-Probes, Policy-Mitführung pro Aufruf und konsistente familienübergreifende Durchsetzung, und dieses Design zahlt das.
- **`read-only` wurde durch Folgearbeit zur familienübergreifenden Grenze.** Dieses RFC lieferte zunächst nur Bash-Durchsetzung; das [Cross-Family-fs-Sandbox-RFC](2026-07-14-cross-family-fs-sandbox.de.md) erweitert dasselbe Modus-Vokabular über einen gesandboxten `ctx.fs`-Provider auf die Dateisystem-Tools und verlagert Mode-/Root-Config sowie den `sandbox/mode`-Override nach `ctx.sandboxPolicy` (§ Prozessinterne Tools).
- **Windows ist ein Partial-Backend.** Dieses RFC reservierte ursprünglich eine leere, fail-closed win32-Kette; die spätere [Windows-ACL-Sandbox-Entscheidung](2026-08-08-windows-acl-restricted-token-sandbox.de.md) füllte sie mit dem Restricted-Token-Runner. Seine Everyone- und Hardlink-Lücken werden als `enforcement: 'partial'` gemeldet, nie zum vollen Versprechen hochgestuft.
- **Die Seatbelt-Stufe stützt sich auf Apples deprecated-aber-ausgeliefertes `sandbox-exec`-CLI.** Als einziger darwin-Kandidat wird es ohne Probe gewählt, sodass eine künftige Entfernung bei nutzbarem workdir als runner-zurechenbarer Spawn-Fehler und eine Executable-Verweigerung über seine fatale Signatur auftaucht — beides wird `SANDBOX_UNAVAILABLE`, und das Kommando läuft nie; fail closed, niemals offen.
- **Landlock-Einschränkung ist nur so vollständig wie die ABI des laufenden Kernels.** Gemeldet als `enforcement: 'partial'` statt verweigert — der bewusste Deal, der den Fallback auf Hosts mit älterem Kernel verfügbar hält.
- **Runner-Attribution nutzt ein In-band-Protokoll.** Exit-Status plus stderr können den Schreiber nicht kryptografisch identifizieren, ein eingeschränktes Child kann also eine fatale Runner-Zeile und den Status imitieren und eine Availability-/Diagnose-Fehlattribution verursachen. Die Konjunktion und der exakte Notice-Ausschluss reduzieren versehentliche Matches; das ist kein Sandbox-Bypass, weil das Child bereits eingeschränkt ist.
- **Der Launcher ist im Source eine Workspace-Dependency und nach Veröffentlichung eine npm-Dependency.** Das Haupt-Repo testet reviewten C-Source, native CI-Builds und byte-gepinnte lokale Tarballs gemeinsam, bevor es dieselbe Paketfamilie veröffentlicht; die Real-Kernel-e2e-Legs bürgen für das Verhalten dieser installierten Bytes.
- **Das Modell kann überfragen.** Eskalieren ohne Verweigerungsgrundlage oder `danger-full-access` wählen, wo `workspace-write` genügt: die Beschreibung steuert und das Enum erzwingt die Leiter, aber der menschliche Prompt ist das eigentliche Gate; die `approval/asked`-Gründe machen Überfragen auditierbar, und ein `prepend`-Policy-Answerer kann Muster auto-ablehnen, die ein Deployment nie will.
- **Die annoncierte Zielmenge ist statisch, während der effektive Modus pro Session gilt** (Schemas sind registry-global) — einer Session auf dem weitesten Modus werden die Felder trotzdem angeboten. Konstruktionsbedingt harmlos: der Strict-wider-Check bei der Ausführung, nicht das Enum, ist die Sicherheitsgrenze — ein nicht-erweiternder Request scheitert mit eigenem Text und fragt niemanden.
- **Ein erteilter Eskalations-Grant ist keine funktionierende Sandbox.** Ein nicht verfügbares Backend schlägt selbst für einen erteilten Grant in einen einschränkenden Modus weiterhin geschlossen fehl — bei `confine()`, wenn die Plattform keine Kette hat oder jede Probe scheitert, über den Spawn-Kanal, wenn die gewählte Executable nicht startet, oder über eine strukturierte Regel, wenn ein gestarteter Runner verweigert — während ein erteilter `danger-full-access`-Lauf den Provider gar nicht berührt: dort ist der Grant, nicht die Probe, die Autorität.
- **Runtime-Context-Historie ist append-only.** Ein Richtlinienwechsel hängt einen vollständigen, ersetzenden Snapshot hinter die behaltene Historie und bewahrt das stabile System-und-Konversations-Präfix; unveränderter Zustand fügt keine Nachricht hinzu.
- **Ältere Richtlinien-Snapshots bleiben in der Historie.** Jeder volle Snapshot ersetzt ausdrücklich frühere Runtime-Context-Snapshots, Replay und Compaction müssen also nur die jüngste materialisierte Nachricht behalten.

## FAQ

- **Ein Kommando kam mit `[sandbox: file access denied under read-only mode]` zurück — ist es fehlgeschlagen?** Es LIEF, und der Kernel verweigerte einen Dateieffekt: die Verweigerung ist eine Ergebnisfakt orthogonal zum Exit-Code. Die Belehrung verbietet, um sie herum zu retryen; der einzige sanktionierte Zug ist dasselbe Kommando, einmal retried mit Eskalationsrequest.
- **Wie unterscheidet man eine KAPUTTE Sandbox von einem scheiternden Kommando?** Eine asynchrone Subprocess-Provider-Abweisung legt keine öffentliche Ausführungsphase offen. Sie identifiziert einen kaputten Einschränkungs-Runner nur, wenn das aufrufereigene workdir nutzbar ist und Node zurechenbaren `ENOENT` oder `EACCES` für dieses argv[0] meldet; ein nacktes `syscall: 'spawn'` ohne exakten Fehlerpfad und alle anderen Abweisungen bleiben phasenneutrale Provider-Failures. Sobald ein direktes Ergebnis vorliegt, schlägt Runner-Fehler Verweigerung nur, wenn ein `runnerFailureRules`-Eintrag sowohl sein optionales Exit-Code-Gate als auch eine fatale stderr-Zeile nach exakten Ausschlüssen informativer Zeilen matcht. Foreground-Runner-Fehler werfen strukturiertes `SANDBOX_UNAVAILABLE` mit Executable- oder Match-Zeilen-Detail; eine zurechenbare asynchrone Background-Abweisung oder ein gematchter abgerechneter Fehler stempelt `sandbox.runnerFailed`, während jede asynchrone Abweisung die Provider-Failure-Notiz des lokalen Executors rendert. Eine `SubprocessRuntime`, die synchron dieselbe `ENOENT`/`EACCES`-Form mit Runner-Pfad wirft, lässt den Background-Start den strukturierten Fehler werfen; andere synchrone Fehler propagieren unverändert. Eine Landlock-Partial-Enforcement-Notice plus ein gewöhnlicher Child-Fehler bleibt ein Kommandoergebnis.
- **Was passiert auf einer Plattform ohne Backend?** `confine()` wirft den fail-closed `SANDBOX_UNAVAILABLE`, und das Kommando wird nie gespawnt.
- **`bwrap` ist auf meinem Host installiert, aber unbrauchbar (deaktivierte unprivilegierte userns, ein LSM, der `mount` verweigert) — was passiert?** Die Ketten-Probe ist funktional — sie baut und erzwingt ein reales Profil statt `--version` zu prüfen — ein vorhandenes, aber unbrauchbares `bwrap` fällt also durch seine Probe, die Auswahl fällt auf den paketierten Landlock-Launcher, und das Urteil wird für die Lebensdauer des Providers gecacht.
- **Beschränkt die Sandbox Netzwerk oder Prozess-Sichtbarkeit?** `SandboxMode` beansprucht nur DATEI-Effekte, und kein Backend beansprucht Netzwerk. Prozess-Sichtbarkeit ist backend-spezifisch: bwrap unshared PID und mountet passendes procfs, weil Host-`/proc/<pid>`-Magic-Links sonst die Dateieinschränkung umgehen, während Landlock und Seatbelt die Prozess-Sichtbarkeit unverändert lassen ([Entscheidung](../bug-fix/2026-08-06-bwrap-private-pid-namespace.de.md)). Ob Netzwerkrestriktion ein eigener Stellwert wird, bleibt in § Der Seam offen.
- **Welche Tools laufen tatsächlich eingeschränkt?** OS-Subprozesse über `ctx.shell` — die Bash-Tools und transitiv die Hook-Kommandos — plus die Dateisystem-Tools (`read`/`write`/`edit`) über den gesandboxten `ctx.fs`-Provider (das [Cross-Family-fs-Sandbox-RFC](2026-07-14-cross-family-fs-sandbox.de.md)): bash beschränkt über den OS-Runner, fs über einen prozessinternen Pfad-Zaun, beide keyed auf denselben `ctx.sandboxPolicy`-Modus. web/todo bleiben prozessintern und unbegrenzt (webs einziger Effekt ist Netzwerk, außerhalb des Datei-Effekt-Modus-Vokabulars).
- **Persistiert ein erteilter Eskalations-Grant?** Nein. Der Grant wird vom exakten Foreground- oder Background-Aufruf konsumiert, der gefragt hat; jeder benachbarte Aufruf behält seinen eigenen effektiven Modus. Eine spätere Background-Verweigerung taucht über `job_output` auf und kann einen neuen Exact-Command-Retry begründen.
- **Wann wird ein Runtime-Modus-Wechsel wirksam?** Sobald sein Session-Event committet, falten die nächste Pre-Step-Policy-Kontext-Abgleichung und die nächste Capability-Auflösung den neuen Modus. Die quellenbehaftete Kontextnachricht zeichnet auf, was dem Modell gesagt wurde, und jede spätere Verweigerung nennt dieselbe Richtlinie am Einsatzpunkt.
- **Was überlebt einen Restart — und was, wenn der Betreiber den Config-Default bei gestopptem Prozess geändert hat?** Overrides stellen aus dem dauerhaften Projection-Cache wieder her und falten über dem Session-Log neu (`effective = projizierter Override ?? config`), eine wiederaufgenommene Session behält ihre Modi also ohne jede Catch-up-Maschinerie; ein offline gedrifteter Default tritt in die nächste vollständige Policy-Kontext-Nachricht ein.
- **Was bedeutet `enforcement: 'partial'` auf einem Ergebnis?** Das gewählte Backend setzt die Teilmenge durch, die seine Kernel-ABI beherrscht — z. B. Landlock vor ABI v3 beherrscht Path-Truncate nicht — und sagt das strukturell, statt den Host abzulehnen; die Report-Zeile der Probe unterscheidet die Fälle. Die bwrap- und Seatbelt-Profile beherrschen konstruktionsbedingt jeden versprochenen Dateieffekt und melden daher stets `full`.
