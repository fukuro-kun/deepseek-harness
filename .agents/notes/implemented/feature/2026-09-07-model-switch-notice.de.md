# Agent Note: Modell-sichtbare Routenwechsel-Hinweise

Status: implemented

[English](2026-09-07-model-switch-notice.md) | [中文](2026-09-07-model-switch-notice.zh.md) | Deutsch

## Problem

Die Session-Historie kennzeichnet Nachrichtenrollen, sagt einem neu gewählten Modell aber nicht, welche Route frühere Assistant-Turns erzeugt hat. In der anlassgebenden Session wechselte der Nutzer von `deepseek-v4-flash` zu `deepseek-v4-flash-vision-exp`. Das neue Modell sah Bild-Platzhalter, die aussagten, ein reines Textmodell habe die Bilder weggelassen, und folgerte, die Einschränkung beschreibe seine eigene Bildfähigkeit.

## Entscheidung

`installModelSelection` vergleicht die bei der Prompt-Montage erfasste Provider-/Modellauswahl mit dem jüngsten dauerhaften Request-Header. Bei Abweichung hängt es `[model changed: assistant turns above this point were generated by <previous>; the session continues with <next>]` als identifizierte User-Rollen-Nachricht an eine nachgelagerte `agent/pre-step`-Entscheidung an, die sonst einen Model-Request senden würde.

Routen desselben Providers verwenden Modell-IDs; providerübergreifende Routen verwenden `provider/model`. Erstauswahl, unveränderte Routen, Änderungen nur der Reasoning-Effort, abgelehnte Steps und abgebrochene Steps fügen keinen Hinweis hinzu. Eine leere Erstentscheidung und eine Entscheidung, die angebotene Nachrichten entfernt, bleiben No-Request-Ergebnisse. Eine leere Fortsetzung nach einem Tool-Aufruf erhält den Hinweis, weil der Loop das Modell aus gehaltener Historie trotzdem anfragen würde. Eine während der Pre-Step-Verarbeitung geänderte Auswahl wartet auf die nächste Prompt-Montage.

Die akzeptierte Nachricht wird vor dem Request-Header über das bestehende `user/message`-Event protokolliert und erscheint damit in Model-Input, Chat und Trajectory. Der Request-Header bleibt der dauerhafte Beleg, dass die neue Route verwendet wurde. Scheitert ein Step vor dem Protokollieren dieses Headers, wiederholt der nächste Request-Step den Hinweis, weil die dauerhafte vorherige Route unverändert bleibt.

## Erwogene Alternativen

**Den Hinweis in den System-Prompt legen.** Eine transiente Prompt-Änderung wäre aus dem Session-Log nicht rekonstruierbar und würde die genaue Stelle nicht markieren, an der die Zuständigkeit für Assistant-Turns wechselte.

**Ein eigenes Paket oder eine eigene Capability schaffen.** Das Verhalten koordiniert nur Prompt-Snapshot und Request-Route, die `installModelSelection` bereits besitzt; es hat keine eigenen Service-, Provider- oder Consumer-Rollen.

**Den Wechsel nur im Client zeigen.** Eine rein clientseitige Darstellung ließe das neu gewählte Modell ohne die Tatsache, die es zur Deutung früherer Assistant-Turns braucht.

## Folgen

Jeder ausgegebene Routenwechsel-Hinweis wird gehaltene User-Rollen-Historie und verbraucht Kontext-Tokens bei späteren Requests. Ein Fehlschlag vor der Request-Header-Persistenz kann mehr als einen identischen Hinweis halten. Bestehende Session-Events stellen das Verhalten dar, sodass sich das Session-Format nicht ändert.
