# Agent Note: PTC mode — das Modell schreibt TypeScript gegen die Tool-Registry

Status: implemented

[English](2026-06-15-ptc.md) | [中文](2026-06-15-ptc.zh.md) | Deutsch

## Problem

In der nativen Darstellung der Registry kündigt der agent loop jede sichtbare capability als JSON-Schema-Funktionsdefinition an. `ToolRuntime` steuert seine Schemas zur System-Prompt-Assembly bei, die `tools` der Assembly landen auf dem wire format (und im geloggten Request-Header), das Modell ruft pro Schritt einen `tool-call`-Block auf, und zum Zeitpunkt dieser Note dispatchte der Loop jeden Aufruf über `ctx.tools.execute()` **sequenziell** (parallele Tool-Ausführung war damals ein offener TODO; begrenztes paralleles Dispatch ist inzwischen ausgeliefert — die [Note zum parallelen Tool-Aufruf](2026-07-10-parallel-tool-call-execution.md), der Rolling Pool in [docs/architecture.md](../../../../docs/architecture.de.md)) — wobei **jedes** Zwischen-`tool-result` mit der nächsten Anfrage wieder in den Modellkontext eintrat.

Für mehrstufige Tool-Arbeit ist das token-teuer und seriell. Das Modell kann Tools nicht komponieren — über eine Ergebnismenge iterieren, auf einen Zwischenwert verzweigen, auffächern, nachbearbeiten — ohne einen vollständigen Modell-Roundtrip pro Aufruf, und jeder Roundtrip zieht das gesamte Zwischenergebnis zurück in den Kontext, ob das Modell es braucht oder nicht.

Cloudflares [Code Mode](https://blog.cloudflare.com/code-mode/) schlägt eine Alternative vor, die auf einer einfachen Beobachtung beruht: LLMs schreiben besser Code, als sie Tool Calls auszugeben, weil sie Millionen Zeilen echten Codes gesehen haben, aber vergleichsweise wenige künstliche Tool-Calling-Traces. Statt eines Tool Calls pro Schritt schreibt das Modell ein TypeScript-Programm gegen eine generierte API über den Tools, das Programm läuft in einer sandboxed Runtime, und das Modell kuratiert, was zurückkommt — nur was es ausgibt oder zurückgibt — statt jedes Zwischenergebnisses.

Tool-Präsentation gehört der Registry, die die Tool-Sichtbarkeit besitzt: Eine zweite Präsentation als nachträgliche waterfall-Transformation zu implementieren würde die Korrektheit von der Listener-Reihenfolge abhängig machen und [rekonstruierbare Requests](../architecture/2026-07-05-reconstructable-requests.md) bekämpfen. Das Ausführungssubstrat ist ebenfalls Teil des Fundaments, kein Platzhalter: Node `worker_threads` bietet einen separaten Isolate, eine leere Umgebung, Heap-Limits und die Terminierung einer heißen synchronen Schleife, und passt dabei ins bestehende Trust-Modell des harness (§Trust-Haltung).

## Entscheidung

Drei Entscheidungen, jede in einem eigenen Abschnitt unten ausgeführt:

1. **PTC mode ist ein First-Class-Präsentationsmodus von `ToolRuntime`** (`dsh-tools`), ausgewählt über eine validierte `mode`-Config: `'native'` (der Default, liefert die Schemas sichtbarer capabilities), `'ptc'` (die Registry liefert nur ihren reservierten `run_code`-Transport plus ein generiertes SDK `.d.ts` im System Prompt) oder `'both'` (native Schemas plus Transport + SDK). Die Registry konstruiert ihren kanonischen Beitrag an der Quelle; das kooperative Prompt-Assembly-Ergebnis bleibt maßgeblich, und der geloggte Request-Header zeichnet genau diese zurückgegebene Präsentation auf.
2. **Code-Ausführung ist ein capability seam** — `packages/code-runtime/` enthält das Service-Definition-Paket `@deepseek-ai/dsh-code-runtime`, das `ctx.codeRuntime` besitzt ([capability seams](../architecture/2026-06-13-capability-seams.md); Consumer = `dsh-tools`, mit dem Präzedenzfall Core-konsumiert-einen-seam bei `agent-loop` → `dsh-llm`). Die Runtime weiß nichts über Tools: Sie erhält ein Programm und benannte asynchrone Bindings, führt das Programm aus und meldet `{ value, logs, error? }`. Sprache und Substrat sind Backend-Eigenschaften, sodass ein künftiges Python- oder Container-Backend ein weiteres Service-Provider-Paket ist, kein Redesign.
3. **Die ausgelieferte Implementierung ist `@deepseek-ai/dsh-code-runtime-worker-thread`**: ein frischer Node-Worker-Thread pro Lauf, der das TypeScript des Modells nach dem Type-Strip ausführt, mit Bindings über den Message Port gebrückt, leerer Umgebung, konfigurierbaren Heap-/Output-/Zeit-Limits und harter Terminierung. Seine Trust-Haltung ist per Design bash-äquivalent — keine Unsafe-Acknowledgement-Flags — weil der harness bereits `dsh-bash-local` ausliefert, der beliebige modellgeschriebene Shell-Befehle mit strikt *mehr* Umgebungsautorität ausführt.

Diese Note besitzt die Präsentations-, Kompositions-, Isolations- und Settlement-Grundlage von PTC mode. Die spätere [Agent Note zu typisierten Tool-Rückgaben](2026-07-20-ptc-typed-tool-returns.md) besitzt die generierte Output-Map, kanonische Binding-Werte, `ToolCallError` und die verlustfreie Outer-Output-Grenze.

### Die Registry besitzt den Modus

`ToolRuntime` erhält eine schemastery-validierte Config (`static Config`), seine erste: `mode: 'native' | 'ptc' | 'both'`, Default `'native'`. Ein Deployment schaltet ihn über `cordis.yml` um (`tools: { mode: ptc }`) — ohne Code-Edit, gemäß der No-Hardcoded-Tunables-Konvention.

**Tool-Liste auf der Leitung.** Die Registry liefert sichtbare capabilities unter `'native'`, nur `run_code` unter `'ptc'` und beides unter `'both'`. Die finale `PromptAssembly.tools`-Liste wird im Request-Header geloggt. `run_code` ist ein reservierter Präsentationstransport außerhalb der Registrierungs- und Restriktionsschichten; direkte Prompt-Provider und die Assembly-waterfall bleiben für ihre eigenen Beiträge verantwortlich.

**Zusammenspiel mit `toolOrder`:** Eine konfigurierte `systemPrompt.toolOrder`, die native capabilities nennt, weist jede Assembly unter `mode: 'ptc'` zurück, weil diese Namen außerhalb des Wire-Validierungs-Universums dieses Modus liegen. Das ist korrektes Verhalten, kein Bug: Ein Deployment, das PTC mode nutzt, aktualisiert seine Order-Config oder entfernt sie.

**SDK-Prompt-Sektion.** Unter `'ptc'` und `'both'` rendert die lazy `tools:sdk`-Sektion im Tool-Guidance-Order-Band die Sprachdeklarationen der geladenen Runtime plus feste Nutzungshinweise für die sichtbaren capabilities des Scopes (standardmäßig TypeScript; die [Language-Dispatch-Note](../../archived/feature/2026-07-31-ptc-language-dispatch.md) fügte Python und die Renderer-Tabelle nach `ctx.codeRuntime.language` hinzu). Sie teilt Lookup- und Execution-Sichtbarkeit, schließt `run_code` aus und sortiert Tools lexikografisch für byte-stabile Ausgabe.

**Assembly-Eigentümerschaft.** `run_code` und `tools:sdk` treten als normale Assembly-Eingaben in die vertrauenswürdige `system-prompt/assemble`-waterfall ein. Eine gescopte `tools:sdk`-Sektion kann den globalen Default vor dem Dispatch überschatten, und ein Listener kann jeden der Beiträge entfernen oder ersetzen. Die von der waterfall zurückgegebene Assembly ist final; wer diese Eingaben ändert, trägt daher die Verantwortung, ein tragfähiges PTC-mode-Protokoll zu erhalten, wenn das Deployment PTC mode nutzbar erwartet; kein Wiederherstellungs-Pass überschreibt bewusste Komposition.

**Codegen.** `jsonSchemaToTs()` bildet die `defineTool`-JSON-Schema-Teilmenge auf TypeScript ab, überträgt Schema-Beschreibungen in JSDoc und degradiert nicht unterstützte Konstrukte zu `unknown`. Das SDK exponiert Tools als quotierte Objektschlüssel, unterstützt beliebige Namen ohne Aliase oder Kollisionen. Die Typisierung ist empfehlend, weil die Runtime Typen vor der Ausführung abstreift.

### Das run_code-Tool und die Dispatch-Bridge

Unter `'ptc'` und `'both'` besitzt die Registry `run_code` als reservierten Präsentationstransport mit zwei Pflichtparametern `{ code: string; description: string }` (die description beschriftet den Aufruf in UIs, der bash-Präzedenzfall). Sie wird durch eine normale `ToolDefinition` für den Dispatch repräsentiert, bleibt aber außerhalb der filterbaren Capability-Schichten, sodass Restriktionen den einzigen Einstiegspunkt von PTC mode nicht versehentlich entfernen können. Aufrufe durchlaufen die komplette Tool-Pipeline — `tools/pre-execute` → monotone Guards → `tools/execute` um den Dispatch → `tools/post-execute` → optionales definitions-eigenes `finalizeContent` → unveränderliche `tools/result`-Notification — genau wie native Aufrufe; ein Permission-Plugin kann den Programmtext vor der Ausführung prüfen, und Final-Result-Beobachter sehen das normalisierte äußere Ergebnis. Ihr `execute(args, exec)`:

1. **Bindings aufbauen.** Ein run-scoped Signal folgt der äußeren Cancellation und wird abgebrochen, sobald der Run settled. Jedes sichtbare Tool-Binding snapshotet verlustfreie JSON-Argumente, tritt in den Dispatch-Pool des nativen Vertrags ein (das Scheduling-Design gehört der [Live-Parallel-Note](2026-07-26-ptc-live-parallel-dispatch.md)), führt mit deterministischer Call-ID und dem äußeren Token als `parent` aus, deferred zurückgegebene Kontexte über die äußere Ausführung und loggt das Ereignispaar `tool/ptc-dispatch-start`/`tool/ptc-dispatch`, dessen Settlement-Seite den vollständig gerenderten Ergebnisinhalt trägt. Erfolg gibt den finalen kanonischen JSON-Wert des Tools zurück; Fehlschlag wird zum programmsichtbaren `ToolCallError`. Jeder Sub-Call behält seine eigene unveränderliche Ausführungsidentität und durchläuft die volle Tool-Pipeline.
2. **Führt das Programm aus**: `ctx.codeRuntime.run({ program: args.code, bindings: [{ global: 'tools', functions }], signal: runController.signal })`. Die Runtime erhält das run-scoped Signal, nicht nur das äußere Signal des Callers, sodass jede Art des äußeren Settlements auch die Arbeit in der Runtime abbricht.
3. **Settlement nach quiescence.** Wenn die Runtime settled, bricht die Bridge ausstehende Arbeit ab und leert die Dispatch-Queue vor der Rückkehr. Erfolg liefert erfasste Logs und den Completion-Wert als kanonische Ausgabe; die Registry rendert diesen Wert in durable `tool/result.content`, den die Ergebniskarte direkt liest. Ein Runtime-Fehler wird zu `CodeRunFailedError`; eine Backend-Reject nutzt die normale Fehlergrenze der Registry. Beide erzeugen strukturierte Fehlerergebnisse, und kein Sub-Call kann nach dem Settlement von `run_code` anfügen.

**Sub-Call-Kontexte werden über den Parent deferred.** Injections innerhalb von `run_code` würden die Parent-Call/Result-Adjazenz brechen, daher sammelt `ToolRunContext.deferContext()` jeden `additionalContexts`-Eintrag eines Sub-Ergebnisses in Dispatch-Reihenfolge. Die Registry trägt dieses Array selbst dann, wenn das Programm später wirft, und der Loop hängt jeden Eintrag erst nach dem äußeren Ergebnis und jedem Sibling-Ergebnis im Schritt an. Ein äußerer Post-Execute-Block verwirft tool-deferred Einträge und exponiert nur Kontexte, die die blockierende Entscheidung explizit angehängt hat.

**Nebenläufigkeit ist begrenzt, nicht serialisiert.** Jeder Run besitzt eine Dispatch-Queue, die Aufrufe strikt in Einreichungsreihenfolge startet und jeden über `registry.executionMode` klassifiziert — denselben Fail-Closed-`isConcurrencySafe`-Vertrag, den der native Loop nutzt. Aufeinanderfolgende als parallel klassifizierte Aufrufe überlappen bis zu `maxParallelSubCalls` (Default 10; `1` stellt serielles Dispatch wieder her); ein exklusiver Aufruf leert den Pool und läuft allein. Settlement verwirft noch nicht gestartete Queue-Aufrufe. Diese Note lieferte den serialisierten Platzhalter; die [Live-Parallel-Agent-Note](2026-07-26-ptc-live-parallel-dispatch.md) besitzt den Scheduler, der ihn ersetzte.

**Präsentation.** Der Render Intent von `run_code` wird hier festgelegt, gemäß der [Render-Intent-Agent-Note](../architecture/2026-07-02-tool-render-intent-union.md): `presentCall` erzeugt eine `generic`-Karte mit `kind: 'execute'`, dem Programmtext als Titel und demselben Programmtext als `rawInput`; `run_code` deklariert absichtlich kein `presentResult`, sodass TUI und Host-/Client-Runtime (Web) die Karte über ihren generischen Raw-Content-Fallback mit dem finalen durable `tool/result.content` vervollständigen, einschließlich erfasster Logs plus Rückgabewert, Fehlschlag oder Post-Policy-spill-Vorschau. Das ist keine `terminal`-Karte: Deren Semantik ist „ein Shell-Befehl in einem Arbeitsverzeichnis", was ein Programm nicht ist. Siehe die [Note zur Vollständigkeit der Ergebniskarte](../../archived/bug-fix/2026-07-20-code-mode-result-card-completeness.md).

### Observability: `tool/ptc-dispatch`

Jedes Sub-Dispatch hängt beim Pool-Eintritt ein reines Log-Event `tool/ptc-dispatch-start` an und schließt mit einem `tool/ptc-dispatch`-Settlement-Event ab, das Parent- und Child-Call-IDs, Tool-Identität, normalisierte Argumente und das vollständig gerenderte `content`/`isError`-Ergebnis enthält. Es bleibt außerhalb der Modellhistorie, steht aber Persistenz und UIs zur Verfügung. Die Appends geschehen innerhalb des offenen `run_code`-Turn. Direkte Ausführungen ohne agent laufen weiter, können das Event aber nicht loggen.

Neue Sub-Calls verwenden `<parent>:ptc:<n>`-IDs, nummeriert in Einreichungsreihenfolge. Alle Call-IDs sind für Consumer opak: Die Migration erhält jede historische ID byte-für-byte, einschließlich `:code:`-Teilstrings, sodass Dispatch-Paare, spill-Referenzen und andere Korrelationen intakt bleiben. Die Bridge attribuiert weitergeleiteten Bildkontext auf `{ kind: 'plugin', plugin: 'tools-ptc' }`.

Die [V2-zu-V3-PTC-Spezifikation](../../../../packages/session/session-format-v2-to-v3/README.de.md#ptc-vocabulary) besitzt die exakte historische Tag- und Attributions-Konvertierung; [native V3-Admission](../../../../packages/session/session-format-v2-to-v3/README.de.md#native-v3-admission) besitzt die Zurückweisung von Vorgänger-Tags. Das sind keine Runtime-Aliase: Eine opake Erweiterung darf allein durch einen Versionswechsel keine PTC-Lifecycle-Bedeutung erlangen.

### Der code-runtime seam

`packages/code-runtime/code-runtime/` — `@deepseek-ai/dsh-code-runtime`, abhängig nur von `cordis`. Ein abstraktes `CodeRuntime extends Service` (`super(ctx, 'codeRuntime')`) plus das Vokabular:

- `CodeRunRequest = { program: string; bindings: CodeBindingNamespace[]; signal?: AbortSignal }`
- `CodeBindingNamespace = { global: string; functions: Record<string, (args: unknown) => Promise<CodeJsonValue>>; errorClass?: { name: string; memberNameProperty: string } }` — die Runtime exponiert jeden Namespace als globales Objekt asynchroner Funktionen im Programm; der optionale Deskriptor bittet die Runtime, eine echte programmsichtbare Rejection-Klasse zu injizieren, ohne dem seam consumerspezifische Namen beizubringen. `CodeJsonValue` ist der strukturelle verlustfreie JSON-Typ dieses abhängigkeitsarmen seam, sodass Binding-Argumente und -Auflösungen die Serialisierungsgrenze der Implementierung ganz überqueren.
- `CodeRunResult = { value?: CodeJsonValue; logs: string[]; error?: CodeRunFailure }` — Ausführungsergebnisse des Programms resolven als `error`-Feld. `run()` darf nur bei Caller-/seam-Missbrauch rejecten (etwa ein doppelter Binding-Namespace); Consumer fangen eine nicht konforme Backend-Rejection weiterhin an ihrer eigenen Fehlergrenze ab.
- `CodeRunFailure = { kind: 'exception' | 'timeout' | 'abort' | 'worker-exit' | 'invalid-output' | 'output-limit'; message: string }` — orthogonale, unabhängig gemeldete Ergebnisse gemäß [defensive patterns](../../../../docs/defensive-patterns.de.md); ein Timeout-Lauf ist keine Exception, ein Abort ist kein Timeout, eine verlustbehaftete Completion ist kein Overflow, und ein Substrat-Exit ist keines davon.
- Zwei readonly Backend-Deskriptoren, informativ statt gating: `language` (worin das Programm geschrieben sein muss — `'typescript'` für das erste Backend; ein Python-Backend sagt `'python'` und paart sich mit einem eigenen SDK-Generator auf der Präsentationsseite) und `isolation` (`'worker-thread'` für das ausgelieferte Backend; `'process'`, `'container'`, … für künftige). `dsh-tools` akzeptiert jede `language` mit registriertem SDK-Renderer und `run_code`-Flavor (TypeScript und Python sind ausgeliefert; siehe die [Language-Dispatch-Note](../../archived/feature/2026-07-31-ptc-language-dispatch.md)) und lässt die Assembly sonst laut fehlschlagen — dasselbe Fehlkonfigurations-Idiom wie `toolOrder`-Verletzungen (etwa wenn `mode` nicht-nativ ist, aber gar kein `ctx.codeRuntime` geladen ist).

Requests enthalten jede Runtime-Eingabe; Implementierungen besitzen validierte Timeout- und Limit-Defaults. Die Registry schlägt die optionale Runtime nur nach, wenn PTC mode assembliert wird, sodass der native Modus nicht von ihr abhängt. Fehlende oder sprachinkompatible Runtimes schlagen laut fehl. Alternative Substrate oder Sprachen können die Implementierung hinter demselben seam ersetzen, gepaart mit dem passenden SDK-Generator.

### Die worker-thread Runtime

`@deepseek-ai/dsh-code-runtime-worker-thread`, das zweite Paket der `packages/code-runtime/`-Gruppe. Pro `run()`:

1. **Type-Strip host-seitig** mit Nodes eingebautem `stripTypeScriptTypes` (`node:module`; über den gesamten Engines-Bereich des Repos `^22.19.0 || >=24.0.0` verfügbar und positionserhaltend, sodass Laufzeit-Fehlerzeilennummern zur Modellquelle passen). Der Strip-only-Modus lehnt nicht-löschbare Syntax ab (`enum`, Namespaces) — diese Rejection kommt als `error.kind: 'exception'` mit Nodes Meldung zurück, die SDK-Anleitung sagt „nur löschbares TypeScript", und das Modell korrigiert sich selbst wie bei jedem anderen Programmfehler. Ein Syntax-Level-Fehler spawned nie einen Worker.
2. **Einen frischen `Worker` pro Run spawnen** aus dem eigenen Bootstrap-Modul des Pakets: `env: {}` (wirklich leer — stärker als die Scrubbed-Env-Regel für gespawnte Befehle), `resourceLimits` aus der Config, `stdout`/`stderr` in `logs` erfasst statt geerbt. Kein Pooling und kein Run-übergreifender Zustand: Die Welt eines Programms stirbt mit seinem Worker, wodurch Runs allein aus dem Log rekonstruierbar bleiben und Zustandsübertrag nicht darstellbar ist.
3. **Im Bootstrap ausführen**: Das abgestreifte Programm wird zum Body einer `AsyncFunction`, deren Parameter die Binding-Globals, alle consumer-deklarierten Rejection-Klassen und ein capturender `console`-Shim sind, sodass Top-Level-`await` und `return` funktionieren. PTC mode deklariert `ToolCallError` mit Member-Property `toolName`; die Runtime materialisiert diesen echten Konstruktor, ohne Tools hart zu kodieren. Eine verlustfreie JSON-Completion überquert die Grenze exakt; `undefined` bleibt Abwesenheit, ein verlustbehafteter Wert ist `invalid-output`, und ein übergroßes äußeres Ergebnis ist `output-limit` statt eines Ersatzes durch einen inspizierten String.
4. **Bindings über den Message Port brücken**: Jede Binding-Funktion im Worker postet `{ id, global, name, args }` und wartet auf die Antwort; der Host validiert den Namen gegen die Bindings des Requests, ruft auf und antwortet `{ id, ok, value }` oder `{ id, ok: false, message }` (eine host-seitige Binding-Rejection wird zur programmseitigen Rejection). Die worker-seitigen Namespace-Objekte werden null-prototype über `defineProperty` gebaut, sodass ein Binding namens `__proto__`, `constructor` oder `toString` eine gewöhnliche eigene Property ist, keine Prototyp-Kollision. Unbekannte Namen, doppelte IDs und Post-Settlement-Nachrichten werden zurückgewiesen oder ignoriert — das Port-Protokoll geht von einem feindlichen Peer aus, weil der Peer Modellcode ausführt.
5. **Unabhängige Budgets durchsetzen.** `computeMs` misst die Busy-Zeit des Workers und erlaubt langsame awaited Tools, ohne eine heiße Schleife zu entschuldigen. `maxWallMs` begrenzt die Gesamtlaufzeit einschließlich unaufgelöster Wartezeiten. `maxOutputBytes` begrenzt nur die kombinierte serialisierte äußere Ausgabe aus Logs, Completion oder Diagnose; Zwischen-Binding-Werte haben kein Byte-Limit. Ablauf, Cancellation und Completion terminieren den Worker, und Heap-Exits oder äußerer Overflow sind explizite Fehlschläge.
6. **Dispose bis zur quiescence**: Das eigene Dispose des Services terminiert laufende Worker und *erwartet* deren Exits, bevor es resolved, gemäß [defensive patterns](../../../../docs/defensive-patterns.de.md).

### Trust-Haltung

Die Worker-Runtime bietet Containment, keine Sicherheitsgrenze: Modellcode kann Node-APIs erreichen und hat mit dem bash-Tool vergleichbare Autorität. `worker.terminate()` stoppt den Thread, aber nicht die von ihm gespawnten OS-Prozesse. PTC mode nutzt dasselbe `tools/pre-execute`-Policy-Gate wie bash und fügt eine leere Umgebung, Heap-Limits, einen separaten Isolate und harte Terminierung des Programms selbst hinzu. Deployments, die eine harte Multi-Tenant-Grenze brauchen, benötigen ein Container-Klasse-Backend sowohl für Code als auch für bash; der Isolations-Deskriptor der Runtime lässt sie dieses Backend unterscheiden.

### Was das Modell sieht

Das SDK weist das Modell an, einen async Body in der Sprache der geladenen Runtime zu schreiben (standardmäßig ein löschbarer TypeScript-Body; ein Python-`async`-Body unter einer Python-Runtime — siehe die [Language-Dispatch-Note](../../archived/feature/2026-07-31-ptc-language-dispatch.md)), Tools über `await tools.name(args)` aufzurufen, rejected Tool Calls bei Bedarf zu fangen und nur die Ausgabe zurückzugeben oder zu loggen, die wieder in den Kontext eintreten soll. Beide Flavors formulieren denselben Vertrag in ihrem eigenen Primitiv: Unabhängige Read-only-Aufrufe DÜRFEN unter `Promise.all` (TypeScript) oder `asyncio.gather` (Python) überlappen, mutierende Aufrufe laufen allein in Einreichungsreihenfolge, und abhängige Arbeit sequenziert mit `await`. Das Deklarationspräfix kann so groß sein wie native Schemas, besonders unter `'both'`, bleibt aber für Provider-Caching stabil.

Das eigene `description` des Transports und beide SDK-Anleitungs-Flavors beginnen damit, `code` und `description` als die zwei Pflichtargumente des Aufrufs zu nennen. Prosa, die den Aufruf als „ein Programm übergeben" beschreibt, lässt das zweite Argument nur über das Parameter-Schema auffindbar, und ein Modell, das nur `{code}` ausgibt, verliert das gesamte geschriebene Programm an eine `INVALID_ARGS`-Zurückweisung.

## Konsequenzen

Deployments, die auf `'ptc'` wechseln, müssen jede nur-native `toolOrder` aktualisieren. Assembly-Listener besitzen die Integrität aller umgeschriebenen Protokollnachrichten. Sub-Dispatch startet in Einreichungsreihenfolge unter einem begrenzten Overlap-Pool, während Per-Call-Kontexte ihre Quelle, Envelope und Metadaten über das äußere Ergebnis behalten.

## In Betracht gezogene Alternativen

**Ein Add-on-Consumer-Plugin mit null Core-Änderungen.** Abgelehnt, weil `agent/request` unter [rekonstruierbaren Requests](../architecture/2026-07-05-reconstructable-requests.md) auf Call-Config beschränkt ist, während die Transformation einer assemblierten Tool-Liste die `toolOrder`-Kanonisierung rückgängig machen müsste, ohne deren Config zu besitzen, und von der Listener-Reihenfolge abhinge. Welche Tools dem Modell angeboten werden und in welcher Repräsentation, ist das einzige Anliegen der Registry: Native Schemas und das SDK sind zwei Projektionen eines sichtbaren Speichers.

**`node:vm` als Referenz-Runtime, mit aufgeschobener Härtung.** Abgelehnt: `node:vm` ist keine Isolation (Prototype-Chain-Escapes erreichen das Host-Realm) und kann eine heiße Schleife nicht unterbrechen. Ein Worker-Thread bietet einen separaten Isolate, leere Umgebung, `resourceLimits` und zuverlässiges `terminate()` bei bash-äquivalentem Vertrauen, sodass Referenz- und Produktionsimplementierung ein Paket sind — ohne Unsafe-Acknowledgement-Zeremonie.

**Ergebnis-Elision/-Zusammenfassung über nativem Tool-Calling.** Behandelt nur die Kontext-Bloat-Hälfte des Problems: Alte `tool-result`s zu trimmen ist als geloggter Surface-Ersatz unter rekonstruierbaren Requests billig, kostet aber weiterhin einen Modell-Roundtrip pro Aufruf und kann weder Schleifen noch Verzweigungen noch Joins ausdrücken. Komplementär, nicht konkurrierend; es kann sich für residuelle native Aufrufe unter PTC mode schichten.

**Paralleles natives Dispatch im Loop.** Die andere Antwort auf Roundtrip-Kosten zum Entscheidungszeitpunkt; es war durch Concurrency-Safety-Metadaten blockiert und bietet ohnehin keine Komposition — es parallelisiert Aufrufe, die das Modell in einem Schritt bereits beschlossen hatte. Die Queue-Entscheidung von PTC mode hielt beide kompatibel, und beide wurden später ausgeliefert: die Metadaten als `isConcurrencySafe` (die [Note zum parallelen Tool-Aufruf](2026-07-10-parallel-tool-call-execution.md)) sowie natives Rolling-Pool-Dispatch plus Per-Tool-Binding-Parallelismus auf demselben Klassifikator.

**Immer exklusiv (Cloudflare-getreu, kein Modus).** Abgelehnt wegen des primären Consumers dieses SDK: Die alltäglichen Einzelaufrufe eines coding agent (`bash`, `read`, `edit`) sind als native Aufrufe bereits ideal, und jede Editierung durch ein Programm zu zwingen belastet den häufigen Fall. Die mode-Config hält die getreue Form (`'ptc'`) eine Config-Zeile entfernt, ohne sie aufzuzwingen.

**Per-Tool-Sichtbarkeitsstufen (dieses Tool nativ, jenes nur-ptc).** Vertagt: Es braucht Per-Tool-Metadaten und eine Präsentationsteilung, die `'native' | 'ptc' | 'both'` nicht bietet, und sein Design hängt von Belegen ab, wie Modelle die Nutzung unter `'both'` aufteilen.

**Bereinigte Identifier-Aliase im SDK** (`my-tool` → `my_tool`, Cloudflares Ansatz). Abgelehnt: Quotierte Schlüssel auf einem `declare const` machen jeden Namen mit null Alias-Kollisionslogik erreichbar; Modelle kommen mit `tools["my-tool"](…)` gut zurecht.

**Ein REPL-artiger persistenter Kernel** (Zustand überlebt `run_code`-Aufrufe). Für den MVP abgelehnt: Call-übergreifender Zustand wäre für das Session-Log unsichtbar und bräche die Rekonstruierbarkeitsgarantie, dass jeder Request eine reine Funktion des Logs ist; frisch-pro-Run erhält sie. Ein Kernel-artiges Backend bleibt später hinter dem seam ausdrückbar, mit eigener Logging-Story.

## Risiken

**Der Worker ist keine harte Sicherheitsgrenze.** Bewusst und dokumentiert (§Trust-Haltung): Die Haltung entspricht dem bestehenden bash-Tool, das Containment übersteigt es, das Gating nutzt dieselben Approval- und Sandbox-Policies. Deployments, die mehr brauchen, benötigen ein künftiges `isolation: 'container'`-Backend — als designed Erweiterung des seam verfolgt, nicht als TODO an diesem Design.

**`stripTypeScriptTypes` ist als experimental markiert.** Es ist dieselbe Engine (amaro/swc) hinter Nodes eigener nativer `.ts`-Ausführung und über den gesamten Engines-Bereich des Repos als API exponiert. Mitigationen: Die Unit-Suite der Runtime prüft Positionserhaltung und die erforderlichen Teile der Erasable-Only-Rejection-Meldung, der Aufruf sitzt hinter einer privaten Funktion, und `amaro`/`sucrase` sind direkte Ersatzkandidaten, falls die API driftet. Die Erasable-Only-Teilmenge ist eine modellzugewandte Eingabebeschränkung, und die Fehlermeldung sagt dem Modell, wie es das Programm korrigiert.

**Prompt-Kosten des SDK, besonders unter `'both'`.** Das `.d.ts` kann mit den nativen Schemas, die es ergänzt, konkurrieren; `'both'` trägt zwei Repräsentationen. Präfix-Stabilität + Provider-Caching amortisieren die Per-Session-Kosten; der Modus ist pro Deployment; die Agent Note erhebt keinen Anspruch auf bedingungslose Einsparungen. Gemessene Anleitung (wann welcher Modus vorzuziehen ist) ist explizit Post-Ship-Lernen.

**Wachstum des Registry-Scopes.** `dsh-tools` absorbiert Codegen, ein Tool, eine Bridge und ein Event. Paketmodule trennen diese Verantwortlichkeiten (`ts-types.ts` und `ptc.ts` neben `schema.ts`, `json-schema.ts` und `presentation.ts`), während `ctx.codeRuntime` die gesamte code-runtime-spezifische Implementierung besitzt.

**Große verlustfreie JSON-Werte können Speicher erschöpfen.** Tool-Bindings snapshoten verlustfreies JSON vor dem Dispatch und geben kanonische JSON-Auflösungen ganz zurück. Die Runtime validiert beide Seiten des Worker-Ports und setzt kein Per-Binding-Byte-Limit; Structured-Clone-Kosten und Prozess- oder Worker-Speicher sind die praktischen Grenzen. Das kombinierte Outer-Output-Ledger für Logs, den Completion-Wert und eine Fehlerdiagnose ist die einzige byte-limitierte Grenze.

**Sub-Dispatch-Overlap wird durch Safety-Zusicherungen der Tools begrenzt, nicht durch den Caller.** `Promise.all` oder `asyncio.gather` eines Programms erkauft Wall-Clock-Parallelität nur über Aufrufe hinweg, die das Tool selbst als concurrency-safe klassifiziert; eine Folge exklusiver Aufrufe kostet weiterhin ihre Roundtrips nacheinander, und Modelle mögen zu viel erwarten. Die SDK-Anleitungen beider Flavors nennen den realen Vertrag. Diese Note lieferte den serialisierten Platzhalter, der das Risiko absolut machte; die [Live-Parallel-Agent-Note](2026-07-26-ptc-live-parallel-dispatch.md) besitzt den Scheduler und sein Overlap-Limit.

**Budget-Messung liest den Event Loop, kein Flag.** Busy-Time-Polling (`eventLoopUtilization()`) ist gröber als ein exaktes CPU-Meter — ein Budget läuft bis zu ein Poll-Intervall zu spät ab — und seine Korrektheitsaussage („ein ausstehender Dispatch kann es nicht pausieren") ist tragend gegen ein feindliches Programm. Beide Seiten sind unit-getestet (eine heiße Schleife mit einem ausstehenden Köder-Dispatch stirbt bei `computeMs`; ein auf ein langsames Binding wartendes Idle-Programm überlebt bis `maxWallMs`), und das Poll-Intervall ist eine interne Konstante, keine Config — nichts, was ein Deployment zu einem Bypass verstimmen könnte. `maxWallMs` ist Config und erreicht `setTimeout`, das eine Verzögerung oberhalb von `MAX_TIMER_DELAY_MS` (2^31-1 ms) auf 1 ms klemmt; ein reiner Positivitäts-Check akzeptiert daher ein 25-Tage-Limit, das beim ersten Tick abläuft und jeden Run in einen Timeout schickt. Die Worker-Runtime range-checkt das Feld deshalb beim Laden. `computeMs` braucht keine Obergrenze, weil es gegen gemessene Auslastung verglichen wird statt an einen Timer übergeben zu werden.
