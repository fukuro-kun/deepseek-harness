# Agent Note: Session persistence als abstrakter service über das bestehende `SessionEvent`
[English](2026-06-14-session-persistence.md) | [中文](2026-06-14-session-persistence.zh.md) | Deutsch

Status: implemented


## Problem

Sessions lebten nur im Speicher. Das Beispiel-`session-jsonl.ts`-plugin (in beiden Beispielen byte-identisch dupliziert) war write-only-Telemetrie: Es pufferte `session/event` und hängte JSON-Zeilen an, ohne read/replay-Pfad, ohne Crash-Sicherheit (kein fsync, kein atomares Schreiben, ein fire-and-forget-dispose-Drain), ohne Listing und ohne Format-Versionierung. Nichts konnte eine vergangene session von der Festplatte in einen live agent rehydratieren, daher waren durable resume, durable forking und host-seitiges session-Browsing allesamt unmöglich.

Das [event-sourced Modell](2026-06-11-event-sourced-sessions.de.md) macht das append-only-Log zur einzigen source of truth und leitet die LLM-Historie davon ab. Die persistence musste dem treu bleiben: das bestehende `SessionEvent` direkt persistieren, ohne einen parallelen "persisted message"-Typ, in den das Log hin- und herkonvertiert wird. Das backend musste auch austauschbar sein — jetzt ein file store, später ein database store — hinter einer einzigen interface.

## Entscheidung

Persistence ist ein **capability seam** mit einer abstrakten Service Definition ([capability seams](2026-06-13-capability-seams.de.md), das `dsh-shell`-Template), nicht loop- oder Core-Logik:

1. **Interface** (`dsh-session-persistence`, `ctx.sessionPersistence`) — ein abstrakter `SessionPersistence`-service: `create`/`open`/`stat`/`list`/`flush`, wobei `create`/`open` pro session `SessionHandle`s zurückgeben, die `read`/`append`/`flush`/`close` tragen ([handle-based seam](2026-08-27-handle-based-session-persistence.de.md)). Seine persistente Einheit IST das bestehende `SessionEvent` (`{ type, seq, time, data }`), wörtlich wiederverwendet — kein Conversion-Typ.
2. **Implementation** (`dsh-session-persistence-jsonl`) — ein append-only logisches JSONL-Log pro session: eine `SessionHeader`-Zeile, gefolgt von storage records, die den zusammenhängenden `SessionEvent`-strom verlustfrei darstellen. Das aktuelle Format schreibt ein event pro Zeile; die eingefrorenen v0- und v1-reader behalten ihre historische packed-delta-Darstellung. [Geprüfte Zstandard-frames](2026-07-19-zstandard-jsonl-session-logs.de.md) sind die Standard-Physische-Kodierung, rohe Zeilen sind konfigurierbar.

Wichtige durable, umstrittene choices:

- **Das kanonische durable Log persistiert jedes aktuelle `SessionEvent` verlustfrei.** Ein `assistant/message` oder `assistant/attempt` embedet den exakten, zeitgestempelten provider stream eines attempts; `deriveMessages()` projiziert nur die surface message. Eingebettete stream-Mitglieder zu verwerfen ist verlockend, aber es verliert replay, timing, usage, partial-failure- und diagnostische Fakten. Das Entfernen eines vollständigen events erfordert ebenfalls dichte Neu-Nummerierung, weil `seq = log.length` und `events[i].seq === i`; die [v1-zu-v2-Migration](2026-09-01-v2-embedded-assistant-streams.de.md) führt dieses Rewrite explizit aus, statt das kanonische Log zu filtern.
- **Append-only; ein gecrashtes turn wird geschlossen, nie gekappt.** Gefluschte events werden nie umgeschrieben. Die [semantische checkpoint policy](../../../../packages/session/session-checkpoint-policy/README.de.md) leert den request vor der model dispatch, einen aufgezeichneten top-level call vor der tool dispatch und das vollständige response/result-batch nach einem step; der loop leert die finale turn-Grenze. Weil ein unterbrochenes turn erhebliche gültige Arbeit enthalten kann, gibt die persistence seine zusammenhängenden, parsebaren events unverändert zurück; der reader besitzt das Ausgleichen — resume berechnet risikoklassifizierte error results für unbeantwortete assistant calls, ein fehlendes `step/end` und ein `turn/end` mit `{ kind: 'interrupted' }` (`interruptedTurnClosers`) und hängt sie über seinen write handle an, während read-only-observer dieselben closer nur im Speicher hinzufügen. Die synthetischen results halten resumed provider transcripts gültig. Nur das unvollständige Fragment eines zerrissenen finalen appends wird verworfen — daraus erholte vollständige records werden vom write path vor seinem ersten neuen append durable umgeschrieben; ein Parse-Fehler oder eine Sequenz-Lücke im commitierten Präfix ist Korruption und macht die session nicht ladbar.
- **Das file backend ist kanonisch, während der service erweiterbar bleibt.** `dsh-session-persistence-jsonl` ist der einzige first-party provider und besteht `runPersistenceContract`; der abstrakte service bleibt out-of-tree-providers verfügbar. Die [JSONL-only-persistence decision](../simplification/2026-08-30-jsonl-only-session-persistence.de.md) besitzt die Entfernung des first-party-database-providers und seinen bewussten compatibility cut.
- **Metadaten sind out-of-log.** Formatversion, cwd und lineage sind storage concerns, nicht replaybarer conversation state, daher leben sie in einem `SessionHeader`, das `dsh-session` besitzt und über ein neues readonly `session.header` an eine `Session` angehängt wird — nie in `SessionEventMap`, nie erreichbar durch `deriveMessages()`. `createdAt` sind nicht-negative safe-integer-Unix-epoch-Millisekunden: live-Erstellung und persistence-Registration verwerfen Bruchwerte, und JSONL validiert den dekodierten header. Die Alternative (ein merge-extensibles `session/meta` event als Log-Zeile 0) wurde abgelehnt: ein in-log-event würde gratis mit einer seeded/forked session mitfahren, aber Metadaten sind kein replaybarer state, daher ist die explizite out-of-log-header-Grenze der sauberere Preis. (Der header wurde ursprünglich in ein immutable `SessionHeader` plus ein mutables `SessionSummary` aufgeteilt, deren Union `SessionMeta` war; das mutable summary wurde später als dead state entfernt — siehe [Das mutable session summary entfernen](../../archived/simplification/2026-06-19-drop-mutable-session-summary.md).)
- **`ctx.agents.create()` und `ctx.agents.resume()` sind async factories; resume überquert zusätzlich die persistence-Grenze.** `ctx.agents.resume({ resumeSessionId })` öffnet den write handle der session, liest das gespeicherte Log und publiziert die vorbereitete Session unter der persistenten id und setzt ihre Projektionen fort. Die [Session preparation decision](../../archived/architecture/2026-08-05-session-preparation.md) besitzt das Ownership-Fenster der unpublizierten Session. Der agent loop injiziert `sessionPersistence` NICHT hart (das würde non-persistent demos forever pendeln lassen); `resume` lehnt mit einem klaren error ab, wenn es fehlt.

## In Betracht gezogene Alternativen

Jede der obigen Key-choices hält ihre abgelehnte Alternative dort fest, wo die choice ausgesprochen wird: ein **stream-gefiltertes kanonisches Log** — verliert attempt-Beweise, während das Entfernen von events ohne explizite Migration zusammenhängende Sequenznummern bricht; **das Kapptieren eines gecrashten turns** — zerstört still die echte Arbeit eines langen autonomen runs; ein **in-log-`session/meta`-event als Log-Zeile 0** — Metadaten sind kein replaybarer state; **endliche Bruch-`createdAt`-Werte** — haben keinen producer und divergieren von der integer-Unix-Millisekunden-Storage; **das Hart-Injizieren von `sessionPersistence` in den loop** — würde non-persistent demos forever pendeln lassen.

Format-Versionierung: der header trägt eine `version`; handles exponieren nur das logische Format, das von `SESSION_FORMAT_VERSION` gewählt wird ([Versions-Autorität](../../../../docs/session-format-status.de.md)). JSONL-event-body-Lesezugriffe komponieren die vollständige statische adjacent-migration-Chain, bevor sie einen handle zurückgeben; jede edge besitzt ihre historischen Transformationen. V0 bleibt bei der suffixlosen `session.jsonl[.zstd]`, während positive Versionen immutable, kleingeschriebene `session.vN.jsonl[.zstd]`-Namen verwenden ([released Session migration](2026-08-31-released-session-format-migrations.de.md)). Append und flush der aktuellen generation sind robust gegen partielle trailing writes; ein zukünftiger provider oder write-ahead log braucht seinen eigenen power-loss- und recovery-contract.

## Konsequenzen

Die Service Definition, der JSONL provider und der metadata contract in `dsh-session` (`session.header`, die `create(header, options?)`-Signatur) erkaufen durable resume/fork, einen read/replay-Pfad, Crash-Toleranz und host-seitigen session-Zugriff über das bestehende event-sourced Log. Die wiederverwendbare `runPersistenceContract`-suite hält den provider und zukünftige implementations an denselben append-only-, contiguous-seq-, lazy-materialization-, logical-recovery-, integer-metadata- und serializability-semantiken fest. Das Persistieren des vollständigen logischen Logs stellt auch die event-Fidelity: Jeder Assistant attempt behält seinen exakten kompakten zeitgestempelten stream in einer durable settlement.
