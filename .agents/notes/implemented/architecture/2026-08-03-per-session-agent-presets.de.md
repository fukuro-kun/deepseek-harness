# Agent Note: Der agent einer Session wird aus einem vorgegebenen cordis.yml zusammengesetzt
[English](2026-08-03-per-session-agent-presets.md) | [中文](2026-08-03-per-session-agent-presets.zh.md) | Deutsch

Status: implemented


## Problem

Ein `dsh`-Prozess bedient viele Sessions, aber die Komposition, die festlegt, was ein agent *ist* — seine Tools, Persona, Prompt-Abschnitte, Delegations-Backends — wird für den ganzen Prozess durch das `cordis.yml` fixiert, mit dem der Launcher gebootet hat. Ein Deployment, das einen benchmark-minimalen agent neben einem voll ausgestatteten coding agent will, muss zwei Prozesse betreiben, und der mitgelieferte Workaround (`apps/cli/config/minimal.cordis.yml`, ein `--config`-Overlay, das Tool-Zeilen deaktiviert) ändert alle Sessions auf einmal.

Die naheliegende Lesart von „eine Session wählt ihre Komposition" ist, dass der loader eine neue Ebene braucht. Braucht er nicht. [`dsh-tools`](../../../../packages/core/tools/README.de.md) und [`dsh-system-prompt`](../../../../packages/core/system-prompt/README.de.md) legen Registrierungen bereits in die Scope-Ebene des aufrufenden Kontexts, und [der agent ist ein Registrierungs-Scope](2026-07-08-agent-scope-contexts.de.md). Was fehlte, war eine Möglichkeit, ein ganzes `cordis.yml` auf den Scope eines einzelnen agents zu richten.

## Entscheidung

Ein **preset** ist ein Verzeichnis, das ein `agent.cordis.yml` enthält. Die `setup(agentCtx)` der agent-Factory mountet es als Cordis-`include`-Teilbaum, der in den Scope-Kontext dieses agents eingehängt wird. Entry-Kontexte verketteten sich an den Kontext, in den ein Teilbaum eingehängt wurde, also landet jede Registrierung innerhalb des presets in der Ebene dieses agents und wird mit dem agent abgewickelt. Keine registry bekommt eine zusätzliche Ebene, und keine bereits laufende Session wird berührt.

Die Komposition teilt sich in zwei Ebenen — entschieden danach, was geteilt werden muss, nicht danach, was sich agent-nah anfühlt:

| Ebene | Instanzen | Inhalt |
|---|---|---|
| Host | eine | Die registries selbst (`tools`, `systemPrompt`, `agents`, `agent-loop`, `sessions`), sessionübergreifende Einrichtungen (Persistenz, Abfrage, Projektionen, Storage, Einstellungen, Credentials, Telemetrie), die subagent-Provider, die jene Einrichtungen auflösen, und der Web-Host |
| Agent | eine pro Session | Was ein einzelner agent zu jenen registries beiträgt: Tool-Plugins, Persona und Prompt-Abschnitte, Compaction-Policy |

Model-Routing bleibt aus presets heraus. `installAgentLlmTarget` ist bereits der pro-agent seam für Provider, Modell und Reasoning-Aufwand, und ein innerhalb eines presets gemounteter LLM-Adapter würde von `agent-loop`, das in der Host-Ebene lebt, niemals aufgelöst.

Die presets, die das Deployment ausliefert, sind die Verzeichnisse unter `packages/preset/agent-presets/presets/`; das Verzeichnislisting ist die Liste, nicht eine hier wiederholte Aufzählung.

Das Mounten ist standardmäßig pro Session. Die gemessenen Kosten für eine zwölfzeilige Komposition liegen bei ~3 ms und ~600 KB pro Session — Isolation ist also der billigere Default als jedes Sharing-Schema, und ein von einem Nutzer oder einem agent verfasstes preset hat dann den kleinstmöglichen Wirkungsradius. Ein preset, das wirklich ein teures Singleton besitzt, entscheidet sich mit Cordis' eigenem `isolate`-Vokabular für Sharing: ein benanntes realm-Label ist prozessglobal, zwei Teilbäume mit demselben Label lösen also eine Instanz auf.

Welches preset eine unbenannte Session bekommt, ist eine Nutzereinstellung (`agent-presets.default`), die sich über das `default` der Komposition legt, welches zur `base` wird. Beide Schichten werden gebraucht: Der Kompositionswert ist das, was ein Deployment ausliefert, und muss ganz ohne Settings-Provider funktionieren; die Einstellung ist das, was eine Person ändert, ohne ein `cordis.yml` zu bearbeiten, das ihr vielleicht nicht gehört.

## Konsequenzen

**Der effektive Default wird bei jeder Auflösung gelesen, nie als Snapshot.** Ein gecachter Wert bräuchte ein `watch`-Abonnement und einen Reload-Pfad, um ehrlich zu bleiben, und der aufgelöste Scope liest ein hot-reloadetes Dokument ohnehin neu. Das Durchlesen ist auch das, was die Grenze korrekt statt bloß billig macht: Der neue Wert gilt für die nächste erstellte Session, und jede laufende Session behält die Komposition, aus der sie gebaut wurde. Diese Invariante ist dieselbe, die das Session-Log von der anderen Seite durchsetzt — der Header zeichnet die id auf, mit der eine Session ERSTELLT wurde, und ein `agent-preset/selected`-Event zeichnet jeden späteren Wechsel einer leeren Session auf; ein Leser löst daher das Paar auf (`resolveSessionPreset`) und niemals den Header allein: Ein resume baut die Komposition wieder auf, unter der die Historie erzeugt wurde, statt den Deployment-Default zum resume-Zeitpunkt; die presenter eines kalten transcripts lösen in der Ebene dieser Komposition auf; und das Gateway lehnt den Versuch ab, eine live Session unter einem anderen preset zu übernehmen als dem, unter dem sie läuft. Ein Snapshot würde beide genau in dem Moment auseinanderlaufen lassen, in dem sich die Einstellung ändert.

**Ein direkt eingehängter Teilbaum ist für das Boot-Audit unsichtbar.** Er verknüpft sich nie mit einem `Entry`, fehlt daher in `ctx.loader.entries()`, und `assertEntriesActivated` kann ihn nicht sehen. Das Mount auditiert stattdessen seine eigenen Zeilen und liest den Baum über eine `Include`-Unterklasse, die ihn publiziert.

**Ein preset kann eine group nur benennen, weil die App eine registriert.** Ein realm über Zeilen hinweg zu teilen ist eine `cordis:group`-Zeile, und ein preset, das außerhalb dieses Workspace lebt — die verfassten unter dem Harness-Home, genau darum geht es — kann `@cordisjs/plugin-group` nicht per Namen auflösen: Nodes aufwärts laufender `node_modules`-Walk erreicht den Harness von dort nie. `boot()` registriert `cordis:group` daher neben `cordis:include` als loader-Builtin, sodass beide über die ambient-Modul-Pipeline laden statt über die eigene Specifier-Auflösung des eingehängten Baums. Ohne sie ist das obige `isolate`-Vokabular nur zeilenweise ausdrückbar, und ein Provider könnte niemals mit seinen Konsumenten gruppiert werden.

**Ein preset darf nicht in das root-service-realm publizieren.** Ein solcher Service ist prozessglobal statt pro Session; die zweite Session, die dasselbe preset mountet, kollidiert also mit der ersten — und die Kollision zeigt sich als unhandled rejection, die `setup` nie beobachtet, und hinterlässt einen halb komponierten agent, der gesund aussieht. Das Mount lehnt ihn stattdessen ab, und die Package-Invariante prüft bei jeder Service-Benachrichtigung erneut, weil eine Zeile, die aus einem Timer oder einer asynchronen Fortsetzung publiziert, einem einmaligen Audit entginge.

**Ein Fehler rollt den agent zurück.** `setup` läuft vor der Publikation; ein abgelehntes Mount lässt daher `ctx.agents.create()` fehlschlagen und hinterlässt nichts. Deshalb ist `setup` die einzige unterstützte Aufrufstelle.

**Ein Test, dass die preset-Datei nie umgeschrieben wird, muss fehlschlagen können.** Die erste Version behauptete, die Datei sei nach einem gewöhnlichen Mount unverändert, und hätte nichts entdecken können: Der Loader erreicht seinen Schreibpfad nur, wenn er entscheidet, dass sich die Config geändert hat, und nichts in jener Komposition disposete sich je selbst. Der Regressionstest pflanzt eine Zeile, die sich selbst disposet — die Form, die ein echtes preset jedes Mal trifft, wenn ein agent abgebaut wird — und hält die Komposition in einem Temp-Root statt unter `fixtures/`, denn ohne die Überschreibung schreibt der Loader die gelesene Datei um: Eine committed fixture würde durch genau den Lauf beschädigt, der den Bug beweist, und jeder Lauf danach würde gegen die beschädigte Datei vergleichen und bestehen.

**Fiber-Mitgliedschaft ist Objektidentität, nicht `uid`.** Eine `uid` ist ein registry-interner Zähler; fibers in zwei verschiedenen roots kollidieren darauf; ein Vergleich per `uid` ließ den Teilbaum einer Laufzeit für einen Service einstehen, der in einer anderen publiziert wurde. `ctx.plugin()` gibt einen thenable `Object.create(fiber)`-Wrapper zurück, der nie identisch mit dem fiber in einer Elternkette ist; der Teilbaum fängt daher während der Konstruktion seinen eigenen fiber.

**Eine preset-Datei ist ein Input, niemals ein Persistenz-Ziel.** `EntryTree.write()` persistiert einen Baum, wann immer der Loader entscheidet, dass sich die Config geändert hat, und ein sich selbst disposeendes Plugin reicht dafür schon — der Abbau eines agents disposet seinen ganzen Teilbaum. Geerbt würde das die gelesene Komposition umschreiben — in der Praxis wird ein ausgeliefertes preset beim ersten Session-Ende auf `[]` gekürzt. Der Teilbaum überschreibt `write()` mit einer No-Op.

**Ein Plugin, das sich selbst in der globalen registry nachschlägt, bricht innerhalb eines presets.** `ctx.tools.register()` legt in den Scope des AUFRUFENDEN Kontexts; ein in einem preset gemountetes Plugin registriert also für einen agent, und ein ungescopter `ctx.tools.get(name)` findet korrekt nichts. `dsh-tool-skill` tat genau das und warf bei jedem preset-Mount; es vergleicht jetzt gegen die von ihm registrierte Definition. Jedes Plugin, das preset-mountbar sein soll, muss seine eigene Registrierung halten statt sie per Namen neu zu lesen.

**Ein entry-lokales `isolate`-realm ist für den eigenen Scope des agents unsichtbar, nicht nur für den Host.** Nur Zeilen innerhalb dieser group lösen den Service auf. Genau das macht die `skills`-registry eines presets zum Eigentum eines agents statt geteilt — und es bedeutet, dass ein Konsument, der außerhalb der group seines Providers steht, stillschweigend die Host-registry auflöst und nichts beiträgt.

**Wechseln ist nur erlaubt, solange eine Session leer ist.** Sobald ein turn gelaufen ist, wurde diese Historie unter den Tools des presets erzeugt, und ein Tausch würde geloggte tool calls verwaist zurücklassen; `agentPreset.select` antwortet daher `agent-preset-locked`. Ein Wechsel im leeren Zustand behält agent und Session und ersetzt nur den Teilbaum, denn der Host verwirft das erzeugte `AgentHandle` und es gibt kein delete-RPC — und sie zu behalten ist ohnehin das bessere Ergebnis, da session id, Workspace-Anbindung und Projektionen alle an Ort bleiben. Der Tausch ist unmount-then-mount (zwei Kompositionen würden dieselben Tool-Namen in eine Ebene registrieren); er löst daher das neue preset auf, bevor irgendetwas abgebaut wird, und stellt das vorherige wieder her, wenn das neue Mount fehlschlägt.

**Ein preset zu verfassen ist ein RPC, und ein privilegierter.** Eine Komposition ist eine Datei, aber „bearbeite sie im Dateisystem" ist keine Browser-Affordanz; das Verzeichnis bekam daher `read`/`write`/`remove` neben `select`. Connection authentifiziert Authoring, `list`, `select` und die komplette Host-API mit einer Browser-Session: Eine Komposition benennt die Plugins, die eine Session ausführt; eine zu lesen ist Aufklärung, eine zu schreiben ist beliebige capability, während die Wahl eines presets nichts gewährt, was `session.create` mit `agentPreset` nicht bereits gewährte. Die capability ist auch nicht die des presets: Der eigene Default des Deployments trägt bereits `bash` und die Dateisystem-Tools; jeder Aufrufer, der überhaupt eine Session starten darf, kann bereits Befehle als dieser Prozess ausführen. Containment ist eine Eigenschaft der id (`[a-z0-9][a-z0-9-]*`), geprüft bevor sie ein Verzeichnisname wird, statt durch Inspektion des zusammengesetzten Pfads danach; der Text wird mit schema und Dialekt des loaders geparst, sodass ein Speichern keine Datei hinterlassen kann, die keine Session laden könnte. Ausgelieferte presets werden für Schreiben und Löschen abgelehnt, denn die Kopie des Deployments ist das, wogegen ein kaputtes lokales preset verglichen wird — was zugleich „duplizieren, dann bearbeiten" zum Authoring-Pfad macht statt zu einem nachträglichen Einfall.

**Ein Service mit einem Konsumenten außerhalb der agent-Ebene kann nicht in ein preset ziehen.** Der aggressive Schnitt verschob die `subagents`-registry und ihre spawn/fork-Backends in das entry-lokale realm der Delegations-gruppe, und `dsh web` bootete danach nicht mehr: `SubagentRuntime` ist eine Host-Zeile, die die sessionübergreifenden Remote-Abfragen des Browsers (`list`, `prompt`) exponiert; sie wartete also ewig auf einen Service, den nur Sessions bereitstellten. Eine pro-Session-Kopie ist doppelt falsch — ein Provider-Name registriert einmal, die zweite Session wäre ohnehin kollidiert. Die registry und jedes geteilte Backend, einschließlich der [fixierten Codex- und Claude-Code-Produktprovider](../../archived/architecture/2026-08-10-product-subagent-providers-in-shared-host.md), liegen in der Host-Ebene; ein preset steuert bei, welche Delegations-TOOLS sein agent sehen soll, und diese Tools lösen die Host-registry auf. `workflows` bleibt entry-lokal, weil nichts außerhalb eines agents sie liest. Das Greppen der Injektoren ist es, was das hätte fangen müssen und nicht fing: Die Suche muss die Host-Packages einschließen, nicht nur die der agent-Ebene.

**Ein Test mit echter Komposition, der eine Host-Zeile deaktiviert, kann diese Zeile nicht auditieren.** Der Web-Kompositionstest hält API Gateway und die Domänen-Remote-Services aktiv, während er die reinen Transport-Zeilen webserver, Connection, Session-Export, Assets und Telemetrie deaktiviert. Mit ersetztem Browse-Verzeichnis-Picker deckt sein Start-Audit den Host-Ebenen-Service-Graphen ab, ohne einen Port zu binden.

**Die Package-Namen eines presets müssen vom Harness auflösen, nicht vom preset.** `EntryTree.import()` löst eine Zeile gegen die `baseUrl` ihres eigenen Baums auf, die `Include` auf das Verzeichnis der Komposition setzt. Für einen relativen Specifier richtig, für einen Package-Namen fatal: Ein lokal verfasstes preset lebt unter dem Home des Nutzers, wo Nodes aufwärts laufender `node_modules`-Walk den installierten Harness nie erreicht; jede `@deepseek-ai/dsh-*`-Zeile schlägt beim Import fehl und das ganze preset ist unmountbar. Die ausgelieferten presets verbargen das — sie liegen innerhalb der Installation. Das Mount zeichnet die base der Host-Komposition auf, bevor es den Teilbaum einhängt, und schickt bare specifier dorthin, während relative Pfade weiterhin vom preset aus auflösen, sodass dessen eigene Dateien mit ihm reisen. Der echten Kompositionstest, der ein preset in ein Temp-Root schreibt, hat es gefunden.

**Die preset-id ist modellsichtbar und muss geloggt werden.** Sie bestimmt Tool-Set und Prompt; eine resumte Session muss daher dieselbe Komposition wiederherstellen; sie aufzuzeichnen ist ein Session-Fakt, kein Laufzeit-State. Sie reist im Session-Header neben `cwd`, und die summary trägt sie, damit ein Picker zeigt, was eine Session tatsächlich läuft, statt des aktuellen Deployment-Defaults.

**Ein dauerhaftes Header-Feld ist erst dauerhaft, wenn der Provider es schreibt.** `agentPreset` landete mit der richtigen Begründung auf `SessionHeader`, und der JSONL-Provider ließ es aus; der abgeleitete Abfrageindex bildet Header-Felder ebenfalls explizit ab; eine resumte Session kam also ohne preset zurück, und die Oberflächen, die es nennen, verstummten. `summarizeCold` hatte dieselbe Form — es baute die Cold-List-Zeile von Hand statt die geteilte Projektion wiederzuverwenden. Ein als dauerhaft deklariertes Feld braucht einen Test, der einen echten store quert, nicht nur den Typ, der es deklariert.

**Die Wahl gehört auf den Screen, wo sie noch funktioniert.** Der Composer-Platz verbrachte fast sein ganzes Leben deaktiviert, da das preset fixiert ist, sobald ein turn gelaufen ist. Er zog auf den New-Session-Screen neben den Workspace-Picker, wo die Wahl *gestaged* wird: Jener Screen geht der Session voraus, für die er gilt, und die Stage landet, wenn eine Session aktuell wird und noch leer ist — deckt also sowohl die Session ab, die ein Workspace-Connect erzeugt, als auch die leere, die er wiederverwendet; das würde ein Reiten auf `sessions.create` verpassen. Sie ist bei erster Nutzung verbraucht, passend zum Workspace-Picker daneben. Was eine laufende Session läuft, ist danach ein Read-Only-Label in ihrem Header: Ein Control dort würde einen Wechsel versprechen, den der Host ohnehin ablehnt.

**Ein preset vervielfacht Kosten, die der Host bereits zahlte: nichts disposet einen agent.** Gemessen an den ausgelieferten Kompositionen mit `--expose-gc` hält ein live agent ~0,17 MB auf `minimal` und ~1,31 MB auf `standard`/`cordis`, gemountet in ~38 ms bzw. ~135 ms; der erste agent eines Prozesses kostet ~7 MB mehr, da Node die Module importiert, die dann jedes spätere Mount teilt. Wachstum ist strikt linear — 10, 30 und 50 agents ergeben dasselbe pro-agent Delta — und disposal holt im Wesentlichen alles zurück (50 `standard`-agents hielten 57,8 MB und gaben sie zurück). Der Objektgraph leckt also nicht; der Lebenszyklus tut es. `ApiSessionAgentController` verwirft das von der registry zurückgegebene `AgentHandle`, `archiveSession` bearbeitet nur die Workspace-registry, `AgentRegistry` hat kein Eviction, und die einzige disposal-Stelle im Host ist der Shutdown des eigenen JSON-RPC-Servers. Ein Web-Host behält daher jede Session, die er berührt hat, bei ~1,3 MB pro Stück, seit presets komponiert werden, statt ~0,2 MB vorher. Zu beachten: Das Stutzen der Mount-registry hilft hier nicht — sie verwirft Einträge, deren fiber-`uid` freigegeben wurde, und ein agent, der nie stirbt, gibt nie eine frei.

- Verbleibendes TODO: Eviction untätiger agents — dispose nach Persistieren der Session und Re-Mount beim resume. Gehört dem Host, der das handle besitzt, nicht diesem seam.

## Erwogene Alternativen

**Eine preset-Ebene zu den gescopteten registries hinzufügen.** `ScopedLayers.merge()` kombiniert die globale Ebene mit genau einer exact-scope-Ebene. Eine Zwischenebene ließe viele Sessions eine gemountete Komposition teilen, ändert aber `dsh-scope` und jede scope-bewusste registry, um Kosten im Millisekundenbereich zu sparen, und gäbe den Registrierungen eines presets eine Lebensdauer, die kein agent besitzt.

**Den Scope-Schlüssel des agents zum preset machen.** Sessions auf einem preset würden gratis eine Ebene teilen, aber pro-agent-Registrierungen — `installAgentLlmTarget`, pro-agent Tool-Beschränkungen — würden dann über Sessions hinweg kollidieren.

**Jedes preset als Kindprozess ausführen.** [`subagent-dsh-sdk`](../../../../packages/subagent/subagent-dsh-sdk/README.de.md) beweist bereits, dass ein vollständiger Kind-Harness funktioniert, und die Isolation wäre absolut. Es bedeutet aber auch, Streaming, Approvals und Projektionen pro Session zu proxen — ein Transport-Projekt, kein Kompositions-Projekt.

**Produkt-subagents globale Enable-Settings und eine eigene Settings-Seite geben.** Der prozessweite Wert würde mit dem preset um die Ownership modellsichtbarer Tools konkurrieren und könnte nicht ausdrücken, dass zwei Sessions unterschiedliche Kompositionen nutzen. Produkt-Provider bleiben Host-seitig, während gewöhnliche preset-Zeilen unabhängig Codex- und Claude-Code-Tools exponieren.

**Ein preset für jede Codex- und Claude-Code-Kombination ausliefern.** Vier Identitäten duplizieren die volle preset-Komposition, um zwei unabhängige Zeilen abzubilden. Ein kopiertes preset kann jede Zeile direkt aktivieren; Kombinations-presets fügen also Verzeichnis- und Wartungskosten hinzu, ohne ein Nutzergebnis zu liefern.
