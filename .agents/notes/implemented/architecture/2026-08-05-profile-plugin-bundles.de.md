# Agent Note: Profil-Plugin-Bundles ersetzen die fixierten Oberflächen-Overlays
[English](2026-08-05-profile-plugin-bundles.md) | [中文](2026-08-05-profile-plugin-bundles.zh.md) | Deutsch

Status: implemented


## Problem

Der `dsh`-Launcher kodierte seine Kompositionen hart: `base.cordis.yml` + `web.cordis.yml` innerhalb von `apps/cli` ausgeliefert, drei maßgeschneiderte Entry-Modi (`--config`, `web`, `-p`) mit jeweils eigenem Schichtenstapel und ein einziges globales persönliches Overlay (`$DSH_HOME/config.yaml`). Es gab keinen Weg, ein Out-of-Tree-Plugin (ein TUI, ein Provider-Pack) in eine ausgelieferte Oberfläche zu installieren, ohne das Repository zu bearbeiten, und keinen Ort, an dem ein Drittanbieter-Package eine Default-Komposition beisteuern konnte.

## Entscheidung

Alles wird ein **Profil**: ein Verzeichnis `$DSH_HOME/profiles/<name>` mit einer `package.json` (pnpm-verwaltete Out-of-Tree-Plugin-`dependencies` plus das Profil-manifest `dsh.profile` mit seiner geordneten `bundles`-Schichtenliste) und einem Nutzer-`cordis.patch.yml`. Ein **Bundle** ist ein npm-Package, das `"dsh": { "bundle": { "patch": "./cordis.patch.yml" } }` deklariert; die beiden manifest-Arten leben unter getrennten `dsh.profile`-/`dsh.bundle`-Schlüsseln, sodass eine package.json aussagt, welche Rolle sie spielt. Der Baum komponiert über einer leeren Wurzel, indem der patch jedes Bundles in `dsh.profile.bundles`-Reihenfolge angewendet wird, dann die Nutzerschicht und `--patch`-Overlays — ein `applyEntryPatches`-Call, den boot und `--dump-config` teilen. App-Aufrufwerte zogen später von launcher-abgeleiteten Patches zu Startup-Services um, in der [app-owned command-line-Entscheidung](../../archived/architecture/2026-08-06-app-owned-command-line.md).

Die Default-Profil-Templates nutzen `@deepseek-ai/dsh-base` als geteilten Kern für `web`, `headless`, `sdk` und `acp`, mit einem Modus-Bundle darüber. Das [eigenständige `sdk-minimal`-Profil](../../../../packages/bundle/sdk-minimal/README.de.md) listet stattdessen ein Bundle, das seinen kompletten expliziten Baum besitzt. Generisches `dsh --profile <name>` reicht seine restlichen Argumente an die Command-Line-Startup-Zeile dieses Profils weiter: Web besitzt seine Flag-Familie, headless besitzt sein Task-Positional, und die Protokoll-Profile akzeptieren keine App-Optionen. Patch-Overlays nutzen das launcher-eigene `--patch`. Ein neues, nicht ausgeliefertes Ziel kann `--from-default-profile <template>` nutzen, um die Bundle-Liste und Patch-Reload-Policy eines Default-Templates vor boot oder config dump zu kopieren. Das erzeugt ein unabhängiges Profil mit leeren Dependencies und einem leeren Nutzer-patch: Es liest weder ein vom Template benanntes lokales Profil noch zeichnet es eine Vererbungsbeziehung auf. Der Launcher beansprucht das komplette Zielverzeichnis exklusiv; bestehender State und konkurrierende Erzeuger scheitern daher ohne Veränderung. `dsh plugin --profile <name> <args...>` ist ein dünner pnpm-Forwarder, der ein base-gestütztes Profil initialisiert und `dsh.profile.bundles` mit installierten Bundle-Deklarationen abgleicht; ein Package ohne Bundle-Deklaration bleibt eine schlichte Dependency. [Headless als direkter Core-Entry-Point](../../archived/architecture/2026-08-09-headless-direct-core-entry-point.md) besitzt den headless-Kompositionsvertrag.

Die Auflösung ist konstruktionsbedingt zwei-verankert: `dsh.profile.bundles`-Namen lösen zuerst aus der dsh-Installation auf, dann aus dem Profilverzeichnis — In-Box-Bundles kommen also immer aus derselben Installation wie das laufende `dsh`, und pnpm verwaltet sie nie — während bare Plugin-Namen in patch-Zeilen über den Node-Parent-Walk des Profilverzeichnisses in den gepflegten flachen Fallback `$DSH_HOME/profiles/node_modules` auflösen (ein symlink pro Package, von dem App und Bundles der Installation abhängen, bei jedem Start geheilt).

Zwei begleitende Refactorings: Das eingebaute statische dist-Serving des webservers wurde zum **Fallback-Seat** mit einem Owner (`registerFallback`/`applyIndexTaps`), wobei der SPA-Server nach `@deepseek-ai/dsh-host-frontend-static` extrahiert wurde, sodass das Web-Bundle sein dist als Komposition besitzt, nicht als Launcher-Code; und die Personal-Overlay-Maschinerie der [dsh-CLI-Personal-Config-Entscheidung](../../archived/feature/2026-07-20-dsh-cli-personal-config.md) (`loadPersonalPatches`, `$DSH_HOME/config.yaml`) wurde auf die pro-Profil- und Home-Ebenen-`cordis.patch.yml`-Schichten umgezielt (`loadOptionalPatches`, `watchUserPatches` mit einem Dateinamen) — sie ersetzt die Entry-Modi und den Dateiort jener Note, behält aber Harness-Home-Root, Patch-Semantik und fail-loud-Parsing.

## Erwogene Alternativen

- **Dependency-Scan plus partielles `patchOrder`** (der ursprüngliche Entwurf): `dependencies` nach Bundles zu scannen und ungelistete alphabetisch zu ordnen hat zwei Quellen der Wahrheit und einen impliziten Tiebreak; eine explizite geordnete `dsh.profile.bundles`-Liste ist kleiner und voll deterministisch. Ein rohes `pnpm add` im Profil installiert eine Bibliothek, ohne einen patch zu aktivieren — explizit, kein Spuk-Scan.
- **`link:`-Einträge für In-Box-Bundles**: pnpm kann ein `link:` nicht in die Installation versionieren, installieren oder aktualisieren; es bettet einen Maschinenpfad in eine Nutzerdatei ein und bricht, wenn die Installation umzieht. Die Zwei-Anker-Auflösung plus geheiltem symlink-Fallback gibt dieselbe Garantie („Bundles kommen aus der Installation") ohne Zeremonie.
- **Ein Pre-Boot-`context`-Modul im Bundle-manifest** für Boot-Zeit-Werte (dist-Pfad, Flag-Fakten): abgelehnt zugunsten reiner Plugins — der Klebstoff sind gewöhnliche Zeilen und app-eigene Startup-Services; die Komposition bleibt also voll dumpbar und das manifest bleibt reine Daten. Die launcher-bereitgestellten Host-Slots (`ctx.cmdlineArgs`, `ctx.appExit` und der Environment-Snapshot) werden in `boot()`s `prepare`-Hook bereitgestellt, bevor irgendein Config-Tree-Entry mountet.
- **Transitive Bundle-Auto-Anwendung**: Nur direkte `dsh.profile.bundles`-Einträge tragen Schichten bei; ein Meta-Bundle, das den patch eines anderen Bundles re-exportieren will, muss das explizit in seiner eigenen patch-Datei tun.
- **Dynamische Template-Vererbung oder Klonen eines lokalen Profils**: Einen Parent aufzuzeichnen erforderte Merge- und Upgrade-Regeln für Bundle-Mitgliedschaft, Dependencies und Nutzer-patches, während das Kopieren lokalem State maschinenspezifische Entscheidungen duplizierte. Template-basierte Erstellung kopiert nur einmal installations-eigene Defaults.

## Konsequenzen

- Neue Kompositions-Oberflächen (ein TUI, Provider-Packs) werden als gewöhnliche npm-Packages ausgeliefert, installierbar pro Profil, ohne eine Repository-Zeile für jede Deployment-Form.
- Nutzer können ein unabhängiges Custom-Profil von jedem ausgelieferten Anwendungs-Template starten, ohne maschinenlokalen Profil-State zu kopieren.
- `apps/cli` schrumpfte auf argv-Parsing, Profil-Maschinerie-Konsum und den pnpm-Forwarder; `AppCLIEntry` und die pro-Oberfläche-Boot-Pfade sind weg.
- Das schlüssellose Web-e2e-Scaffold bootet dieselben Bundle-Schichten über derselben leeren Wurzel-Form wie die Produktion, einschließlich des Profil-Modul-Fallbacks; Kompositionsdrift zwischen Test und Produkt schlägt also laut fehl.
- Unter der Pre-Release-Haltung tragen Backends kein Kompatibilitätsverhalten für alte On-Disk-Konfiguration; `$DSH_HOME/config.yaml` wird ignoriert.
