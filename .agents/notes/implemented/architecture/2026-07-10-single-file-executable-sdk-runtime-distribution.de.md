# Agent Note: Single-File-Executable SDK-Runtime-Distribution (single-exe)
[English](2026-07-10-single-file-executable-sdk-runtime-distribution.md) | [中文](2026-07-10-single-file-executable-sdk-runtime-distribution.zh.md) | Deutsch

Status: implemented


## Problem

DeepSeek Harness braucht eine dedizierte SDK-Distributionsform für die Python-Bibliothek — keine Node-Installation, läuft direkt auf der Zielplattform: eine Single-File-Executable (fortan „die exe"), die ein stdio-JSON-RPC-Serving-Interface exponiert (`HarnessSdkJsonRpcServer`, der Peer des Python-SDK), wobei die tatsächlich gebooteten Plugins und die Konfiguration vollständig durch ein `cordis.yml` entschieden werden, das von außerhalb der exe geliefert wird.

- Das JSONRPC-Protokoll zur Kommunikation mit dem Python-SDK ist bereits validiert
- Ein standardisierter Weg, wie cordis.yml jedes Plugin (ESModule) lädt, wird benötigt
- Die Distribution muss die Node-Runtime mitführen und einen lokal gelinkten Source-Debugging-Modus unterstützen

## Entscheidung

### Packaging-Route: @yao-pkg/pkgs `--sea`-Modus

Die exe wird mit dem **`--sea` (enhanced SEA)-Modus** von [@yao-pkg/pkg](https://github.com/yao-pkg/pkg) (der aktiv gepflegte Fork, nachdem vercel/pkg archiviert wurde) gepackt. Relativ zu Nodes nativem SEA fügt pkg obenauf ein `/snapshot`-VFS und Runtime-Modul-Hooks hinzu, reicht den ESM-Entry unverändert an Nodes Default-ESM-Loader und hängt von keiner ESM→CJS-Transpilierung ab.
> Gemessen (macos-arm64, node24-Target, pkg 6.21.0): Bare-Specifier-ESM-Dynamic-Import innerhalb des VFS (einschließlich Top-Level-Await), CJS-Interop, `node:sqlite`, Fail-Loud bei Paketnamen außerhalb des Sets und On-Disk-ESM-Import außerhalb des VFS bestehen alle; `import.meta.url` kommt unverändert als `file:///snapshot/...` durch.

`--sea` erfordert Target ≥ node22; die exe targetet einheitlich node24. Ein pkg-Aufruf packt genau ein Target; Multi-Plattform-Builds rufen es einmal pro Plattform auf.

`@yao-pkg/pkg` ist eine exakt gepinnte Root-`devDependency`, aufgerufen als `pnpm exec pkg`, mit [`patches/@yao-pkg__pkg@6.21.0.patch`](../../../../patches/@yao-pkg__pkg@6.21.0.patch), der den `patchChildProcess`-Aufruf des SEA-Bootstrap entfernt. Ungepatcht schreibt pkg gespawnte Befehle namens `node` um — einschließlich des Strings nach einem `-c`/`/c`-Flag, genau die `bash -c`-Form des Bash-Tools — auf die Executable selbst und stempelt `PKG_EXECPATH` in jede Child-Umgebung, sodass ein modell-ausgegebenes `node --version` stillschweigend die dsh-CLI bootet; Nodes eigene SEA-Schicht führt kein solches Rewrite durch, und eine SEA-Binary kann schlichtes Node nicht imitieren, weil sie immer ihre eingebettete App bootet. Mit dem entfernten Aufruf lösen Kinder `node` über PATH auf wie jeder andere Prozess (eine Maschine ohne Node meldet ehrlich command-not-found), kein `PKG_EXECPATH` erreicht Kinder, absolute `process.execPath`-Spawns re-enter weiterhin die App, Worker-Threads wendeten den Hook nie an, und `process.pkg`-Sidecar-Auswahl bleibt unberührt.

Terminologie-Erinnerung: pkgs `/snapshot`-VFS hat nichts mit dem „snapshot" des Testing-Systems dieses Repos zu tun (ACP-Replay-Expected-Outputs, `$DSH_SNAPSHOT`); dieses Dokument sagt „VFS" für erstere.

### Das Serving-Interface ist ein Plugin innerhalb der dsh-Anwendung

Die deterministische Serving-Oberfläche ist ein Plugin, das die gepackte `dsh`-Anwendung auswählt:

- [`packages/sdk/server`](../../../../packages/sdk/server/README.de.md) (`@deepseek-ai/dsh-sdk-jsonrpc-server`): das reine Protokoll-Plugin; bei Apply mountet es `HarnessSdkJsonRpcServer` plus einen zeilen-delimitierten JSON-RPC-Transport auf dem Prozess-stdio, mit Disposal über `ctx.effect()`. Ob geservt wird, entscheidet `cordis.yml`; ein yml, das es nicht mountet, ist ein legitimer Prozess, der nicht servt. Protokoll-Level-Exit gehört zum Plugin (nach Beantwortung und Flushen der `shutdown`-Antwort disposed es die Root-Runtime, damit Persistenz drainet, dann `exit(0)`; ein HMR-artiger Unload stoppt nur den Service, ohne den Prozess zu beenden).
- [`apps/cli`](../../../../apps/cli/README.de.md) (`@deepseek-ai/dsh`): der gepackte Anwendungs-Entry; sein `sdk`-Profil mountet `dsh-sdk-jsonrpc-server`, und die CLI besitzt Environment-Layering, Profil-Komposition, stdin/Signal-Shutdown und Prozess-Exit.

Der Python-Client liefert ein explizites Harness-Home und wählt das `sdk`-Profil plus geordnete Patch-Dateien. Ein fehlendes Home, Profil, Bundle oder Server-Row failt laut; es gibt kein externes Complete-Config-Fallback. [docs/architecture.md](../../../../docs/architecture.de.md) besitzt diese Anwendungs-Oberfläche.

### Plugin-Resolution: Das VFS hält einen echten Paketbaum, das Closure-Manifest IST die Deploy-Root

Innerhalb des VFS der exe sitzt ein **echter Paketbaum in Build-Artefakt-Form** (jedes Pakets `lib/` plus ein echtes `node_modules`). Der gepackte JSON-RPC-Entry liefert seine installierte Harness-Basis an App-Boots Root-Include: Relative Plugin-Spezifizierer lösen aus dem externen Konfigurationsverzeichnis auf, während Bare-Paketnamen aus dem VFS auflösen, sodass eine Konfiguration innerhalb eines anderen Node-Projekts das gepackte Plugin-Set nicht überschatten kann. Die gewöhnliche Development-Bin lässt Bare-Pakete config-owned. Bare-Spezifizierer im gepackten Entry lösen aufwärts entlang `node_modules` von der Position des Entry innerhalb des VFS auf und landen natürlich innerhalb des VFS. Das geschlossene Set braucht keinen Allowlist-Code — das Set ist, was immer das VFS installiert hat, und ein Name außerhalb des Sets zu importieren failt.

Die Deploy-Root ist [`python/sdk-runtime/package.json`](../../../../python/sdk-runtime/package.json) (`dsh-python-runtime-closure`, ein pnpm-Workspace-Mitglied und ein Zero-Code-Pure-Dependency-Manifest) — die einheitliche Source of Truth für „welche Plugins die exe shippt" und „was die Python-Runtime distribuiert". Ein Plugin zur exe hinzufügen = eine Dependency-Zeile zum Manifest hinzufügen und neu packen. [`scripts/verify-runtime-closure.ts`](../../../../scripts/verify-runtime-closure.ts) liest jedes geshipte `packages/preset/agent-presets/presets/*/agent.cordis.yml`, evaluiert `disabled`-Bedingungen, die `process.platform` vergleichen, für jedes Target in `python/sdk-runtime/platforms.json` und verlangt jedes aktive Workspace-Plugin an der Runtime-Root durch eine explizite `workspace:`-Dependency. Es traversiert außerdem jedes Workspace-Paket, das dieses Manifest abdeckt, und verlangt jeden nicht-optionalen Workspace-Peer, wobei es die komplette Preset- oder Referenzierungs-Paket-→-fehlende-Dependency-Kette meldet; unbekannte Plattform-Bedingungen bleiben aktiv, sodass ein Plugin nicht durch einen nicht unterstützten Ausdruck weggelassen werden kann. `pnpm run hygiene`, CI static und der Single-exe-Build führen es vor dem Packen aus. Deploy packt außerdem nach jedem Pakets `files`, sodass die Shared-Chunks, die tsdown heraustrennt, von `files` abgedeckt sein müssen.

Die Deploy-Root enthält `@deepseek-ai/dsh-mcp-client` als explizit unterstütztes Custom-Config-Plugin, obwohl kein geshiptes Preset es mountet. Eine externe Config kann daher zu User-gelieferten stdio- und Streamable-HTTP-MCP-Servern verbinden und deren Tools registrieren; die Distribution führt diese Server nicht mit und erweitert die Bridge nicht auf MCP-Resources und -Prompts. Die Executable- und Installed-Wheel-Smokes starten einen temporären stdio-Server, entdecken sein Tool und vollenden einen modell-angeforderten Call.

### Build-Pipeline und Artefakte

[`scripts/build-exe-for-python-sdk.ts`](../../../../scripts/build-exe-for-python-sdk.ts): Runtime-Closure-Verifikation → `pnpm run build` → (nach Clearing) `pnpm --filter dsh-python-runtime-closure deploy --legacy --prod --config.node-linker=hoisted --config.auto-install-peers=false --config.link-workspace-packages=true` **direkt in** `python/sdk-runtime/src/deepseek_harness_runtime/runtime/node/`, einschließlich [`python/sdk-runtime/runtime-bootstrap.mjs`](../../../../python/sdk-runtime/runtime-bootstrap.mjs) als Carrier-Root-`runtime-bootstrap.mjs` → direkte Workspace-Pakete wiederherstellen, die Legacy-Deploy weglässt, und jede verbleibende Manifest-Lücke rejecten → gestagte Dependency-Symlinks durch ihre Ziel-Bytes ersetzen, Paketmanager-`.bin`-Links entfernen und failen, falls ein Symlink bleibt → den deployten Bootstrap verifizieren und pkg-Konfiguration mit diesem Bin plus Assets injizieren, die dynamische Profil-, Bundle-, Frontend-, Preset-, Native-Library- und Konfigurations-Reads abdecken → das Target-`node-pty`-Addon stagen → `pkg --sea` einmal pro Target aufrufen → `deepseek-harness-sdk-runtime-<platform>-<arch>` unter `dist-exe/` schreiben und in das Runtime-Verzeichnis kopieren. Die Python-Runtime besitzt diesen Bootstrap. Sie ruft den öffentlichen CLI-Export für gewöhnliche Launches auf und dispatcht eine Provider-private Auswahl an denselben `@deepseek-ai/dsh-subprocess-local/runner`-Kern, ohne CLI-Grammatik zu ändern oder eine weitere Executable hinzuzufügen; die [Native-Containment-Entscheidung](2026-08-28-subprocess-native-containment.de.md) besitzt diesen privaten Pfad. Linux-CI rebuildet `pty.node` innerhalb des passenden manylinux-2.28-Containers, weil Legacy-Deploy diesen Install-Side-Effect weglässt. Jedes Target kopiert seine native `@vscode/ripgrep`-Binary neben die Executable als erforderlichen `-rg`-Sidecar; pkg-Runtimes wählen diesen Sidecar über `process.pkg`, während gewöhnliche Node-Ausführung `@vscode/ripgrep` direkt nutzt. macOS nutzt sein Target-Prebuild und emittiert außerdem den erforderlichen `-spawn-helper`. Alle vier Deploy-Flags sind in Messung fundiert: `--legacy` ist der verpflichtende Pfad bei ausgeschaltetem Inject-Workspace-Packages; Hoisted gibt pkg ein stabiles Single-Instance-Layout, das der explizite Materialisierungs-Pass symlink-frei macht; automatische Peer-Installation zu deaktivieren verhindert, dass undeklarierte Peers die Closure aufblähen; Link-Workspace-Packages wählt direkte Workspace-Dependencies. [`pnpm-workspace.yaml`](../../../../pnpm-workspace.yaml) überschreibt die transitiven `@deepseek-ai/cosmokit`- und `@deepseek-ai/schemastery`-Semver-Requests auf die gepinnten Vendor-Quellen, sodass Legacy-Deploy diese unveröffentlichten Namen nie aus einer Registry auflöst.

CI: [`.github/workflows/build-exe-for-python-sdk.yml`](../../../../.github/workflows/build-exe-for-python-sdk.yml) führt [Installed-Wheel-Validierung](../testing/2026-08-23-installed-python-wheel-black-box-ci.de.md) auf Linux/Windows x64 für Pull Requests und Linux ARM64 plus beide macOS-Architekturen für Master-Pushes aus. Der [öffentliche Publikations-Workflow](../../archived/process/2026-08-11-python-publication-workflow.md) ruft es für alle fünf Targets auf; `workflow_dispatch` kann weiterhin eine Teilmenge wählen. Native Builds laufen auf linux-x64 / linux-arm64 (`ubuntu-24.04-arm`) / macos-arm64 / macos-x64 (`macos-15-intel`) / win-x64 (`windows-2025`), mit `~/.pkg-cache` gecacht wo anwendbar, und pkg übernimmt macOS-Ad-hoc-Signing. Jeder Leg installiert die Release-förmigen SDK- und Runtime-Wheels in ein sauberes venv außerhalb des Checkouts, beweist ihre Paket- und Executable-Provenance und treibt dann das komplette keyless Szenario-Set durch das öffentliche SDK und direktes NDJSON-JSON-RPC. Trusted Pull Requests und Master-Pushes führen zusätzlich einen echten DeepSeek-Two-Turn-Tool-Smoke auf ihren gewählten Targets aus; Fork- und Dependabot-Köpfe erhalten keinen Key. Linux inspiziert die GLIBC-Anforderungen der Executable und des nativen Addons und führt einen zusätzlichen manylinux-2.28-Smoke aus, während macOS die Architekturen von Runtime, ripgrep und PTY-Helper prüft und verifiziert, dass alle drei Deployment-Targets zum Wheel-Tag passen. Ein voller Fünf-Target-Lauf behält sechs Artefakte, jedes mit einer Release-Datei: das plattform-unabhängige SDK-Wheel und fünf native Runtime-Wheels; ein Subset-Dispatch behält das SDK-Wheel und die gewählten Runtime-Wheels. Bare-Executables und Source-Bundles bleiben Zwischen-Test-Inputs. [`.gitlab-ci.yml`](../../../../.gitlab-ci.yml) akzeptiert `python-v<repository-version>`-Tag-Pipelines, deren Version zum Root-`package.json` passt, baut ein SDK-Wheel und fünf native Runtime-Wheels, dann prüft und publiziert ein einzelner serialisierter Job alle sechs zur Projekt-PyPI-Registry. Das [`python/sdk-runtime` README](../../../../python/sdk-runtime/README.de.md) besitzt das Windows-Target und den expliziten Ausschluss von Windows arm64.

### Python-SDK-Distribution: zwei Carrier, exe für Produktion, node für Entwicklung

Das Python-SDK lebt unter [`python/`](../../../../python/README.de.md): `python/sdk` ist der Client und `python/sdk-runtime` das Runtime-Carrier-Paket. Das Datenverzeichnis des Runtime-Pakets hält die Build-injizierte Plattform-Executable mit ihrem erforderlichen `-rg`-Sidecar und optionalem macOS-Helper plus den Build-injizierten `runtime/node/`-Closure-Baum für Repository-Entwicklung. `resolve_bundled_launch_args()` wählt standardmäßig die Executable; explizites `DSH_RUNTIME_MODE=node` führt `runtime/node/node_modules/@deepseek-ai/dsh/lib/bin.js` auf System-Node 22.19 oder neuer aus. Der Node-Carrier kommt nie in Wheel-Distributionen, und kein Carrier nutzt ein eingechecktes komplettes `cordis.yml`.

[`scripts/build-python-release.py`](../../../../scripts/build-python-release.py) liest die autoritative `X.Y.Z`- oder Prerelease-Version aus dem Repository-Root-`package.json`, konvertiert Prereleases in ihre PEP-440-Schreibweise und staget beide Pakete auf dieser Wheel-Version, wobei `deepseek-harness-sdk` exakt vom passenden `deepseek-harness-runtime-bin` abhängt. Ein optionaler `python-v<repository-version>`-Release-Tag ist eine Konsistenz-Assertion und wird rejected, wenn er von der Repository-Version abweicht; der `pyproject.toml`-Development-Sentinel bestimmt nie eine Release-Version. Staging trägt außerdem die Repository-Lizenz in beide Wheels und die Third-Party-Notices ins gebundelte Runtime-Wheel. Das SDK ist ein `py3-none-any`-Wheel; jedes Wheel-only-Runtime-Paket enthält eine exe und ihren architektur-passenden ripgrep-Sidecar, und das macOS-Wheel enthält außerdem seinen architektur-passenden Spawn-Helper. Runtime-Wheels nutzen `py3-none-manylinux_2_28_x86_64`, `py3-none-manylinux_2_28_aarch64`, `py3-none-macosx_14_0_arm64`, `py3-none-macosx_14_0_x86_64` oder `py3-none-win_amd64`; der Hatch-Hook rejectet sdists, Universal-Tags, Mixed-Platform-Payloads, fehlende oder extra Sidecars und nicht unterstützte Plattformen. Beide macOS-Tags deklarieren bewusst eine konservative 14.0-Installations-Untergrenze: Die gepackten Node-24-Executables deklarieren macOS 13.5 und der x64-PTY-Helper deklariert 10.7, aber Release-Validierung beweist den kompletten Payload nur gegen den 14.0-Wheel-Claim, statt jedes beobachtete Komponenten-Minimum als unterstützten Host zu versprechen. Die beiden macOS-Wheels bleiben architektur-spezifisch; kein universal2-Wheel wird publiziert.

Der Python-Client startet den gepackten `dsh`-Befehl mit dem gewählten Profil (`sdk` als Default), geordneten Patch-Dateien und einem expliziten Harness-Home. Das Profil besitzt JSON-RPC-Serving und Anwendungs-Komposition; fehlende Homes, Profile, Bundles, Patches und Server-Rows failen ohne externes Complete-Config-Fallback.

### Naming-Lineage

`dsh-python-runtime-closure` ist das private Deploy-Manifest und `deepseek-harness-sdk-runtime-<platform>-<arch>` ist die Executable-Familie. Der Wire-`serverInfo.name` ist `deepseek-harness-sdk-runtime`; die Python-Distributionsnamen sind `deepseek-harness-sdk` / `deepseek-harness-runtime-bin`, während die Import-Module `deepseek_harness` / `deepseek_harness_runtime` sind.

## Disposition der Worker-artigen Plugins

`dsh-workflow-worker-thread` und `dsh-code-runtime-worker-thread` werden innerhalb der exe unterstützt. Ihre gebauten Hosts konvertieren die Sibling-`lib/worker.cjs`-URL mit `fileURLToPath()` und reichen den resultierenden Dateisystem-String an `Worker`, was die Form ist, die pkgs Worker-Hook innerhalb des VFS auflöst. Die Worker-Entries sind CommonJS, weil dieser Hook VFS-Worker-Dateien als CommonJS kompiliert. Die Workflow-Engine behält ihren Data-URL-Bootstrap für ungebaute Source-Ausführung; nur ihr gebauter Sibling-Entry nutzt den Dateisystem-String. Der Custom-Config-Executable-Smoke lädt beide Backends, ruft einen echten `run_code`-Call und einen Zero-Agent-`workflow`-Call auf und verlangt, dass jeder Worker `42` aus pkgs VFS zurückgibt.

## Testing

Die Verifikations-Oberfläche hat drei Ebenen. Mechanismus-Ebene: Die gemessenen Schlussfolgerungen für die `--sea`-Kette sind in den Entscheidungs-Sektionen eingebettet (ESM-Dynamic-Import innerhalb des VFS, einzelne Cordis-Instanz, Fail-Loud-Config-Kette, `node:sqlite`, macOS-Ad-hoc-Signing-Läufe). SDK-Ebene: Die komplette keyless pytest-Suite deckt das Client-Protokoll gegen einen Fake-Runtime-Peer, Subprocess-Cleanup, absolute cwd-Propagation, Dual-Carrier-Launch und Carrier-Resolution ab; Root-CI führt sie auf Python 3.10 aus. End-to-End-Ebene: Jeder Plattform-Build installiert beide Wheels in ein sauberes venv außerhalb des Checkouts, beweist passende Versionen und installierte Modul-/Executable-Orte, vollendet dann Turns gegen einen Mock-Endpoint durch den Default-SDK-Pfad, eine Custom-Config, die eingecheckte Standalone-Minimal-Komposition und das direkte Binär-Protokoll, mit finalem Text und JSONL geprüft. Der Minimal-Lauf assertet seinen exakten System-Prompt und Single-Shell-Tool-Katalog und behält Shell-Zustand über Calls hinweg. Die Custom-Config treibt zusätzlich `run_code` und einen Zero-Agent-`workflow` durch ihre echten Worker-Dateien innerhalb des gepackten VFS. Das Filesystem-Search-Szenario verlangt, dass das Modell sowohl `glob` als auch `grep` über den Target-nativen `-rg`-Sidecar aufruft. Das Spawn-Node-Szenario treibt das Plattform-Shell-Tool durch einen mit `node` beginnenden Befehl und verlangt die eigene Node-Version der Maschine im Tool-Ergebnis ohne `PKG_EXECPATH` in der Child-Umgebung, was die gepackte Runtime gegen ein pkg-Upgrade pint, das den Child-Prozess-Patch re-recordet. Das MCP-Szenario startet einen temporären externen stdio-Server, verzögert bewusst seine initiale `tools/list`-Antwort und startet dann sofort den ersten SDK-Prompt; der Prompt muss das entdeckte Tool sehen und aufrufen, was beweist, dass `initialize` eine echte Loader-Settlement-Readiness-Grenze ist statt ein Timing-Sleep. Derselbe Installierte-Lauf vergleicht einen committed Executable-spezifischen Snapshot durch das Python-SDK: Ein keyless gescriptetes Modell mountet ein Cordis-Plugin, das ein Tool registriert, ruft dieses Tool aus `run_code` auf, führt einen direkten Spawn-Subagent und einen Workflow aus, der ein zweites Spawn-Kind startet, und unmountet dann das Plugin. Die Fixture deaktiviert explizit ihr ungenutztes gebundeltes Bash und lokale Skill-Discovery, damit ihr Tool-Set nicht von Repository-externem Zustand abhängt, und der Vergleich normalisiert opake Message-, Agent-, Workflow-Run- und Session-IDs über das SDK-Ergebnis und den Notification-Stream plus die Parent- und zwei Child-JSONL-Logs. Trusted Pull Requests fügen einen Real-Provider-Two-Turn-Datei-Write/Read hinzu, dessen externe Bytes, Tool-Calls, Completed-Reasons und persistiertes Log übereinstimmen müssen. Dieser Harness bleibt getrennt von ACPs `pnpm run test:snapshot`, weil sich Protokolle und Build-Artefakte unterscheiden.

Manual-Driving-Caveat: Die Bin behandelt stdin-EOF als „der Client ist weg" und disposed sofort, sodass eine kurzlebige Pipe einen in-flight Turn abbricht — Pipe-getriebene Läufe müssen stdin offen halten, bis der Turn endet.

## Erwogene Alternativen

**Bare Node native SEA.** Das injizierte Main-Script muss eine einzelne CJS-Datei sein, und der Blob trägt kein Dateisystem und keine Modul-Resolution, sodass ein Dynamic-Import eines Bare-Spezifizierers nichts hat, gegen das er auflösen könnte; die einzige Option ist, Plugins statisch ins Main-Script zu kompilieren und von Hand zu registrieren — was Standard-Modul-Resolution umgeht und das Plugin-Set hardcodiert, entgegen „Konfiguration entscheidet alles". Die finale Route ist tatsächlich „die offizielle SEA-Grundlage + pkgs VFS/Module-Hook-Schicht"; was abgelehnt wurde, ist die Bare-Nutzung, nicht SEA selbst.

**pkg Standard-Modus.** Vom PoC gekillt, kein Trade-off: Er wandelt ESM via esbuild in CJS + V8-Bytecode um, die Runtime-VM-Kompilierung verdrahtet keinen Dynamic-Import-Callback, jedes `import()` wirft `ERR_VM_DYNAMIC_IMPORT_CALLBACK_MISSING`, und `--options experimental-require-module` hat keinen Effekt; außerdem hängt er von Community-gepatchten Node-Binaries ab (kein macos-arm64-Prebuilt; aus Source vor Ort zu kompilieren dauert etwa 10 Minuten). Null Viabilität für die Architektur dieses Repos.

**Jedes Paket ESM→CJS ins VFS vor-bündeln.** Der Kompromiss, der echte Resolution-Semantik behält und nur das Modul-Format downgradet; `--sea` bestand die Messung direkt, sodass diese Build-Komplexitätsschicht nie eingeführt werden musste.

**jsonrpc-agent trägt die vollen Closure-Dependencies.** Die App-Bin würde 53+ Dependencies deklarieren, die sie nie importiert — ein „Packaging-Manifest", das sich als echte Dependency-Beziehungen tarnt — und würde Constraints zwingen, zwei Ausnahmen für sie zu öffnen, cordis-in-dependencies und ein Files-Wildcard. Mit dem Closure-Manifest auf dem Python-seitigen Manifest-Paket braucht Constraints gar keine Ausnahme, und die Bin behält die normale Paketform isomorph zu acp-agent.

**Ein offenes Plugin-Set (User-Plugins von Disk laden).** Das geshipte Set ist geschlossen; der PoC bestätigte nebenbei, dass On-Disk-ESM-Import außerhalb des VFS funktioniert (über den `ctx.baseUrl`-Relative-Pfad-Kanal). Es ist als zukünftige Evolution gelistet, die separat lösen muss, wie man die Cordis-Instanz innerhalb der exe mit externen Plugins teilt.

## Konsequenzen

**Gekauft**: Zero-Dependency-Single-File-Distribution auf Zielplattformen; Plugin-Semantik strikt identisch zum Laufen aus Source (derselbe echte Paketbaum, keine Transpilierung, keine Registry); das Serving-Interface, das Plugin-Set und die Konfiguration konvergieren alle auf zwei Sources of Truth — `cordis.yml` plus ein Dependency-Manifest; die exe- und node-Carrier teilen einen Baum und eine Semantik, sodass Development-Verifikation nie auf Packaging wartet; offizielle Node-Binaries entfernen das Patched-Binary-Supply-Chain-Problem.

**Bezahlt**: Artefakte in der Größenordnung von 174MB, wobei Source as-is in den Blob eingeht (keine Bytecode-Obfuskation; ein Closed-Source-Distributions-Requirement braucht eine separate Evaluierung); pkgs VFS/Module-Hook-Schicht bleibt Community-maintained (`@yao-pkg/pkg` ist eine exakt gepinnte, pnpm-gepatchte Root-devDependency; ein Upgrade re-recordet den Patch und ist eine explizite Änderung); `--sea` ist ein Aufruf pro Target (passt zu CIs einem Leg pro Plattform; lokale Multi-Plattform-Builds sind seriell).
