# Agent Note: Handle-basierte Session-Persistence

Status: implemented

[English](2026-08-27-handle-based-session-persistence.md) | [中文](2026-08-27-handle-based-session-persistence.zh.md) | Deutsch

## Problem

Der bisherige persistence-seam besaß weit mehr als Storage. Ein geteilter Koordinator abonnierte `session/created`/`session/event`/`session/flush`/`session/disposed` und adoptierte jede publizierte Session (ownerlose claims, HMR-Re-Seeding, stored-prefix-Adoption); ein begrenzter prepared-Session-LRU mit exklusiven reservations bediente resume und read-only-observation aus einem cache; committete crash repair lebte in `load`/`prepare`; und optimistische revision-read/check/read-Schleifen standen für Ownership, sodass ein kontinuierlicher externer writer einen read livelocken konnte und nichts einen zweiten writer ausschloss. Die service-Oberfläche (zwölf Methoden) vermischte Storage mit Session-Konstruktion und Lifecycle. Prozessübergreifende write-Ownership — der nächste Schritt — hat in dieser Form kein ehrliches Zuhause: Ownership gehört zu einem expliziten per-session-Kanal mit einem Owner, nicht zu einem globalen listener.

## Entscheidung

**Der seam besteht aus fünf service-Methoden, die per-session handles zurückgeben oder bedienen.** `create(header)` speichert eine neue Session und liefert ihren owned write handle; `open(id, 'read' | 'write')` öffnet eine bestehende; `stat(id)`/`list()` beobachten Snapshots (`header`, opake `revision`, optionale `eventCount`/`sizeBytes`-hints — das JSONL-backend liefert `sizeBytes`), ohne Logs zu lesen; service-level `flush()` ist eine backend-weite durability-Barrier, die jeden aktiven write handle drainiert und flusht und per-session-Fehler aggregiert, ohne den sweep abzubrechen. Der seam trägt kein raw-artifact-export: der WebUI-ZIP-Download serialisiert das logische Log (header-Zeile + events) aus einem read handle in `dsh-session-log-export`, sodass jedes backend identisch exportiert und der JSONL-only-501-Pfad entfällt. Ein `SessionHandle` trägt `read(offset?, length?)` (validierte zusammenhängende Präfix-Slices, nie ein zerrissener tail, monoton pro handle), `append` (zusammenhängend; persistence ist best-effort bei resolution, und das ausgelieferte JSONL-backend persistiert zufällig jeden batch sofort), `flush` (die durability-Barrier, die zugleich eine leere Session materialisiert) und idempotenten, nicht abbrechbaren `close`. Ein handle-Typ bedient beide Zugriffe — eine Mutation auf einem read handle ist ein runtime-`SessionReadOnlyError`, die bewusste Konvention der anderen seams dieser codebase statt einer typisierten Trennung. Single-writer-Ownership wird in-process durch eine registry (`SessionAlreadyOwnedError`) erzwungen; das durable prozessübergreifende Lease ist die geplante nächste Schicht auf derselben Form.

**Der agent-Lifecycle besitzt die handle-Akquise; das backend besitzt den event-getriebenen Fluss.** agent-loop — der einzige Produktions-Publikationspunkt für Sessions — erwirbt den handle vor der Publikation (`create` für frische Sessions, wobei ein eventueller constructor-seed darüber angehängt wird; `open(id, 'write')` für resume) und schließt ihn in demselben memoized teardown, das den loop drainiert. Weil die persistence bereits einen aktiven write handle pro Session-id erzwingt, installiert das backend die Session-listener einmal und routet nach id: `session/event` in das begrenzte write-behind-Fenster des besitzenden handles (eine interne Scheduling-Policy, keine Konfiguration), `session/flush` als durability- und Fehlerbeobachtungs-Barrier, `session/disposed` als finaler drain und close. Nichts am write path überschreitet die Paketgrenze — keine writer-Komponente, keine batching-Konfiguration, keine drain-registry. Root-fiber-disposal führt die disposers aller fibers nebenläufig aus, daher drainiert `close()` selbst den gerouteten Puffer durch den noch offenen storage; der close-sweep des backend-teardowns hält den application shutdown verlustfrei, egal welcher fiber zuerst abwickelt. Der drain garantiert nur gepufferte bereits-emittierte events; ein root dispose mitten im turn verliert den nicht emittierten Rest des turns weiterhin by design — `interruptedTurnClosers` des nächsten resume reparieren diesen tail durable. Außerhalb des Lifecycles publizierte Sessions persistieren nicht mehr implizit; nichts in der Produktion tut das.

**Semantische crash repair ist aus der persistence herausgezogen.** Resume liest das physisch gültige Log über seinen write handle, berechnet `interruptedTurnClosers` und hängt sie (plus den `session/end-seed`-Marker des constructors) über denselben handle an wie gewöhnliche batches — repair ist kein besonderer storage-Einstiegspunkt. Read-only-observer (session-query) balancieren ein unterbrochenes kaltes Log nur im Speicher und besitzen ihren eigenen cold-Session-cache, auf `stat().revision` gekeyed; der persistence-seitige prepared cache und die revision-Konvergenzschleifen sind gelöscht.

**Sichtbarkeit und Freshness sind explizit.** Eine erzeugte Session ist in-process ab `create` beobachtbar; die physische Materialisierung darf (eine reine Optimierung) bis zum ersten append oder flush aufgeschoben sein, andere Prozesse sehen nur materialisierte Sessions, und ein crash vor der Materialisierung bedeutet, dass die Session nie existierte. Sobald ein append oder flush resolved, beobachten danach gestartete reads auf derselben backend-Instanz mindestens dieses Präfix — die Garantie, auf der die durable-target-Prüfung von `message-feedback` reitet.

**Revision vereinfacht sich zu einem per-instance-Änderungstoken.** Gleiche tokens dürfen als unverändertes Log behandelt werden; Ownership-Wechsel ändern ein token nie. JSONL leitet ein best-effort-token und `sizeBytes` aus einem `fs.stat` ab; ein backend, dessen Medium events billig zählen kann, darf stattdessen den `eventCount`-hint liefern. Session-Listing bleibt eine Metadaten/cache-Operation ohne body-read: sie vertraut einem gecachten nonblank-Wert, behält einen gecachten blank-Wert nur bei übereinstimmender aktueller cache-Identität und meldet sonst `blank: false` als sichtbaren unbekannten fallback. Keine kalte blank-probe oder probe-limit-Konfiguration bleibt.

## Erwogene Alternativen

**Typisierte read/write-handle-Klassen (oder overloads).** Als seam-Stil abgelehnt: die seams dieser codebase bevorzugen einen zugriffsgetaggten Typ mit runtime-Ablehnung, und die Trennung würde jeden consumer-seitigen Typ für eine compile-time-Prüfung verdoppeln.

**Den adoption/HMR-write-path des Koordinators neben handles behalten.** Abgelehnt: adoption existiert, um Ownership nachträglich zu erraten; da der Lifecycle den handle explizit übergibt, lässt ein reloadetes backend, das alte handles nicht bedienen kann, den writer laut fehlschlagen, statt Logs still erneut zu claimen, und eine Session ohne handle ist ein Kompositionsfehler, der durch fehlende persistence sichtbar wird statt durch adoption maskiert.

**Ein service-level `append(id, events)` neben handles.** Abgelehnt: ein id-adressierter write path umgeht Ownership; jeder write fließt durch den besitzenden handle, damit die künftige lease-Prüfung genau eine Tür hat.

**Persistence-geführte batching-Konfiguration.** Abgelehnt: das batching-Fenster ist internes write-path-Scheduling, keine deployment-variierende Wahl, daher ist es eine provider-Konstante und es existiert nirgends ein Konfigurationsknopf.

## Konsequenzen

Resume-, fork-, subagent-, ACP-, webhook- und SDK-Sessions persistieren alle über einen expliziten Akquise-Punkt, und dispose gibt die write-Ownership nachweisbar frei (erneutes Öffnen zum Schreiben gelingt nach teardown). Die Kosten: ein backend-plugin-reload unter live Sessions invalidiert ihre handles — writes schlagen laut fehl, bis die Sessions neu starten, wo adoption früher still wieder anband; `ctx.sessions.create` + `flush` in einem Test persistiert ohne handle nichts (Tests seeden über `create`/`append`/`close`); resume liest ein kaltes Log nur dann erneut, wenn keine unmittelbar vorangehende Observation dasselbe Artefakt parste — ein begrenztes provider-lokales memo (Session-id + stat revision, bei jeder lokalen Mutation invalidiert) bedient die observe-then-promote- und authorize-then-resume-Übergaben, ohne den gelöschten borrow/reservation-Lifecycle wiederherzustellen, und der eigene prepared cache des session-query-readers bleibt die pin-fähige Schicht darüber (eine spätere Konsolidierung mag das eine ins andere falten); und eine leere erzeugte Session ist für andere Prozesse unsichtbar, bis ein expliziter flush erfolgt (ACP erzwingt einen für sein resumable-empty-session-Versprechen). Handle-Ownership ändert die serialisierte Session-Repräsentation nicht.
