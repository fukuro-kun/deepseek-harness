# Agent Note: Serielle plattformübergreifende CI-Referenz
[English](2026-07-21-serial-cross-platform-ci-reference.md) | [中文](2026-07-21-serial-cross-platform-ci-reference.zh.md) | Deutsch

Status: implemented


## Problem

Der Pull-Request-Workflow konsolidiert die erforderlichen Checks in dedizierte Linux- und Windows-Jobs. Diese Jobs sollten dennoch nicht das einzige Vollständigkeits-Orakel sein: Ein Defekt in ihrem Gate-Inventar oder Abhängigkeitsgraphen könnte Arbeit auslassen, während das erforderliche Aggregat grün bleibt.

Das Eincodieren des Ein-Minuten-Ziels für Nicht-Windows und des Drei-Minuten-Ziels für Windows als Job-Timeouts erzeugt einen separaten Fehlermodus. Startzeit und Leistung gehosteter Runner variieren, sodass ein korrektes Gate an der Zielgrenze abgebrochen werden kann, bevor es brauchbare Diagnostik ausgibt. Das Leistungsziel braucht eine Messung anhand von GitHub-Zeitstempeln, während die Korrektheit genug Zeit zum Abschluss braucht.

Reviewer brauchen außerdem eine direkte Antwort auf eine einfachere Frage: Was passiert, wenn das vollständige primäre Node-CI-Aggregat des Repositories ohne Matrix-Auswahl, Shard-Variablen oder konkurrierende Gates auf jedem ausgewählten gehosteten Betriebssystem läuft?

Real-Kernel-Sandbox-Nachweise erfordern spezifische gehostete Betriebssysteme und Architekturen, liefern aber kein Merge-Urteil für Pull Requests. Die Wiederholung dieser Vier-Job-Matrix für jeden Pull Request verbraucht Linux-, arm64-Linux- und macOS-Kapazität, ohne Branch Protection zu erfüllen oder zum erforderlichen Aggregat in einem anderen Workflow beizutragen.

## Entscheidung

[CI](../../../../.github/workflows/ci.yml) (nur Pull Request) und [CI master](../../../../.github/workflows/ci-master.yml) (master-Push + `workflow_dispatch`) geben Pull-Request- und Master-Push-Ereignissen komplementäre Zuständigkeiten. Pull Requests führen Linux, natives Windows, [Node-Kompatibilität mit Self-Hosted-Routing unter der Linux-Variable und den Trust-Bedingungen](2026-09-06-node-compatibility-selfhosted.de.md) sowie Python-Checks aus; die [Plattform-Zeitplanung](2026-09-06-master-only-platform-ci.de.md) weist Wine und drei Python-Runtime-Träger den Master-Pushes zu. Bei einem Push auf `master` sind die aktiven Referenzen `serial / linux (self-hosted standby)` auf dem hauseigenen `vm-backup`-Pool und `serial / windows (self-hosted standby)` auf dem hauseigenen `dsh-win-ci`-Pool — die Hot-Standby-Übungen, die die im [Failover-Runbook](2026-07-26-ci-failover-runbook.de.md) beschriebenen Failover-Ziele kontinuierlich erneut nachweisen. Es gibt keine standard-gehostete `serial / linux`-Definition; die standard-gehostete `serial / macos` bleibt unter `TODO(hosted-serial-ci)` deaktiviert, bis ihre portable Kapazität wiederhergestellt werden kann. Die aktuelle `serial / windows`-Definition ist der hauseigene `dsh-win-ci`-Standby. Die getrennten Job-Definitionen halten ihre kurzen Checkout-, Runtime-Setup- und Immutable-Install-Sequenzen absichtlich sichtbar, statt Betriebssysteme hinter einer Matrix oder einem wiederverwendbaren Workflow zu verstecken. `workflow_dispatch` ist für Runner-Benchmarks reserviert.

Jeder Referenz-Job führt `pnpm run check:ci` ohne jede Shard-Auswahl aus. `DSH_GATE_CONCURRENCY=1` lässt das Top-Level-Aggregat jeweils ein bereites Gate ausführen; Coverage, Snapshot-Replay, Built-Bin-Smoke und Publikationsvalidierung erhalten ebenfalls Worker-Zahlen von eins. Die Referenz-Jobs dürfen nebeneinander laufen, aber die Repository-Gates jedes Hosts sind seriell und vollständig. Linux installiert bubblewrap vor dem Replay der Snapshots, und Windows aktiviert den Entwicklermodus, bevor der verlinkte Workspace installiert wird.

Die Plattform-Zugehörigkeit bleibt innerhalb dieses vollständigen Aggregats explizit. `terminal-bash` unterstützt Linux und macOS und besitzt daher seinen Unit- und Per-File-Coverage-Vertrag unter POSIX, statt ein Backend zu laden, das `win32` ablehnt; der Windows-Lauf führt dennoch jedes portable Package aus. Portable Fixtures leiten native Pfade über `node:path` ab, vergleichen kanonische Identitäten mit derselben nativen realpath-Implementierung wie die Produktion und verwenden Dateinamen, die auf jedem Host legal sind. ACP-Snapshot-Läufe übergeben zudem sowohl die JavaScript- als auch die native realpath-Schreibweise ihres erzeugten cwd an den Normalisierer, der Aliase längste-zuerst ersetzt, damit kurze und lange Windows-Pfade geteilte Fixtures nicht verändern können.

Die macOS-Referenz führt das gewöhnliche Vitest-Projekt in geforkten Prozessen aus. Node 24 ist auf macOS arm64 in seinem CJS-Lexer aus einem Worker-Thread heraus abgebrochen; die Prozessgrenze enthält diesen externen Runtime-Ausfall, ohne einen Test aus dem Aggregat zu entfernen, während Linux und Windows den Thread-Pool mit geringerem Overhead behalten. Repository-eigene Races werden an ihren Beobachtungsgrenzen behoben: Das Polling des Dev-Bundles stuft jede Kandidaten-Tabelle, -Graph und Watch-Baseline-Map zwischen, bevor ein Rescan veröffentlicht wird, und ein fehlendes Bundle bleibt dirty, bis ein erfolgreicher Content-Hash vorliegt. Die PTY-Bereitschaft behält einen Prompt-Kandidaten, während das Polling die Foreground-Zugehörigkeit prüft; die gewöhnliche Silence-Grenze deckt von interaktiven Kindern geerbte Marker ab. Reale PTY-Fixtures bauen Synchronisations-Tokens zur Laufzeit zusammen, damit das Input-Echo der interaktiven Shell kein Child-Readiness-Wait erfüllen kann. Das Live-Link-Package-Manager-e2e bewahrt das vom Workflow vorbereitete Corepack-Home sowie die pnpm-Metadaten- und Store-Caches, während es die veränderlichen Caches der anderen Manager isoliert, sodass es wiederverwendbaren Package-Manager-Zustand vor der Installation nicht verwirft.

Der eigenständige [Sandbox](../../../../.github/workflows/sandbox.yml)-Workflow gehört zur Referenzseite derselben Teilung. Seine bwrap-, Landlock-x64/arm64- und Seatbelt-Real-Kernel-Matrix läuft nur nach einem Push auf `master`. Diese vier Jobs sind diagnostisch: Sie sind keine Branch-Protection-Anforderungen und speisen `all checks passed` nicht über Workflow-Dateien hinweg. Die Pull-Request-CI prüft Sandbox-Quellcode weiterhin durch ihr gewöhnliches Unit- und Coverage-Inventar; die Host-Kernel- und Packed-Install-Nachweise berichten nach dem Merge.

Master-Referenz-Jobs sind diagnostisch und nehmen am erforderlichen `all checks passed`-Ergebnis des Pull Requests nicht teil. Die ci-master- und Sandbox-Workflows behalten ihre plattformübergreifenden Referenzen auf Master-Pushes. Die Leistung wird aus Zeitstempeln abgeschlossener gehosteter Jobs ausgewertet und als Messung berichtet; sie wird nicht als `timeout-minutes`-Wert encodiert.

Die aktiven seriellen Referenzen laufen auf den Self-Hosted-Pools `vm-backup` (`serial / linux`) und `dsh-win-ci` (`serial / windows`); die einzige verbleibende deaktivierte gehostete serielle Referenz (`serial-macos`) verwendet `macos-latest`, und es gibt kein standard-gehostetes `serial / linux`-Label. Der nur-für-Master bestimmte Wine-Job läuft auf `ubuntu-latest`, während die nativen Pull-Request-Jobs im Normalbetrieb den gehosteten `dsh-windows-2025-16core`-Runner und unter Failover den Self-Hosted-Pool `[self-hosted, dsh-win-ci, windows]` verwenden (siehe das [Failover-Runbook](2026-07-26-ci-failover-runbook.de.md)), wobei Build- und gezielte Prozess-Checks unter der [nativen Windows-Entscheidung](2026-08-08-native-windows-pull-request-ci.de.md) erforderlich sind. Erforderliche Pull-Request-Jobs verwenden portable Standardkapazität unter der [Required-CI-Entscheidung](../../archived/process/2026-07-23-portable-required-pull-request-ci.md). Gehostete Runner mit mehr Kernen bleiben manuelle Benchmarks, weil ein Korrektheitspfad ohne repository-externe Runner-Konfiguration lauffähig bleiben muss.

## Erwogene Alternativen

- **Jedes Timeout gleich seinem Latenzziel setzen** — abgelehnt, weil Scheduling-Varianz korrekte Arbeit abbrechen und die zur Diagnose einer Regression nötige Evidenz unterdrücken würde.
- **Nur dem konkurrierenden Primär-Inventar vertrauen** — abgelehnt, weil Scheduling und Validierung Implementierungsannahmen teilen; ein serielles Aggregat ist eine unabhängige Vollständigkeitsprüfung.
- **Die seriellen Referenzen auf jedem Pull Request ausführen** — abgelehnt, weil sie vollständige plattformübergreifende Aggregate duplizieren und jeder Änderung macOS-Arbeit hinzufügen; die erforderlichen Jobs führen bereits die blockierenden Linux- und nativen Windows-Checks aus, und die anderen nativen Jobs liefern das vollständige Windows-Ergebnis.
- **Die Real-Kernel-Sandbox-Matrix auf jedem Pull Request ausführen** — abgelehnt, weil ihre vier Status nicht an Branch Protection teilnehmen, während wiederholte Installs, Landlock-Builds und macOS-Unit-Parität Runner-Kapazität verbrauchen, ohne das Merge-Urteil zu ändern. Der Master-Lauf behält das Plattform- und Installed-Launcher-Signal.
- **Eine einzige Betriebssystem-Matrix verwenden** — abgelehnt, weil drei benannte Jobs die Referenzfläche ohne einen weiteren Auswahlmechanismus sichtbar machen.
- **Die serielle Referenz auf größeren Runnern ausführen** — abgelehnt, weil sowohl die erforderliche CI als auch ihre unabhängige Referenz lauffähig bleiben müssen, wenn organisations-eigene Pools keine Jobs zuteilen können.

## Konsequenzen

Der Workflow enthält duplizierte Setup-Schritte, und ein Master-Referenzlauf kann deutlich länger dauern als der optimierte Pull-Request-Pfad. Diese Duplikation ist bewusst: Reviewer können das vollständige Kommando jedes Betriebssystems inspizieren, ohne eine Matrix oder einen konkurrierenden Scheduler auflösen zu müssen.

Die Referenz kann Plattformfehler offenlegen, für die das optimierte blockierende Set noch keine Unterstützung beansprucht, insbesondere unter Windows. Ein solcher Fehler ist Evidenz über das aktuelle plattformübergreifende Verhalten, kein Grund, das Aggregat abzuschwächen oder still zu überspringen.

Eine Sandbox-Regression, die nur für einen realen Host-Kernel oder den gepackten Landlock-Install sichtbar ist, kann gemergt werden, bevor der Master-Lauf sie meldet. Dieses Post-Merge-Erkennungsfenster wird akzeptiert im Tausch dafür, vier nicht-blockierende Jobs aus jedem Pull Request zu entfernen; der Default-Branch behält das vollständige Signal.

Die explizite `terminal-bash`-Zugehörigkeitsgrenze bedeutet, dass Windows keine Coverage für ein Backend beansprucht, das es nicht laden kann, und geforkte macOS-Unit-Worker kosten mehr Prozessstartzeit. Im Gegenzug hat jede unterstützte Fläche ein ehrliches Plattform-Orakel, ein nativer Runtime-Abbruch kann den Rest des Unit-Ergebnisses nicht auslöschen, und timingempfindliche Beobachter starten von Zustand, der etabliert wurde, bevor Aufrufer ihn mutieren können.

Das Entfernen strikter Dauer-Timeouts bedeutet, dass eine Latenzregression beobachtet statt automatisch abgebrochen wird. Gehostete Messungen müssen daher Leistungsänderungen begleiten, während die abgeschlossenen Logs die zur Optimierung der langsamsten Spur nötige Information behalten.
