# Teststrategie

[English](testing.md) | [中文](testing.zh.md) | Deutsch

Wie dieses Repository Tests durchführt, Ebene für Ebene, und die Regeln, die eine grüne Testsuite sinnvoll halten. Befehle stehen im Wurzel-[AGENTS.md](../AGENTS.md); verlinkte Agent Notes tragen die Begründung.

## Ebenen

- **Unit** (`pnpm run test`): vitest über Package- und Beispiel-Specs in ihren `tests/**`-Verzeichnissen sowie Repository-Skript-Specs unter `scripts/**/*.spec.ts`; Tests verbleiben beim Codebereich, den sie ausüben. Jede Registry erhält einen HMR-Sicherheitstest (den beitragenden fiber disposen, Cleanup assertieren). Bevorzuge Randfälle, Fehlerpfade, Ereignisreihenfolge, Nebenläufigkeitsraces und dauerhafte Tests für Vertragsregressionen (siehe `packages/core/agent-loop/tests/contract-regressions.spec.ts`).
- **Coverage-Gate** (`pnpm run test:coverage`): der Gate-Lauf, pro Datei 100% auf `packages/*/*/src`. Eine ungedeckte Zeile ist oft toter Code, den das Gate zum Löschen markiert, nicht ein fehlender Test, der angeflanscht werden muss. Zeilenabdeckung ist notwendig, nie hinreichend — sie beweist, dass Zeilen liefen, nicht dass das Feature wie ausgeliefert funktioniert. Pro-Datei-100% auf `packages/shell/pwsh-local/src` benötigt ein echtes `pwsh`: ohne eines überspringen sich dessen Executor-Suites und `vitest.config.ts` exemptiert die Datei, sodass pwsh-lose Hosts grün bleiben, während CI-Runner pwsh mitbringen und die volle Latte durchsetzen.
- **Real-API-e2e** (`pnpm run test:e2e`): With-Key-Tests gegen Live-Provider-APIs — das DeepSeek-Modell plus providerspezifische Smokes, die auf eigene Keys gate-en (`EXA_API_KEY`, `PERPLEXITY_API_KEY`, …); jede Suite überspringt sich ohne ihren Key selbst, sodass keyless CI grün bleibt ([Real-API-e2e-Agent-Note](../.agents/notes/implemented/testing/2026-06-19-real-api-e2e-ci.de.md)).
- **Owner-lokale Expected-Output** (`pnpm run test:expected`): keyless assemblierte CLI/Prozess-Expectations ohne Recorded-Session-Roundtrip. Treiber verwenden `*.expected.e2e.ts` neben `tests/expected/`; CI führt gebaute Exporte aus. Package-/Skript-Expectations verwenden `test`, Browser-Expectations `test:web`.
- **Performance-Benchmarks** (`pnpm run test:bench`; erforderliches Linux-PR-Gate `node 24 / benchmarks`): `benchmarks/` gruppiert User-Path-Gates. Es baut Libraries und Worker; zeitgemessener Code läuft unter plain Node, nie TSX. Synthetische Inputs setzen Zeit-, Heap- und Skalierungs-Budgets durch; paketlokales `.perf.ts` bleibt Diagnose ([Regeln](../.agents/notes/implemented/testing/2026-09-04-session-open-performance-gate.de.md)).
- **Snapshot** (`pnpm run test:snapshot`): die höchste aufgezeichnete Parent-Generation eines Top-Level-Szenarios liefert User-Input und Modell-Replay und dient dann als erwartetes persistiertes Ergebnis. Parent-Dateinamen sind `session[.vN].jsonl`; Child-Rollen sind `session.<ordinal>[.vN].jsonl`; v0 lässt `.v0` weg, positive Versionen erfordern kleingeschriebenes `.vN`, und jeder Dateiname muss mit seinem Header übereinstimmen. Prozess-Szenarien starten durch `dsh`: Headless besitzt One-Shot-Verhalten, das SDK besitzt persistente Kontrolle, ACP besitzt Automationsprotokoll-Verhalten, und Web behält Browser-/ARIA-Evidence neben derselben Session. `snapshot.yml` deklariert Profile, Composition-/Header-Klasse, Aufzeichnungs-Policy, Ausnahme-Replay- oder Input-Metadaten und Workspace-Fakten. Typisierte Tokens bewahren Parent-/Child-Identitätsbeziehungen; nur Header pin-ownen Prompt-/Schema-Sidecars. Ein mutierendes Szenario vergleicht den vollständigen `workspace.expected/`-Baum unabhängig, den Record und Refresh nie umschreiben. Verwende `test:snapshot:record`, wenn sich ein Modell-transcript ändert, und `test:snapshot:refresh`, wenn Replay-Input gültig bleibt; prüfe jeden resultierenden Diff.
- **Web-Browser-Snapshot** (`pnpm run test:web`; erforderliches Linux-PR-Gate): Chromium vergleicht Session-getriebenen Output unter `snapshots/web/` und UI-only-Output unter `apps/web/tests/expected/`. CI erzwingt read-only `DSH_SNAPSHOT=replay`, schreibt nie Expected-Outputs; Record/Refresh bleiben lokal und jeder Diff wird geprüft ([Web-e2e-Lane](../.agents/notes/implemented/testing/2026-07-24-web-gui-browser-e2e-lane.de.md), [CI-Gate-Entscheidung](../.agents/notes/implemented/testing/2026-07-30-web-browser-snapshot-ci-gate.de.md)). `test:web` baut zuerst für Plugin-CSS.

Session-Fixtures behalten Header und Payloads, lassen aber Body-Seq-/Time-Envelopes weg; Replay synthetisiert sie. Replay, Record und Refresh wählen die höchste Generation jeder Parent-/Child-Rolle. Aktuelle Fixtures verwenden das [Writer-Format](session-format-status.de.md) in ihren Dateinamen und Headern, eine Zeile pro Event, und eingebettete kompakte Assistant-Streams. Historische Fixtures behalten ihre veröffentlichte Repräsentation; explizite `sessionFormat`-Owner bewahren Migrationsabdeckung. Folge dem [Format-Version-Cookbook](cookbook/adding-a-session-format-version.de.md#snapshot-successors), um Nachfolger hinzuzufügen, ohne Vorgänger zu ändern.

## Wie Specs ausgeführt werden

Geforkte Worker führen mehrere Spec-Dateien gleichzeitig aus, das Coverage-Gate teilt sich in nebenläufige Partitionen neben den anderen Gates in seinem Job, und die Self-Hosted-Runner teilen sich einen Host und einen Volume. Isoliert ist nur der Prozess: Ports, vorhersagbare Pfade, externe Namespaces und geerbte Children sind es nicht. Besitze jede akquirierte Ressource über ihren Teardown, und lese eine Spec, die nur allein läuft, als Defekt der Spec, nicht als instabilen Runner. [dsh-ci-test-reliability](../.agents/skills/dsh-ci-test-reliability/SKILL.md) besitzt die Allokations-, Restorations-, Synchronisations-, Timeout-Budget-, Plattform- und Teardown-Regeln; sein [Flake-Diagnose-Workflow](../.agents/skills/dsh-ci-test-reliability/references/ci-flake-diagnosis.md) klassifiziert einen bestehenden probabilistischen Fehler.

## Die With-Key-Policy: Inference ist hier billig

Wir sind DeepSeek — rationiere keine Real-API-Tests. Ein No-Key-Test beweist Plumbing; nur ein With-Key-Lauf beweist, dass der agent gegen ein echtes Modell funktioniert. Decke Datei-schreibende Prompts, Multi-Turn-Conversations, Tool-Use und Mid-Stream-Cancellation ab. Höchsten Wert haben **Smoke-Tests**, die ein ausgeliefertes `dsh`-Profile booten, einen Prompt senden und die Welt prüfen — sie fangen die „grüne Unit-Tests, kaputtes Produkt"-Klasse, die mocks nicht können ([Postmortem 0001](postmortem/0001-acp-default-export-drops-inject.de.md)). Self-Skip hält Secretless-CI und keyless Contributor frei; es ist kein Kostensignal. Profile-Level-Integrationstests leben unter `apps/cli/tests/profiles/`; paketspezifische Compositions bleiben bei ihren Package-Tests.

## Bevorzuge die echte Implementierung über einen mock

Mock nur die teure oder nicht-deterministische Grenze (LLM-Adapter, Netzwerk, Clock); halte alles stromabwärts echt. Ein handgefertigter Stand-in beweist, dass die Bridge Bytes bewegt, nicht dass das ausgelieferte Tool sich wie behauptet verhält. Bridge-Tool-Call-Tests behalten die echte Tool-Registry und Pipeline hinter dem gescripteten Mock-Modell: `makeBridgeHarness()` mountet den agent loop, den Session-Store, die Tool-Registry und JSONL-Persistenz mit einem `MockAdapter` als einzigem Mock (packages/acp/acp/tests/harness.ts).

Recovery-Tests trennen Pre-/Post-Chunk-Fehler nach Step und beweisen, dass fehlgeschlagene Chunks keine Message- oder Tool-Side-Effect ableiten. Decke Exhaustion, Cancellation, Policy-Composition, Persistenz, Status, Wire-Counts, Transport-schließende Idle-Timeouts und ausgelieferte Loader-Composition ab.

## Verifiziere die Welt, nicht den Self-Report

Ein e2e-Assertion re-runnt den Befehl oder re-readed die Datei extern; eine Keyword-Probe auf dem agent-Eigenoutput lässt einen schummelnden agent passieren. Assertiere, dass unberührte Dateien byteidentisch sind. e2e-Tests besitzen ihre Ressourcen: erstelle sie im Test, dispose in `afterEach` (auch bei Failure/Retry/Timeout); Shared-Fixtures leben in einer simplen `tests/harness.ts`, nie in einem anderen `*.e2e.ts` (Importieren einer Spec re-registriert deren `describe` und dupliziert echte API-Aufrufe).

## Teste den echten Entry-Path

- Produkt-sichtbare Plugins erfordern einen nicht-Unit-REAL-Composition-Test. Handgebaute `ctx.plugin(...)`-Suites reichen nicht: boote test-only `cordis.yml` durch Loader und App/Process, mock nur externe Services oder nicht-deterministische Inputs, und assertiere modell-sichtbare Request/Log, dauerhaften State oder User-sichtbaren Output. Halte Opt-Ins aus ausgelieferten Defaults heraus.
- Ein Guard guardet nur, wenn die Regression ihn failt. Für ein Plugin ohne `inject` (Bundle-/Composition-Plugins) bleibt ein Loader-Smoke grün, wenn ein Default-Export die benötigten Named-Exports ersetzt — füge ein explizites `expect('default' in mod).toBe(false)` plus eine `unwrapExports`-Roundtrip-Assertion hinzu und beweise es: Regression einführen, rot beobachten, revertieren.
- „Echter Entry-Path" bedeutet das veröffentlichte Artefakt: ein Package-`bin` läuft gebautes `lib/bin.js` unter plain `node` und exponiert Failures, die tsx maskiert (Settle-Races, Module-Resolution, verschluckte Load-Failures). Dasselbe gilt für Non-Index-Runtime-Entries (das Worker-Thread-Sibling `lib/worker.cjs`) und Singleton-Module, die über Bundles geteilt werden (`packages/sdk/server/tests/built-scope-carrier.e2e.ts`). Halte die Built-Artefact-Smokes grün (`packages/examples/*/tests/built-bin.e2e.ts`, `packages/code-runtime/code-runtime-worker-thread/tests/built-lib.e2e.ts`), und assertiere, dass eine genuin fehlende Config non-zero exitet.

## Test-Auflösung: Nur Source-Plane

- Jede vitest-Konfiguration zeigt vite-tsconfig-paths auf `tsconfig.base.json`; Bare-Workspace-Imports resolvieren zu `src` ([Layout](development.de.md#typescript-project-layout)), nie durch Package-`exports` zu gebautem `lib/` — stale-Artefakte dort laden eine zweite Kopie von Module-Singletons. Built-Artefakte werden nur explizit konsumiert: `lib`-Mode-Subprocesses und die Built-Smokes unten.

## Test-Subprocess-Launch-Modes

- CI- und Build-habende Test-Lanes laufen jedes Profile- oder Cordis-Config-Subprocess von gebautem `lib/` durch den geteilten Dual-Mode-Launcher. Schreibe nicht manuell `--import tsx` für diese Subprozesse.
- Protokoll- und Betriebssystem-Fixtures, die Cordis nicht laden, laufen erasable `.ts` direkt mit Node, ohne tsx oder die Root-Paths-Map.
- Nur ein Test, dessen Subjekt Source-Path-Auflösung ist, darf `src` wählen; stelle diesen Vertrag im Test klar.

## Wann ein Snapshot-Test erforderlich ist

Jede nicht-triviale Modell-, Protokoll- oder Human-sichtbare Änderung fügt oder aktualisiert ein keyless Recorded-Session-Szenario im selben PR hinzu; Package-, e2e-, Mock-only- und Rationale-Evidence ersetzt nicht den assemblierten transcript. Headless-, SDK-, ACP- und Web-Aufzeichnungen leben unter `snapshots/session/`, `snapshots/sdk/`, `snapshots/acp/` und `snapshots/web/`; ein Web-Rendering darf explizit eine andere Szenario-Session ausleihen. Expected-Output, der nicht von einer Recorded-Session getrieben wird, bleibt bei seiner besitzenden App, seinem Package oder Skript unter `tests/expected/` und verwendet nicht das `*.snapshot.ts`-Suffix. [`dsh-session-snapshot`](../packages/test-support/session-snapshot/README.de.md) besitzt die Shared-Storage-Regeln und Profile-Adapter. Agent-loop-, Session-Lifecycle- und `SessionEventMap`-Änderungen aktualisieren beide SDK-Projektionen: `snapshots/sdk/` besitzt TypeScript, während [Python-Runtime-CI](../.agents/notes/implemented/process/2026-09-06-master-only-platform-ci.de.md) `scripts/snapshots/python-sdk-single-exe/` besitzt. Neue Capability-Seams und Lifecycle- oder transcript-Varianten nennen jede erforderliche Ebene zur Planzeit.
